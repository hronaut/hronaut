# Hronaut local wallets

Hronaut provides locally managed EVM, Solana, and Tron wallets to websites and MCP coding agents without giving either party private keys, seed phrases, decrypted vault data, or an approval capability. Wallets are optional and disabled for signing when Hronaut cannot establish secure vault protection. Watch-only accounts remain available.

Hronaut does **not** integrate WalletConnect, Reown, MetaMask SDK, Phantom SDK, TronLink SDK, hosted custody, hosted relays, or proprietary wallet infrastructure.

## Security boundary and threat model

The trusted signer, encrypted vault, policy engine, transaction adapters, and approval state machine run in Electron's main process. Normal website pages retain context isolation, sandboxing, and no Node.js access. The website preload exposes only validated provider methods. The Hronaut Vue renderer receives public descriptors and sanitized approval summaries, never key material or encrypted vault blobs.

Hronaut protects against a website or MCP agent directly reading keys, approving its own request, silently crossing workspace/origin boundaries, replaying a mutated approval, or automating a mainnet signature without a prior user-created, narrowly bounded delegation. Requests are bound to the wallet, workspace, top-level HTTP(S) origin, account, chain/network, requesting website or agent, active tab, navigation generation, nonce or recent blockhash when available, expiry, and a SHA-256 approval hash. Navigation, tab/workspace closure, permission revocation, or request expiry cancels applicable pending work.

Managed wallet descriptors, workspace attachments, network metadata, permission grants, automatic policies, and durable policy counters are one XChaCha20-Poly1305-authenticated authority state inside the vault. Schema-valid edits, cross-file substitution, and partial counter resets therefore fail before managed signing becomes available. The signer additionally requires a one-shot authorization minted in the current main-process run and bound to the exact approved request; a persisted request record cannot release key material by itself. Watch-only records remain outside this encrypted authority so they stay usable without a managed vault, but Hronaut rejects any watch-only record whose ID collides with an authenticated managed wallet.

The trusted approval dialog is Hronaut chrome. While it is open, website WebContents are moved out of the interactive content region; a page cannot overlay or click the approval. The dialog shows the wallet/account, network, origin, workspace, requesting agent, decoded destination/action/amount, simulation, estimated fee, expiry, approval hash, and expandable unsigned details. When an EVM transaction's simulation reverts, it also shows **Revert reason**, read from the revert data the node returns, never from the node's error text, which can name the RPC endpoint: the contract's message in its own code box (up to 200 characters, with runs of spaces and line breaks shown as one space and hidden characters as `[U+XXXX]` codes), a Solidity panic code and its meaning, a custom error selector, named when it is a common token, access-control, Permit2 or Uniswap router error, or that the contract reverted without a reason. When a transaction comes without a gas limit and the node's gas estimate reverts, Hronaut still prepares it, as other wallets do, with a fallback gas limit of 95% of the latest block's gas limit, at most 16,777,216 (the EIP-7825 cap), so the dialog can show the reason; a person who approves it anyway will usually pay gas for a failed transaction. A failed simulation still needs a person and never auto-approves. For a token call it recognizes (an ERC-20 or TRC-20 `transfer`, `approve` or `transferFrom`, an ERC-20 `increaseAllowance`, or an ERC-721 or ERC-1155 `setApprovalForAll`), it also shows the token contract. On TRON, TRX that a contract call sends along (`call_value`) appears as its native amount, and a call that also sends a TRC-10 token is shown as an unknown contract call. An approval names its spender, or for `setApprovalForAll` its operator, and warns that the spender can move the token later without another approval, with a further warning when the amount is unlimited (at least 2^160 − 1, or exactly 2^96 − 1 or 2^128 − 1, the maximum of a 96- or 128-bit allowance, which tokens that store allowances in fewer bits, such as UNI and COMP in 96 bits, treat as unlimited). An `increaseAllowance` instead warns that it adds to any allowance the spender already has, so the spender may be able to move more than the amount shown. A `setApprovalForAll` that grants access warns that the operator can move every NFT the wallet holds in that collection, including ones it receives later; one that revokes access gets no warning. ERC-721 shares the `approve` and `transferFrom` signatures, so on an NFT contract the amount shown is the token ID, and a token ID that reads as unlimited, such as an ENS name's, which is at least 2^160 − 1, also gets the unlimited warning. For a UTF-8 message signature it also shows the text itself under **Message to sign**, up to 4,096 characters. Characters that render as nothing or as blank space, or that reorder text (controls other than tab and line feed, format, bidirectional, zero-width, default-ignorable, private-use, line or paragraph separator, noncharacter and blank braille characters), appear as visible `[U+XXXX]` codes with a warning. When a message uses the sign-in phrase ("wants you to sign in with your"), the dialog warns if it names a different website, account or, for Sign-In with Ethereum, chain than the request, or if it does not follow the Sign-In with Ethereum or Solana format. TRON has no sign-in standard to check, so such text on a TRON wallet always gets that warning. For EIP-712 typed data the dialog shows **Typed data to sign**: the type, the app name and version, the chain ID and the verifying contract. It reads only fields that the request's types declare, so keys the signature does not cover cannot change the summary, and integer values are read the way the signer encodes them. It warns when the signed chain ID is not the wallet's chain, and recognizes token permits (ERC-20 and DAI `Permit`, and Permit2 allowances and signature transfers), showing the spender and up to 16 tokens with their amounts in the token's smallest units, and EIP-3009 transfer authorizations (`TransferWithAuthorization` and `ReceiveWithAuthorization`), showing the recipient and amount. When the permit or transfer declares when it ends, the dialog shows **Valid until**, the last time it can be used: the permit's `deadline` (a DAI permit's `expiry`), the second before an EIP-3009 authorization's `validBefore`, or for a Permit2 allowance the latest `expiration` of its tokens, where an expiration of zero ends at the `sigDeadline`. A DAI `expiry` of zero, any time after the year 9999 such as a maximum integer, or a value Hronaut cannot read reads **Never expires**, with a warning that the signature can still be used long after it is signed. Times before then are shown as dates, so a deadline centuries away reads as that date without a warning. It also warns when the type looks like a marketplace or exchange order (Seaport, Blur, 1inch, CoW Protocol, 0x or LooksRare `Order`-style types), which anyone can fill to take the tokens or NFTs it offers, or a Safe multisig transaction or message (`SafeTx` or `SafeMessage`), which can move the Safe's assets once enough owners sign; a Safe message makes the Safe accept whatever signature it wraps. It also warns when the request looks like a meta-transaction or a delegation: a recognized type (ERC-2771 `ForwardRequest` and Biconomy `ERC20ForwardRequest`, GSN `RelayRequest`, Gelato's `SponsoredCallERC2771` and `CallWithSyncFeeERC2771` calls and their `Concurrent` variants, native `MetaTransaction`, 0x `MetaTransactionDataV2`, ERC-4337 `PackedUserOperation` and Safe `SafeOp`), a MetaMask Delegation Framework `Delegation` with a `delegator`, or any type that signs call data in a `bytes` field named `data`, `callData`, `calldata` or `functionSignature`, since some forwarders accept a request type under any name. Someone else submits the signed call and the contract treats it as coming from this account, so it can transfer tokens like a transaction. An unrelated type that matches also gets the warning. Each permit or transfer gets a warning that the tokens can be moved without another approval, with a further warning for an unlimited amount (at least 2^160 − 1, exactly 2^96 − 1 or 2^128 − 1, or a DAI permit with `allowed: true`), including one beyond the 16 shown, and a warning to treat the signature as unlimited when an amount cannot be read. Hidden characters in the shown text appear as `[U+XXXX]` codes, and text longer than 256 characters ends with `…`. Binary messages appear only in the unsigned details, which always hold the complete request.

Hronaut cannot protect against a compromised operating system, malware running as the same user, a malicious Electron/Chromium runtime, screen or input capture outside Hronaut, a malicious RPC lying about chain state, or a user approving a misleading but accurately displayed request. JavaScript and Electron do not guarantee deterministic memory erasure; Hronaut uses short-lived buffers and best-effort overwrite after signing, but copies may exist transiently in the runtime.

Copying an older complete profile can also roll the entire locally authenticated vault back to an older valid snapshot; Hronaut does not claim a hardware-backed monotonic counter. Restore profiles only from trusted backups and review permissions and automatic policies after any restore.

## Wallet types and onboarding

Open **Settings → Wallets**. Settings are organized into four tabs:

- **Your wallets** lists existing wallets with their names, networks, account types, and public addresses. Select one to inspect its details, rename it, change its RPC endpoint, or remove it. Signing-vault locking is available here for managed accounts.
- **Add wallet** lets you generate a wallet, import a mnemonic or private key, or add a watch-only address. Generated and imported wallets can be designated as dedicated agent wallets. Choose workspace access during setup. Successful onboarding selects the new wallet in **Your wallets**.
- **Access & automation** lets you select a wallet and manage selected-workspace or **Any workspace** access, bounded signing policies, and website permissions.
- **Activity** shows request and audit-event counts and the latest 20 audit events, with a refresh action.

Vault setup, unlock controls, and errors remain visible across tabs. Switching tabs clears any unsubmitted recovery phrase or private key; non-secret form choices remain available. A validated import can be reviewed again in **Add wallet** until confirmed, cancelled, or expired.

Create separate accounts for EVM, Solana, and Tron unless you intentionally accept the larger blast radius of reusing recovery material. Hronaut never silently derives all three families from one seed.

Generated recovery material is displayed only in a native trusted Hronaut dialog. The wallet is enabled only after you confirm that the recovery material was saved; choosing **Not yet**, losing the trusted dialog, or failing to persist that confirmation discards the new wallet so an unrecoverable account is never retained. Imported material is entered only in trusted Settings, validated in the main process, cleared from the UI immediately, and retained in memory only for a five-minute confirmation window. Hronaut automatically zeroes and drops an unconfirmed import when that timer expires, even if the user takes no further action. Validation errors never echo secret fragments.

Removing a managed wallet deletes its encrypted local record and revokes its permissions and policies. Removal is not a recovery mechanism: retain your recovery material independently.

## Vault protection

Each wallet secret is encrypted with XChaCha20-Poly1305 using a random data-encryption key. Wallet ID, schema version, and chain family are authenticated metadata, so modified, truncated, or substituted records are rejected. A separate encrypted authority record authenticates the complete managed descriptor and the combined permission/policy/usage state. The vault supports data-key rotation, including re-encryption of authority metadata.

Only version-2 encrypted wallet vaults are supported, and Hronaut neither migrates nor deletes older wallet data. A version-0 or version-1 `vault.json` fails the integrity check: the wallet reports "Wallet data failed integrity checks" and both managed and watch-only wallets stay off. To use wallets again, quit Hronaut and delete `vault.json` and `requests.json`, which holds its pending requests, from the `wallet/` folder of the Hronaut application-data directory by hand. That removes the wallets the old vault held, so add them again from your recovery material. Plaintext `policies.json`, `permissions.json` and `policy-usage.json` files left by those versions are ignored and grant nothing. Current encrypted vaults and their authenticated authority remain supported.

On Windows and macOS, and on Linux with a secure Secret Service/KWallet backend, Electron `safeStorage` wraps the data-encryption key. Electron's asynchronous encryption APIs are used. On Linux, `basic_text` is never considered secure. When Hronaut detects `basic_text`, an unknown backend, or no available secure store, it requires a user passphrase and derives the wrapping key with Argon2id (64 MiB, three passes, one lane) through the MIT-licensed RustCrypto Node-API binding. Failure to initialize either protection mode disables managed signing without silently downgrading; watch-only wallets remain usable.

Wallet files live below Electron's Hronaut application-data directory in `wallet/`. Never copy `vault.json` as a substitute for recovery material. Neither the renderer nor website profiles, localStorage, IndexedDB, cookies, command-line arguments, environment variables, logs, audit events, telemetry, or MCP responses contain plaintext wallet secrets. Pending message bodies are kept only in main-process memory; the durable request record contains a digest and length.

## Website provider support

Only wallets attached to the current workspace or explicitly marked **Any workspace** are eligible. Global availability affects discovery only: an address remains hidden until that exact workspace, top-level origin, and requester receive explicit account permission, and signing still follows the normal simulation, policy, and trusted-approval flow. Cross-origin iframe wallet requests are denied by default and attributed to the top-level origin.

### EVM

Hronaut exposes an EIP-1193 provider and announces it with EIP-6963. The provider also keeps the legacy `enable()`, `isConnected()`, and `off()` helpers that older dapps call. Supported methods are `eth_accounts`, `eth_requestAccounts`, `eth_chainId`, `wallet_switchEthereumChain` for networks configured on wallets available to the current workspace, `wallet_addEthereumChain` (which switches to an already configured network and otherwise rejects with code 4001, because websites cannot add networks or RPC URLs), EIP-2255 `wallet_getPermissions` and `wallet_requestPermissions` plus `wallet_revokePermissions` for `eth_accounts` only, `eth_sendTransaction`, `eth_signTransaction`, `personal_sign`, `personal_ecRecover` (which returns the checksummed address that signed a `personal_sign` message, as MetaMask does, without a connection, a wallet key or a prompt; a signature that is not 65 bytes or cannot be recovered fails with code -32602), `eth_signTypedData_v4`, `eth_signTypedData_v3` (signed as v4 when the two hash it the same: no array types, a declared `EIP712Domain` type, and a value for every declared field; otherwise it fails with code 4200), `eth_sign`, the EIP-5792 batch methods `wallet_getCapabilities`, `wallet_sendCalls` and `wallet_getCallsStatus`, and EIP-747 `wallet_watchAsset`. Each tab and origin keeps its own active EVM network; account results include only permitted wallets on that network. Provider availability, chain changes, wallet removal, permission expiry or revocation, and vault locking publish the corresponding `connect`, `disconnect`, `chainChanged`, or `accountsChanged` event to connected dapps. Transaction and message requests select the exact permitted account requested by the dapp. Raw `eth_sign` always requires trusted human approval. A fixed set of read-only methods is forwarded to the active wallet network's RPC so libraries such as wagmi, viem, and ethers can read chain state through the provider: `eth_blockNumber`, `eth_call`, `eth_estimateGas`, `eth_gasPrice`, `eth_maxPriorityFeePerGas`, `eth_feeHistory`, `eth_getBalance`, `eth_getCode`, `eth_getStorageAt`, `eth_getTransactionCount`, `eth_getTransactionByHash`, `eth_getTransactionReceipt`, `eth_getBlockByNumber`, `eth_getBlockByHash`, `eth_getLogs`, `eth_createAccessList`, `eth_getProof`, `eth_blobBaseFee`, `eth_getBlockTransactionCountByNumber`, `eth_getBlockTransactionCountByHash`, `eth_getTransactionByBlockNumberAndIndex`, `eth_getTransactionByBlockHashAndIndex`, and `eth_simulateV1` (viem's `simulateBlocks` and `simulateCalls`); `net_version` is answered from the configured network. Log and block filters are forwarded too (`eth_newFilter`, `eth_newBlockFilter`, `eth_getFilterChanges`, `eth_getFilterLogs`, and `eth_uninstallFilter`), which ethers v6 uses to deliver contract event listeners. A filter belongs to the tab and site that created it and to the node it was created on (the network's chain ID and RPC URL), and it stays usable across the site's own navigations, such as a dApp's route changes. Any other page that sends its ID gets a `filter not found` error (code -32000), or `false` from `eth_uninstallFilter`, without reaching the node. A tab keeps at most 32 filters per site and node; beyond that, creating one fails with code -32601 and a "method does not exist" message, which makes ethers and viem fall back to polling `eth_getLogs`. Hronaut tracks filters for up to 64 tab and site pairs, removes a forgotten pair's filters from the node, and removes a tab's filters when the tab closes; the node still expires idle filters on its own schedule. Pending-transaction filters are not forwarded. Like `eth_chainId`, these reads need an eligible wallet on the active network but no account permission, and they never sign. EIP-5792 batches (`wallet_sendCalls` version `2.0.0`) run one call at a time, in order, each as an ordinary transaction with its own approval dialog or bounded policy check, exactly as if the page had sent `eth_sendTransaction` for it; a batch never bypasses a per-call approval. Later calls usually depend on earlier ones, such as a swap after its token approval, so Hronaut prepares each call only after the one before it is mined and succeeded (it waits up to 10 minutes per call while the page stays open), and stops at the first call that is rejected, fails, or reverts; if the first call does not go out, the request fails with that call's error. Because calls are separate transactions, `wallet_getCapabilities` reports `atomic` as `unsupported` on each network the account is permitted on, and a batch of more than one call with `atomicRequired: true` is refused with code 5760. A batch may hold up to 10 calls (more is code 5740), a capability not marked `optional` is refused with code 5700, a `chainId` other than the tab's active network with 5710, and an `id` the site already used with 5720. Hronaut remembers up to 32 batches per site in each workspace and 256 in total, forgetting the oldest finished batch first; a batch still sending calls is never forgotten, and a new batch is refused with code -32005 while every remembered batch is still sending. `wallet_getCallsStatus` answers only the site that sent the batch, while it keeps account permission: status 100 while calls are being sent or mined, 200 when every call was sent and succeeded, 400 when no call reached the chain because another transaction from the account took the nonce of each sent call, 500 when none succeeded, and 600 otherwise, including a batch Hronaut stopped early; `receipts` lists the mined calls' receipts and `atomic` is always `false`. An unknown or another site's batch ID gets code 5730. An agent testing the dApp sees the site's batches and where each one got to in `wallet_page_requests`, as `callBatches`. `wallet_watchAsset` accepts the token a dApp offers through an "Add token to wallet" button (`ERC20`, or `ERC721` and `ERC1155` with a `tokenId`) and returns `true` without a prompt: Hronaut keeps no token list to add it to, and accepting moves no funds and reveals no account. It needs an eligible wallet on the tab's active network, like `eth_chainId`. Like MetaMask, it reads an ERC-20's `symbol()` and `decimals()` from the contract on that network and refuses with code -32602 an offer whose symbol (ignoring case) or decimals disagree with the contract, or that leaves out a value the contract does not report; when the contract cannot be read, the page's values are not checked. It also refuses with -32602 a missing or malformed contract address, a symbol longer than 11 UTF-16 units, decimals that are not a whole number from 0 to 36, or a missing token ID, and, unlike MetaMask, a symbol with control, invisible formatting or line break characters. Like other JSON-RPC transports, the provider drops object properties whose value is `undefined` (viem leaves unset options that way) before reading a request. Node errors keep their JSON-RPC code and short revert data; the RPC URL is never returned to the page. When the node refuses a signed transaction after approval, the page and the agent get the node's JSON-RPC server error code (-32000 for a code outside -32099 to -32000, so a node cannot pass for a provider code such as 4001) and a fixed reason in Hronaut's words, such as `the node refused the transaction: nonce too low, the account already used this nonce`. Hronaut recognizes insufficient funds, nonce too low or too high, an underpriced replacement or gas price, a max fee below the block base fee, a priority fee above the max fee, a gas limit below the minimum or above the network's limit, an unsupported transaction type, another chain's transaction and an unverifiable sender; any other refusal reads `Wallet request failed validation or processing`. A node that answers that it already has the transaction, for example after a hosted RPC retried the send itself, does not fail the request while the node still holds it: as in MetaMask, Hronaut counts the transaction as sent under its own hash and waits for its receipt. If the node no longer holds it, the request fails with `the node says it already has this transaction`. Two identical requests approved at the same nonce sign the same transaction, which the network runs once, so only the first counts as sent and the other fails with `Transaction was already sent by another wallet request`. Hronaut itself never follows CCIP-Read (EIP-3668) offchain lookups: its token checks, balance reads and transaction simulations treat an `OffchainLookup` revert as a failure, shown as that custom error under **Revert reason**, instead of fetching the URLs a contract names, while a page that receives that revert data from `eth_call` can still do the lookup in the browser. Private-key, seed, raw-transaction, other RPC-forwarding, and unknown methods are rejected.

### Solana

Hronaut registers a Solana Wallet Standard wallet with connect/disconnect, events, sign transaction, sign-and-send transaction, sign message, and Sign-In with Solana (`solana:signIn`) features. Sign-in connects first if needed, then builds the standard sign-in text in the main process for the requesting top-level origin's host: a dapp-supplied `domain` or `address` that does not match is rejected, multi-line fields are rejected, and the person approves the exact text like any other message. Its standard signing features advertise legacy and version 0 transactions, so Wallet Standard adapters can send the versioned transactions most current Solana dapps build. A transaction Hronaut cannot fully decode, such as one that resolves accounts through address lookup tables, is treated as unknown and needs human approval. Account-change subscribers receive complete Wallet Standard account objects only after connection state resolves, including notifications when a connected account's chain, capabilities, public key, or display metadata changes without an address change, and receive an empty account list before legacy disconnect listeners run. Configured custom networks are added to the wallet's advertised chains before their accounts are exposed, so every account chain remains a subset of the wallet-level chain metadata. Permission expiry publishes the same empty-account and disconnect lifecycle as explicit revocation. Disconnect revokes only that Solana wallet's permission for the requesting website and cancels its matching pending requests; unrelated same-origin chain connections remain available. A narrow `window.solana` compatibility surface supports common legacy transaction objects, including legacy and versioned serialized transactions and batch signing, and emits `accountChanged` with a PublicKey-like value or `null` after its own connection state changes. The requested signer account and `solana:<network>` chain are validated.

### Tron

Hronaut exposes `window.tron` and TIP-6963 discovery without claiming to be TronLink. Its TIP-1193 surface supports `eth_accounts`, `eth_requestAccounts`, `eth_chainId`, configured-network switching, transaction signing, sign-and-send, message signing, typed provider errors, and connection/account lifecycle events. Mainnet, Nile, and Shasta use their official hexadecimal provider chain IDs. A custom network ID must itself be a canonical hexadecimal or decimal chain ID for `eth_chainId`, chain switching, and `connect` metadata to be available. Account permission expiry publishes empty accounts and a typed disconnect without waiting for another wallet mutation. After authorization, `provider.tronWeb` exposes the selected address and narrow `trx.sign`/`trx.signMessageV2` compatibility. Dapps should use their own public TronWeb instance to build unsigned transactions, then ask Hronaut to sign. Address, owner, and network consistency are validated. Hronaut also recomputes canonical Tron protobuf bytes and the transaction hash at normalization, simulation, signing, and broadcast boundaries; JSON that does not match those signed bytes is rejected.

## Approval and automation

Requests advance through `draft → validated → simulated → policy-decision → awaiting-human/approved → signing → submitted → confirmed`, or a terminal rejected, expired, cancelled, or failed state. A simulation, audit, or state-preparation error moves its request to `failed` immediately, so trusted chrome cannot approve a request whose caller already received an error. Once a human decision, cancellation, revocation, or expiry makes a request terminal, Hronaut settles its caller, stops its timer, and clears retained in-memory message bytes even if the corresponding audit write fails. An untouched request expires automatically at its displayed deadline; no approval click or application restart is required. Submitted transactions remain non-replayable while Hronaut polls for a terminal chain result, and that confirmation tracking resumes from the durable transaction hash after an application restart. On EVM networks, a submitted transaction also becomes `failed` when another transaction appears to have replaced it: the node no longer holds it and the account has already mined a transaction with its nonce, for example after a wallet elsewhere sped it up or cancelled it with the same key. Because a load-balanced RPC can briefly answer from a backend that lags behind, this must hold on at least three checks over a minute, with no pause of more than 30 seconds between two checks (such as the computer sleeping); a check the node cannot answer counts neither way. Its audit entry is marked `replaced`, and a batch stops at such a call. A node that lags behind for longer than that, or has pruned old transactions, can still make a mined transaction look replaced. A transaction the node dropped while its nonce is still unused stays `submitted`, since another node may still hold it and mine it. Submission and terminal confirmation are written to the non-secret hash-chained audit history. Signing checks the exact normalized request hash again immediately before key use and consumes a one-shot in-memory authorization. Durable request IDs and idempotency keys prevent duplicate submission.

A tab whose page is waiting on a wallet call stays awake from the moment the page calls the provider until it gets the answer, including while a `wallet_sendCalls` batch is still sending its calls: Memory Saver and the sleep commands skip it, as they skip a tab with an open dialog, because sleeping would discard the page that gets the answer while a request could still be approved and sent. Reads and filter calls that Hronaut forwards to the network's node are the exception, since they never prompt, sign or send. A request an agent made for the tab keeps it awake the same way until it is signed, refused or cancelled, or expires. While going to sleep replaces a page, that page cannot start a wallet call.

The default policy is deny/ask, including on mainnet. A user may opt one dedicated EVM agent wallet into **Bypass Approve mode** for an exact agent-only policy: one workspace, configured network, origin, destination, and method, plus the token contract for a token call; per-transaction native/token/fee limits; native-currency session/daily limits; at most 100 operations; successful simulation; and an expiry no more than seven days away. The configured, requested, and RPC-reported EVM chain IDs must agree, but that equality is not independent proof that a malicious RPC is honest; use an endpoint you trust. A matching agent transaction then signs and sends without a per-request approval dialog. This is not a blanket wallet switch: websites, ordinary wallets, Solana and TRON mainnet wallets, raw or message signing (apart from plain-text sign-in and opted-in typed data under the separate switches below), unknown or undecodable actions, unlimited approvals, and new contracts/programs still require trusted human approval. The initial account permission and creation or modification of the bypass policy also require the user in trusted Hronaut UI; an agent cannot grant itself either capability.

Automatic approval is also available for an explicit allowlist of EVM testnet chain IDs whose configured and RPC-reported IDs agree, or a known local-chain ID paired with a loopback RPC URL. Chain-ID equality is not independent proof of endpoint honesty, so use a trusted RPC even on testnets. Solana and TRON public testnets currently require human approval until their adapters can bind an independently verified genesis/network fingerprint into the request. A user-supplied `testnet` label is never trusted by itself: unknown, mislabeled, public-hosted local, and undelegated mainnet networks return to human approval. Eligible policies can restrict wallet/workspace, network, origin, destination (the recipient, spender or operator), token contract, method/instruction, per-transaction native amount, native-currency session/daily spend, fee, expiry, operation count, and successful simulation. Hronaut revalidates the exact selected policy immediately before automatic approval; removing, tightening, or allowing it to expire while a request is in flight prevents that stale request from auto-signing. A policy names transaction methods as the approval dialog shows them, such as `native-transfer`, `erc20.transfer`, `erc20.approve`, `erc20.increaseAllowance`, `erc20.transferFrom`, `nft.setApprovalForAll`, `trx.transfer`, `trc20.transfer`, `trc20.approve`, `trc20.transferFrom` or `system.transfer`. A token call (an `erc20.`, `trc20.` or `nft.` method) is signed without a person only when the policy also lists its token contract under **Token contract**, so a policy meant for one token does not cover another token sent to the same recipient or spender. A new policy for a token method must name its token contract, and a mainnet Bypass Approve policy names at most one. To turn this check off, a policy can instead use the default-off **Allow any token contract** switch, shown with a warning: its token calls to the listed recipient or spender are then signed on any token contract, so its token amount limit applies to every token, whatever it is worth. The policy list shows each policy's token contract, or that it allows any. Unknown or undecodable actions, unlimited approvals (an ERC-20 or TRC-20 approval of at least 2^160 − 1 or of exactly 2^96 − 1 or 2^128 − 1, or a `setApprovalForAll` that grants an operator access), ERC-20 `increaseAllowance` calls, which add to an allowance the policy cannot see, new contracts/programs, blind/raw messages, permission changes, recovery export, and vault changes always require a person, apart from the website account connection and typed-data signing described next.

**Website sign-in without a click** is a separate opt-in on a bounded policy: **Let this site connect and sign in without asking** under **Access & automation**. It is off by default. When it is on, a page whose top-level origin exactly matches the policy's allowed origin, in the policy's workspace, can connect that wallet (`eth_requestAccounts` or `wallet_requestPermissions`) and get `personal_sign` messages signed without a person. A message qualifies only as UTF-8 plain text of at most 4 KiB with no control, format, bidirectional, zero-width or private-use characters other than tab and line feed. Text containing the Sign-In with Ethereum (EIP-4361) phrase must parse as such a message and name the requesting site's host (and scheme, if given), this wallet's address and its chain ID; a plain-HTTP site other than a loopback development server must also name its `http://` scheme, because verifiers read a missing scheme as https. Otherwise it goes to a person. A `personal_sign` signature is valid on every chain, so other plain text is signed without a person only by a dedicated agent wallet; on a managed or imported wallet, whose key may also be used elsewhere, only matching Sign-In with Ethereum text is. Raw `eth_sign`, agent requests, other origins, Solana and TRON always ask, typed data asks unless the typed-data switch below is on, and transactions ask unless a transaction rule on the same policy covers them; leave the destination and method empty for a sign-in only policy. Each automatic connection or signature counts toward the policy's operation limit and stops at its expiry. Account access granted this way expires no later than the policy; removing the policy stops new automatic approvals but does not disconnect the site, so revoke it under **Website permissions**. On its own the switch works only on the eligible EVM testnets and loopback local chains above. Mainnet needs a second, separate **Also allow on mainnet** switch, shown with a warning, on a dedicated EVM agent wallet, with one origin, at most 100 operations and an expiry no more than seven days away; a mainnet sign-in policy without Bypass Approve lists no transaction target. Some services treat a signed message as authorization, so keep only funds you can afford to lose in such a wallet. Hronaut re-checks the policy immediately before approving, and the audit history records each automatic approval as `request-approved-by-policy`.

**Typed data without a click** is a further opt-in on a website sign-in policy: **Also sign typed data without asking**, shown once the sign-in switch is on and only for a dedicated agent wallet. It is off by default. When it is on, the allowed origin's EIP-712 typed-data requests (`eth_signTypedData_v4`, or `eth_signTypedData_v3` that hashes the same) are signed without a person if the typed data is at most 32 KiB as JSON, its signed domain names this wallet's chain ID, so the signature cannot be used on another chain, it is valid for the signer and quick to hash, and it signs a message rather than only a domain. Anything else goes to a person, and Hronaut checks typed data only for a page the policy would sign for, so other sites cannot make it do the work. Typed data can authorize token permits, transfers and marketplace orders that move tokens later, so a managed wallet, or an imported key not designated as a dedicated agent wallet, always asks. On testnets and local chains unlimited permits are signed too, since test tokens have no value. Each signature counts toward the policy's operation limit. On mainnet it also needs a second, separate **Also sign typed data on mainnet** switch, shown with a warning, under the same mainnet limits as the sign-in switch: one origin, at most 100 operations and an expiry no more than seven days away. There, a token permit or transfer authorization that Hronaut recognizes (ERC-20 and DAI permits, Permit2, and EIP-3009 transfers) still goes to a person when its amount is unlimited or unreadable, and so does a Safe transaction or message, because a Safe owner's signature can move assets this wallet does not hold, and a meta-transaction or delegation that the dialog warns about, because it is a contract call from this account that someone else submits; other typed data, such as a marketplace order or an unrecognized allowance type, is signed as requested, so this check is not a general spending limit. Hronaut re-checks both switches immediately before approving.

## MCP agent operations

The MCP catalog exposes only:

- `wallet_list`
- `wallet_balance`
- `wallet_prepare_transaction`
- `wallet_request`
- `wallet_request_status`
- `wallet_page_requests`
- `wallet_cancel_request`

`wallet_list` opens an unguessable, short-lived wallet agent session bound to the caller's server-issued MCP transport session, isolated workspace, and active tab/top-level origin. Every other wallet tool requires that returned `walletSessionId`; it cannot be used by another MCP client or in another workspace or tab, even when two clients identify with the same User-Agent, and it expires after inactivity. Agent wallet descriptors expose only the network ID, display name, and environment; configured RPC endpoints and transport credentials remain internal. Adapter failures and simulation logs are reduced to non-secret status before they cross MCP or durable approval boundaries. Request status and cancellation are also bound to the tab's exact top-level origin and navigation generation, so navigating the tab cannot carry request access into a different page. For wallet requests, only starting a navigation to another document, even one that ends as a download, begins a new page: a dApp's own route change in the same document, through the history API (`pushState` or `replaceState`) or a fragment, keeps the page's pending requests, its active EVM network and its request list. Status and cancellation responses keep the public address hidden until that exact agent session has active account permission. Starting a fresh wallet session requires account permission again. Explicit MCP session termination and listener shutdown synchronously revoke the requester, drain in-flight wallet work, and run a final durable cancellation sweep before completing; a request cannot be created, signed, or broadcast after that revocation wins. A cancellation failure is contained and reported without exposing request contents. Hronaut keeps the wallet broker and tab authority alive until that durable cleanup finishes during application shutdown. `wallet_page_requests` lets an agent that is testing a dApp read the wallet requests the page itself made: connect, message or typed-data signing, and transaction signing or sending. Each comes with its status and transaction hash. It is limited to the same tab, top-level origin and navigation generation, returns the newest 50, and keeps addresses hidden until the agent session has account permission; where a request names the wallet's own address as its source, destination or token contract, such as a transfer to itself, that field reads `this wallet (address hidden until account permission)` instead. When the site offered tokens with `wallet_watchAsset` in that tab, the result also lists the newest 20 as `suggestedAssets`, including refused ones, and keeps them across the site's own navigations. Each has the type, checksummed contract address, symbol, decimals, token ID, network ID and time, the contract's own `contractSymbol` and `contractDecimals` when it reports them, `refused` (`symbol-mismatch`, `decimals-mismatch`, `symbol-missing` or `decimals-missing`) when Hronaut refused it, and the image link without its query string when it is a plain http or https URL; other images are marked `imageOmitted`. A suggested address or image that contains a wallet's own address reads `this wallet (address hidden until account permission)` or is omitted until the agent session has account permission. The result also lists the newest 20 wallet calls the site made in that tab that failed, as `failedCalls`, kept across the site's own navigations: the chain family, the method (or `invalid` when the name is not a plain method name of up to 128 letters, digits or underscores), the error the page received, and the time. It covers methods Hronaut does not support, networks it cannot switch to, malformed or refused requests and rejected approvals, so an agent can tell why a dApp button did nothing. Reads forwarded to the node, such as `eth_call`, are left out because contracts revert them routinely. The parameters the page sent are never listed, and a wallet's own address in an error reads `this wallet (address hidden until account permission)` until the agent session has account permission. The result also lists the site's newest 20 `wallet_sendCalls` batches in that workspace, sent from any of its tabs, as `callBatches`. Each has the batch ID, the network ID, how many calls the batch holds, its `state` (`sending`, `stopped` when Hronaut stopped before the last call, or `sent` when every call went out), and each sent call's transaction hash with the status of the request that sent it, marked `replaced` when another transaction from the account took its nonce. When Hronaut could not send the next call at all, for example because the account could not pay for it, the batch also has the `error` that stopped it; a rejected next call's request is listed with the page's other requests. A batch ID the page chose that is not a plain ID of up to 128 letters, digits, dots, colons, hyphens or underscores reads `not shown`. A batch whose first call fails is forgotten and not listed, as `wallet_getCallsStatus` forgets it too. A wallet's own address in a batch ID or error reads `this wallet (address hidden until account permission)` until the agent session has account permission. When an EVM transaction's simulation reverted, its details include `simulationRevert` with the same reason the dialog shows (`kind` `message`, `panic`, `custom-error` or `no-reason`), and `wallet_prepare_transaction` returns it as `simulation.revert`; a wallet's own address in a revert message reads `this wallet (address hidden until account permission)` until the agent session has account permission. It is read-only and cannot approve, reject or cancel the page's requests. `wallet_balance` returns the native balance, or with `token` one fungible token balance: an ERC-20 contract on EVM, an SPL mint on Solana, or a TRC-20 contract on TRON. The token result includes the raw integer amount, decimals and, when the contract returns a plain one, the symbol, so an agent can check that a dApp swap or mint credited the wallet. With `token` and `spender` on EVM or TRON, the token result also includes `allowance`: the spender address (checksummed on EVM), such as a DEX router, and how much of the token it may still move from the wallet, formatted and raw, marked `unlimited` when it is 2^160 − 1 or more, or exactly 2^96 − 1 or 2^128 − 1, the maximum a token that stores allowances in fewer bits, such as UNI or COMP in 96 bits, reports for an unlimited approval; Hronaut's approval warnings use the same rule. An agent can use it to check that a dApp's approval step requested the expected amount, or that a revoke set it back to zero. Hronaut does not read SPL token delegates, so `spender` is refused on Solana. It needs the same account permission as the native balance. The optional `agentName` is display-only and appears in trusted approvals. An agent cannot approve a request. There is no decrypt, export, raw-vault, private-key, mnemonic, generic RPC-forwarding, or approval tool.

## RPC configuration and testing

Choose a curated network in **Settings → Wallets** to start with its public RPC, or choose **Custom network** to enter every identity field yourself. EVM presets cover common mainnets and testnets plus local Anvil. Solana includes Mainnet, Devnet, Testnet, and a local validator. TRON includes Mainnet, Shasta, Nile, and a local/private FullNode. The form uses chain-specific identity and endpoint labels so an EVM chain ID is not confused with a Solana cluster or TRON network key.

Preset identity fields remain fixed, while the RPC endpoint stays editable. Selecting another preset restores that preset's published default. Existing wallets retain the exact network and endpoint copied at creation; later application upgrades do not silently rewrite them.

Hronaut does not ship third-party API keys. Built-in public endpoints are convenience defaults, may be rate-limited, and are not a production-availability promise. TronGrid production traffic may require a `TRON-PRO-API-KEY`; Hronaut deliberately does not put that secret in a wallet URL, so use a dedicated or self-hosted custom endpoint instead. Treat every RPC operator as part of the transaction-information trust boundary and prefer your own or explicitly trusted endpoints.

Use local/test networks and valueless accounts for development. Hronaut's fast and authoritative suites run inside Docker with deterministic RPC fixtures for EVM, Solana, and Tron adapter behavior; they never submit mainnet transactions or use real funds. The fixtures cover normalized transaction preparation, simulation, fee estimation, signing, broadcasting, confirmation, malformed responses, chain/account mismatches, replay, and concurrent request isolation without depending on a mutable public testnet. Real-node smoke testing should use a disposable Anvil, `solana-test-validator`, or private Tron node outside the default suite when those large runtimes are available locally.

For observation-only QA without any signing material, use the [watch-only public-address wallet QA recipe](WATCH_ONLY_WALLET_QA.md). It uses a synthetic address and direct local-node state to verify scoped account access, balance reads, signing rejection, and the absence of automatic signing authority. For a separate copyable signing smoke test with a fixture dApp, approval rejection, provider events, delayed and reverted receipts, independent chain readback, and cleanup, use the [local EVM wallet QA quickstart](WALLET_QA_QUICKSTART.md). The signing quickstart requires Hronaut 2.4.21 or newer and never uses real recovery material or funds. When a QA plan also names browser extensions, WalletConnect/Reown, proprietary wallet SDKs, or mobile wallets, use the [external-wallet and mobile dApp QA boundary](EXTERNAL_WALLET_QA_BOUNDARIES.md) to keep Hronaut-local evidence separate from the provider-specific suite.

## Revocation and incident response

In **Settings → Wallets**, limit a wallet to selected workspaces, revoke each account permission, remove bounded policies, cancel pending requests, lock decrypted signing keys out of memory, or remove the wallet. Locking pauses managed signing but does not close tabs or disable ordinary browsing and watch-only wallets; passphrase vaults require their passphrase to unlock, while OS-protected vaults unlock through the operating-system secure store. Narrowing an **Any workspace** wallet revokes permissions, removes policies, and cancels pending requests in every workspace that loses access. Detaching, permission revocation, wallet removal, navigation, renderer destruction, tab closure, and workspace removal cancel matching pending requests immediately. Hronaut also revalidates the current workspace scope and account permission at the signing boundary. If recovery material may be compromised, move funds with a separately trusted wallet and retire the account; local revocation cannot invalidate a blockchain key already copied elsewhere.
