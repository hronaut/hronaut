# Hronaut

Hronaut is a visible, multi-tab Electron browser that exposes its live tabs to AI clients through MCP. It is deliberately not headless and is not tied to the lifetime of an AI session.

Hronaut is source-available under the [Subscription and Trial License](LICENSE). All users need a paid subscription after one 10-day trial from the first agent tool call: $4/month or $24/year per named user (50% off $48), with three devices per seat. Earlier releases retain their original terms.

For supported platforms, connection prerequisites, workspace recovery, client
replacement, support routes, and the product's identity boundary, use the
canonical [Support, recovery, and exit path](docs/SUPPORT_RECOVERY.md).

Project home: https://github.com/hronaut/hronaut

## What it keeps

- Cookies, local storage, IndexedDB, service workers, cache, and login sessions use Electron's persistent `persist:hronaut` partition.
- Open tabs and the active tab are restored from `tabs.json` in Electron's user-data directory.
- A two-tab split view, its side-by-side or stacked layout, pane order, and proportion are restored from the same file.
- Per-tab and all-tab human-interaction locks are restored from `tabs.json` as well.
- Appearance, search-engine, and other application settings are restored from `settings.json` in the same profile.
- Allowed and blocked website permissions are restored from `site-permissions.json` in the same profile.
- Window position, size, monitor, maximized state, and fullscreen state are restored. If that monitor is disconnected, the window is centered on the current primary display.
- Closing the window hides it by default. The Electron process and MCP endpoint keep running; click the tray icon to open its menu and choose **Show Hronaut** or **Quit**. Disable **Hide in tray when closing** in Settings to make the window close button quit Hronaut instead.
- **Launch Hronaut when you sign in** registers a per-user startup item on Windows, macOS, and Linux. Enable **Launch minimized** to keep only the tray icon visible for automatic sign-in launches; ordinary manual launches still open the browser window.
- A second launch focuses the existing instance instead of starting a competing browser profile.

## Same-origin iframe observations

`browser_snapshot action=capture frameSelector="#preview"` reads bounded headings, authored control labels/states, sanitized links and text
from one directly embedded same-origin HTTP(S) iframe without changing context
or parent references. Unsupported history fails closed. See [the complete
provenance, privacy, omissions and timeout contract](docs/frame-observation.md).

## Explicit React topology inspection

`browser_react` and **React inspection** in a tab's context menu provide explicit,
per-tab opt-in for bounded ReactDOM 19.2.4 production topology. Enabling requires
a subsequent normal reload/navigation and never reloads automatically. Activation
is not persisted across restart. Disabled hook residue remains until reload.
Names/version claims are untrusted; unsupported or partial results do not establish
absence. See [the complete contract, limits, authority lifecycle and provenance](docs/react-inspection.md).

Settings opens as a reusable application tab beside Home. Use its section navigation to switch categories;
switch to Home or a website without closing it, then return to the same section.
The Close buttons or Ctrl/Cmd+W close Settings and return to the previous browser view;
Escape leaves the tab open. Navigation and
content scroll independently, keeping the footer actions available in small windows.

Open **Settings** from the gear button in the top strip. Hronaut includes ten appearance choices:

- **Light** for a bright, neutral browser shell.
- **Dark** for a low-glare browser shell.
- **Midnight** for a deep blue-black browser shell.
- **Sepia** for a warm paper-toned browser shell.
- **Cyberpunk** for a neon cyan and magenta browser shell.
- **Cyberpunk Turbo** for clear reading text, cyan highlights, magenta controls and yellow tab indicators, with a matching Home page.
- **Matrix** for a green terminal-inspired browser shell.
- **Machine** for an industrial red and graphite browser shell.
- **Galactic** for a space-inspired violet and blue browser shell.

The selected theme is applied immediately and survives application restarts. System mode keeps Hronaut's renderer, native menus, and window background aligned with Electron's current operating-system theme. A fixed theme changes Hronaut's controls and native color preference without injecting styles into websites.

### The page in the window

The website sits in the window as a card with 12 px rounded corners, a hairline edge and a soft shadow. A 10 px margin of the shell's surface separates it from the window's right and bottom edges, from a docked or side panel, and, with tabs above the page, from the left edge; beside the tab rail and under the toolbar, their own padding gives it room. With the tab rail, the rail, the toolbar, the bars under it (such as Find and Zoom) and that margin share the rail's color, and the window controls on Windows and Linux match it. When the window has room for both, a docked panel at its largest still leaves the page and its margins at least 220 px high or 360 px wide. In a shorter window, a panel docked above or below the page may take up to 240 px or two thirds of the height below the toolbar, whichever is less, so the page and its margins keep at least a third. The page's viewport is the inside of the card, so measure it rather than deriving it from the window size. The corners scale with the interface scale, and Home, both panes of split view, an emulated viewport and the picture of the page under a dialog use them too.

With the tab rail, that shared surface takes a soft wash of the color of the workspace whose page is in view: strongest in the window's top-left corner, at about 13 percent of the workspace color (10 percent in Sepia), and fading out before the middle of the window, so the window controls and the page keep their usual colors. Switching to a page in another workspace crossfades the wash over 600 ms. Home, Settings, a page outside any workspace, the tab strip above the page and a panel in its own window stay neutral. Workspace cards in the rail keep their own opaque tint on top of the wash, and muted text keeps 4.5:1 contrast on the wash in every theme and workspace color; over a window material, the rail's veil keeps it there (see below).

Behind the open tab rail, the main window shows the system's material in the Light and Dark themes (including System when it resolves to either): macOS vibrancy (the sidebar material) and, from Windows 11 22H2 (build 22621), Mica. Main decides it from the platform, the OS build, the window's title bar, the resolved theme, the tab position, and the system's reduced-transparency, increased-contrast and high-contrast settings, sets the window's background clear while it shows, and tells the shell through its renderer settings state (`windowMaterial`), which marks the root element with `data-window-material`. The rail then lays one veil of its surface and the workspace wash over the material, from the top of the window to the bottom: 78 percent in Light and 58 percent in Dark, which keeps muted rail text at 4.5:1 over a light material as dark as #a0a0a0 and a dark material as light as #707070; workspace cards stay opaque, since a card's sticky header hides the tabs scrolling under it, and the rail's command row keeps a light veil of the toolbar color. Everything right of the rail (toolbar, bars and the space around the page) keeps the solid surface, which a fixed layer beside the rail paints; the Find, Zoom and page problem bars start beside the rail, like the toolbar, never under it. A rail opened over the page in a narrow window, the other themes, tabs above the page, a panel in its own window, Linux, older Windows, Windows with **Use system title bar** (Windows draws Mica under the page only with Hronaut's own title bar; that setting applies at the next start), and the system's Reduce transparency, transparency effects off or a high-contrast mode keep the solid surface. A change of theme, tab position or system setting applies at once when the system reports it.

### Dialogs over the page

Websites are native views drawn above Hronaut's own window, so Hronaut hides them while one of its dialogs is open, such as Commands, Search tabs, a workspace editor, Settings or a wallet approval. Before hiding them, Hronaut takes a still picture of each page on screen and shows it under the dialog, then hides the pages once that picture is on screen, so the page area never goes blank. Keyboard focus moves to the dialog at once, and clicks or keys never reach the page while a dialog is open. The picture stays in the shell window only, is never saved and is dropped when the dialog closes; if the window is resized or the tab changes while the dialog is open, the picture is withdrawn rather than shown in the wrong place. When the picture is not ready within 250 ms, the pages are hidden anyway.

### Interface language

Choose **System default**, English, Ukrainian, Russian, German, French, Spanish, or Polish in **Settings → Appearance**. The preference is stored in Hronaut's profile and applies immediately to the main window, detached panels, Hronaut Home, and native menus. System mode keeps the `system` preference and resolves Electron's operating-system locale centrally; unsupported system languages use English. Electron does not provide a reliable cross-platform live notification when the operating-system language changes, so an OS-language change is picked up on the next Hronaut launch. Choosing an explicit language, or switching back to System default, applies immediately without restarting.

**Interface size** scales Hronaut's tabs, toolbar, Settings, and diagnostic panels independently from website page zoom. New profiles use Compact 100%; choose Comfortable 110% or Large 125% at any time. Detached Hronaut panels follow the same setting, while every website retains its own zoom and viewport. The same dialog includes separate **Search engine**, **Downloads**, **Performance**, **MCP security**, **Workspaces & data**, **Site permissions**, **Passwords**, and **Updates** sections.

## Choose the default search engine

Open **Settings → Search engine** to choose Google, DuckDuckGo, Bing, Brave Search, or Startpage. Plain text submitted from the address bar and `browser_navigate` uses the selected provider immediately; recognizable addresses and explicit URL schemes continue to navigate directly. Scheme-less public addresses default to HTTPS, while `localhost`, `*.localhost`, `127.0.0.0/8`, and `[::1]` default to HTTP so local development servers work without requiring an explicit scheme. An explicitly entered scheme is always preserved. The choice is stored in the local Hronaut profile. Local tab, bookmark, and history suggestions remain on-device and do not send keystrokes to any provider.

## Clear browsing data safely

Open **Settings → Workspaces & data** to review active and archived workspaces, manage one workspace, or copy selected cookies and local storage between two workspaces. Moving data requires both workspaces archived. The **Global history** section clears application-wide browsing history for one origin or all origins. It preserves bookmarks, saved passwords, permissions, downloads, settings, open tabs, and workspace website data.

Under **Visited websites**, **Search websites** matches every whitespace-separated word across one site's hostname, full origin and retained title, in any order. Matching is literal and case-insensitive. Filtering only changes the visible list: a row's clear action still targets its exact origin, while **Clear history…** still clears all history, including hidden sites.

The website inventory combines history, open tabs, bookmarks, saved accounts, and permission decisions. Website-scoped history clearing matches the exact origin.

For the current page, open **Site controls** at the left of the address. It shows cookies from that tab's isolated workspace, exact-origin history, and saved permission decisions. **Site storage** opens the inspector for that workspace. Use its website-data controls to clear cookies, local storage, IndexedDB, service workers, caches, or other site storage within that workspace.

Obsolete base-profile browser data, workspaces without isolated storage, and tab snapshots older than version 3 are deleted at startup. Supported isolated workspaces retain their identities and storage. Explicit workspace deletion clears website data immediately and records pending file cleanup in the workspace-state snapshot. On a later startup, before workspace sessions open, Hronaut removes only those recorded partition directories whose ownership and paths can be verified. Active, archived, ambiguously referenced, recovery-blocked, and unsafe linked profiles are preserved. Existing unreferenced directories are not swept. Removal does not guarantee secure erasure from disks, backups, or filesystem snapshots. No legacy profile migration or Default-workspace aliases are available.

## Portable workspace templates

Open **Create workspace → Portable workspace templates** to prepare an export or review a selected JSON template before import. File selection and preview create no profiles and open no pages.

An export starts with a generic name and no start pages. You can edit names and colors, enter HTTP(S) start pages, or choose a source workspace. Adding a source copies only its color into a new entry; including its name or individual page URLs requires an explicit selection. Review every entry, remove sensitive information, check the review box, and choose **Save workspace template**. Names and URLs can contain secrets even without URL credentials; this is a reviewed setup template, not an automatic redaction guarantee.

Templates contain only schema version, source platform, workspace names, colors, and start pages. They exclude cookies, local storage, passwords, tokens, workspace IDs and resume capabilities, site-access rules, remembered permissions, and machine-specific profile paths. Full profile migration and automatic cloud synchronization are not supported by this flow.

To import, choose **Open workspace template**, review its entries, remove unwanted entries, and rename any entries that collide with an active or archived workspace. Changes to the entries, or selecting a file again, require fresh review. **Import and open pages** creates fresh isolated profiles with direct agent access disabled and opens the listed pages without selecting their tabs. It never merges with an existing profile or copies a sign-in. Existing site-access rules and browser permissions are not imported; review the new workspaces' settings before enabling agent access.

Files use format `hronaut-workspace-template`, version `1`, and UTF-8 JSON, limited to 256 KiB, 20 workspaces, and 20 start pages per workspace. Unknown fields, unsupported versions, duplicate names, non-HTTP(S) start pages, and URL credentials are rejected. The same format works across Windows, macOS, and Linux.

If an import fails, Hronaut attempts to remove only profiles created by that import. If cleanup also fails, the panel lists the retained profiles and offers **Retry cleanup**. Removing a profile does not undo effects caused by loading a start page in an external service. Inspect any uncertain external outcome before repeating an operation. Pricing and trial terms remain in [License](README.md#license).

## Site permissions

Use **Search saved site permissions** to filter by part of an origin, a permission's internal name such as `geolocation`, or its translated label such as **Location**. Every whitespace-separated word must match that decision's origin or permission name/label, in any order; for example, `staging.example.test camera` finds camera permissions on that site. Search is literal and case-insensitive. The count distinguishes visible decisions from the full saved list; clearing the search restores hidden rows. Filtering does not change stored decisions, and resetting the section still clears all saved decisions, including hidden ones. Leaving this settings section or closing Settings clears the search.

When a website requests access such as location, notifications, clipboard, camera, or microphone, Hronaut asks before granting it and remembers the Allow or Deny decision for that exact website origin. Open **Settings → Site permissions** to change a saved decision, forget one so Hronaut asks again, or reset the section to clear all saved decisions. When a focused permission row disappears, keyboard focus moves to the next available matching control, then a previous row, or the section heading if none remain. Focus already moved elsewhere is preserved.

## Updates

Automatic update checks are enabled by default. Packaged builds check the public GitHub release feed shortly after startup unless you disable **Check for updates on startup**. Hronaut never downloads an update silently: an in-app notification shows the available version and release notes, then asks you to **Download update** and **Install and restart**.

Open **What's new** from **Settings → Updates** or **Help → About Hronaut** to browse the complete published release history without leaving Hronaut. GitHub Releases is the source of truth: Hronaut fetches stable releases in bounded pages, sanitizes their notes before rendering, opens note links through trusted external navigation, and temporarily caches pages so an already viewed history remains available during a short GitHub outage. Use **View all on GitHub** when you want the canonical public release pages directly.

On Linux, Hronaut waits for the old single-instance process to finish its bounded profile and MCP shutdown before launching the newly installed DEB, RPM, or AppImage. This prevents an immediate second update prompt from the still-running old binary during consecutive releases.

You can also check manually from Settings, the Hronaut application menu, or the tray menu. Update preferences are stored in the persistent profile. Development builds do not contact the release feed; set `HRONAUT_DISABLE_AUTO_UPDATE=1` to disable checks for a packaged launch as well.

## Hronaut Home

The dedicated **Home** application button sits outside the browser tab list and opens **Hronaut Home**, an internal dashboard with its own application partition, separate from workspace site data. It is app navigation, not a reserved browser tab. New profiles use the left workspace rail; existing saved tab-layout choices are respected. While Home is active, Hronaut keeps the top strip for switching to open websites but removes the website-only Back, Forward, address, and page-action row, giving the dashboard the reclaimed space. Application-wide Search tabs, Downloads, History, Hronaut lock, MCP, and Settings controls remain in the same top-strip positions on Home and websites; only page-specific navigation and tools appear beside the address. Hronaut keeps Home as a singleton: clicking the button focuses the existing Home page or recreates it if needed. Regular new tabs remain blank. Home separates Workspaces, Connect an agent, Overview, and Tool library into keyboard-navigable views. Workspaces is the initial view after upgrading, and clicking Home returns to it. Other selected views survive a page refresh. Live status refreshes never switch the selected view. Home provides:

- A searchable workspace hub with Open and Archived views, creation, settings, templates, archive undo, and restoration.

- Copy-ready setup instructions for Codex, Claude Code, Cursor, VS Code / GitHub Copilot, OpenCode, Gemini CLI, Goose, Cline, Zoo Code, Kiro, Kilo Code, JetBrains Junie, Devin Local, Zed, Mistral Vibe, Warp, Windsurf, Grok Build, Qwen Code, and generic Streamable HTTP clients, including verification commands where the client provides one.
- A live list of active requests and recently seen MCP clients.
- A copy-safe MCP readiness diagnostic that keeps application health, the local endpoint, protocol initialization, advertised tools, active-client tool visibility, and a benign read-only probe as separate checks. Pasted client tool output is parsed locally for registered tool names and is never retained.
- The current browser tool catalog, grouped by session, navigation, interaction, and inspection.
- A privacy-safe activity dashboard with recent tab actions, duration, bounded outcome and reason categories, dispatch/effect certainty, and per-launch and per-tool totals. Legacy `finished`/`failed` fields remain available to dashboard consumers. It records no URLs, selectors, typed text, screenshots, or page content.
- The local MCP endpoint and authentication guidance.

An unused profile also shows an inline connection journey above its workspace
hub. Choose a client, copy the local profile's configuration, connect, and ask
the client for the read-only first page check. Listener readiness, initialized
clients, and verified read-only probe evidence are separate. The journey retires
after a verified probe; existing workspace profiles keep workspace-first access.
The MCP status control opens the same compact evidence summary. **Copy URL** is
an explicit action inside it, and Escape closes it and restores keyboard focus.

Regular websites, including `https://google.com`, can be opened from the address bar, a new-tab request with a URL, or `browser_navigate`.

The MCP tool set selected in **Settings → MCP security** applies to new connections. Each live connection keeps the names, schemas, annotations, descriptions, and server instructions it received when it connected. Reconnect an MCP client to adopt an intentional catalog change; Hronaut never rewrites that model-facing metadata within an established transport session.

Right-click a website tab to create or edit its workspace, open another tab in that workspace, or archive its workspace. Fresh profiles start on Home without creating a Default workspace. Every website tab belongs to a workspace; creating the first website tab creates a normally named isolated workspace when none exists. Every tab and workspace has a UUIDv7 identity. Human-created workspace labels remain collision-checked, while isolated MCP clients may use the same task label without learning that another client already chose it. Renaming never changes the stable `workspaceId`. An MCP workspace ID identifies a target but does not grant access; live connections must have created it or resumed it with its private capability. Workspace membership is immutable, so tabs cannot move between workspaces.

Workspace authorization and write ownership are separate. Creating a workspace gives that exact MCP transport a five-minute, renewable, process-local `exclusive-write` lease; resume claims it when available and otherwise grants only shared inspection while reporting the existing lease as busy. Read-only tools remain shareable. A second authorized transport receives `BUSY` with `effects: "none"` before a conflicting mutation is dispatched; it receives no holder identity or foreign lease generation. `browser_workspaces` supports `ownership-status`, `claim-ownership`, and `release-ownership` for explicit inspection and handoff. Its normal `list`, `create`, and `resume` responses include a privacy-safe `writeLease` status.

Disconnect, explicit release, MCP pause, authentication rotation, server stop, or expiry revokes the lease. A command admitted under an older generation must still hold that exact generation immediately before dispatch; it otherwise returns `LEASE_LOST` and cannot silently regain authority after another transport claims the workspace. After pause or takeover, inspect the visible workspace, claim ownership again, and revalidate the tab, origin, account, navigation generation, and intended target. A lease serializes the whole workspace, including separate tabs and shared-origin state; it deliberately does not promise concurrent writes within one workspace or coordination between separate Hronaut processes.

**Hide from left sidebar** hides a workspace and its tabs from the left navigation while keeping the workspace active and accessible from Home. It does not change agent access. **Protect from deletion** blocks permanent removal by people and agents at the browser lifecycle boundary; archiving and restoring preserve both preferences. Only a person can change deletion protection. Archived cards expose this preference under Workspace options.

Browser mute is independent of the number of open tabs. It persists across restart and applies to newly opened and restored tabs. Use a tab’s **Mute / Unmute** control to change that tab while browser mute remains on. These exceptions are temporary: turning browser mute on again clears them, and turning it off restores each tab’s saved mute preference.

The workspace editor offers **Allow direct agent access**. Disabling it blocks direct agent actions and resume access to that original workspace. The normal agent workspace list still shows a metadata-only entry marked `forkOnly`, with a `forkWith` action containing the source ID, and the fork-source catalog also lists it. Agents can copy its cookies and local storage into an independent fork. This setting does not prevent cloning. Forks inherit site restrictions and start with one blank tab; they do not copy open tabs.

**Transfer browser data** lets people select source and destination workspaces. Copy merges cookies and local storage, replacing matching destination entries while retaining unrelated entries. Move verifies the destination before removing the transferred source entries. Both workspaces must be archived for Move so their pages cannot change the data during cleanup. Profiles with background service-worker data cannot be moved through this operation; use Copy instead. These transfers do not include IndexedDB, history, passwords, cache, or downloaded files. Incomplete cleanup is reported explicitly and the verified destination copy is retained.

## Save resources in large workspaces

Memory Saver is enabled by default under **Settings → Performance**. After one hour of inactivity, Hronaut unloads eligible background website tabs and marks each sleeping tab with a moon. Choose 5 minutes through 4 hours, sleep every eligible tab immediately, or disable the feature. Selecting a sleeping tab or targeting it with an MCP command reloads it and restores its navigation history before the work begins.

Visible split-view panes, pinned or loading tabs, audio playback, active downloads, open dialogs, pages waiting on a wallet approval or still sending a wallet call batch, Developer Tools, current MCP commands, and pages with edited form or rich-text content stay awake. Right-click an inactive tab to sleep or wake it directly. These protections follow the same practical model as mainstream browser memory savers while preserving Hronaut's persistent multi-agent workspace.

## Pause agents instantly

Use the pause button beside **MCP ready** to reject new MCP commands immediately while keeping Hronaut, its tabs, logins, and browser profile open. Resume from the same control when you are ready. This runtime safety switch is intentionally separate from MCP authentication and resets when Hronaut restarts.

While paused, the status pill shows how many tool callbacks are still settling, including work whose HTTP client disconnected. When the count reaches zero, the callbacks have finished; this does not establish whether every browser side effect succeeded or whether later page events have stopped. Pause does not undo dispatched actions. Inspect the visible page and obtain a fresh snapshot before continuing, and do not automatically repeat a possible write whose outcome is unknown.

Human approval is not a substitute for the target service's authorization and business-rule checks. See [browser approval and downstream authorization](AUTOMATION_BOUNDARIES.md#browser-approval-and-downstream-authorization) for a synthetic example, receipt requirements, and negative tests.

Use the separate **Pause agents / Resume agents** page control to pause one tab or resume only that tab while global pause remains on. Turning global pause on again clears these temporary exceptions. Turning it off restores saved per-tab pause preferences. Other tabs remain blocked; a single-tab exception does not authorize workspace-wide operations such as creating tabs or changing shared site data. Existing workspace ownership and capability restrictions still apply. Temporary pauses during protected operations cannot be overridden. **Live / Frozen** continues to control page execution independently.

With no tab exceptions, paused MCP requests receive HTTP 503 with a `handoff` snapshot: `state` is `PAUSED_WITH_ACTIVE_COMMANDS` or `PAUSED`, and `activeCommands` counts tool callbacks rather than open HTTP connections. `priorActionOutcome` remains `NOT_ESTABLISHED` in both states. This process-wide count contains no command contents or workspace identifiers and does not authorize retries.

## Saved passwords

When you manually sign in to a website, Hronaut can ask whether to save or update that login. It observes native form submissions and common scripted login buttons, including buttons inside forms. Passwords are encrypted asynchronously by the operating system through macOS Keychain, Windows DPAPI, or a supported Linux secret store. Hronaut refuses to enable password saving when Linux would fall back to Electron's unprotected `basic_text` backend.

Saved-account metadata can be reviewed or removed under **Settings → Passwords**. Hronaut never exposes stored passwords through its preload API, Settings, Home dashboard, or MCP tools. Use the password button in the toolbar to fill an account for the active website. Hronaut pauses new MCP commands before decrypting and filling, waits for active requests to finish, and remains paused until you explicitly resume agents.

### Import browser sign-ins into one workspace

On Linux, choose **Import from browser…** from a workspace's context menu, or
open **Manage workspace → Browser data** and choose the destination. Archived
workspaces are available through Home's Browser data transfer controls; select
that workspace as the import destination. Choose a Chrome/Chromium or Firefox
profile, approve the native permission to read cookies, then select sites using
search, individual checkboxes, or Select all. Nothing is imported by the read
permission alone. Site selections remain selected when hidden by a filter.
The profile picker uses available browser display names, including Chromium account
and customized profile names, with directory suffixes to distinguish profiles.
When name metadata is missing or unreadable, it falls back to the profile directory.
Changing the label does not change the selected source or import destination.

Choose **Import into “Workspace name”**. Active and archived workspaces are
supported, including workspaces with service workers. Open tabs stay open and
unsaved forms are retained; reload a site when ready to use its imported sign-in.
An archived workspace can be restored from the result screen. Workspaces can
also be archived when they have no tabs; their browser data remains available.
Imports are one-time local copies and
never change the source browser. Source profiles and import operations have no
MCP tools. Imported sign-ins can subsequently be used according to the existing
workspace and fork permissions. Agents remain paused until the human resumes them.

The importer copies supported cookies, preserving their scope and attributes.
It skips entire selected cookie domains that overlap existing destination
cookies or known site storage, or are outside the destination's site rules.
Existing cookies are rechecked before each site's import. Live pages and workers
can still change cookies while an import runs, so this is a best-effort additive
copy, not an atomic snapshot. Passwords, local storage, IndexedDB,
cache, and service-worker data are not imported. Partitioned cookies and Firefox
container records are excluded. Expired, invalid, unsupported, and unreadable
records are counted as skipped. Cookies present only in the source browser's
memory may not be available; a copied cookie does not guarantee a valid login.
Firefox persistent-cookie schemas 10–17 and Chromium cookie schemas 23–24 are
supported. Unknown schemas fail closed until validated.

Chrome/Chromium uses its existing Linux Secret Service key through
`/usr/bin/secret-tool` (`libsecret-tools`), with any OS keyring prompt occurring
after native read consent. Basic-storage v10 cookies are also supported. KWallet,
Windows, macOS, and Safari import are not supported in this version. Hronaut does
not change source-browser encryption settings or create keyring entries.

Reads use a bounded read-only SQLite transaction, including committed WAL data;
no plaintext export or temporary profile copy is created. Cookie values and
short-lived previews stay in the main process. Previews expire after five minutes
and are invalidated by cancellation, profile changes, shell navigation, or a
changed destination storage identity/policy. Commit verifies cookie attributes
and flushes the destination. A failed cookie does not discard other successful
imports. The importer never removes cookies to roll back a failure, preserving
changes made by live pages. The result reports imported, skipped, and failed
cookies; if verification or saving fails, review sign-ins before resuming agents.

To migrate accounts from an installed browser, export its passwords as CSV, then choose **Settings → Passwords → Choose browser CSV…**. Chrome, Edge, Firefox, and compatible password managers use or can produce the required `url`, `username`, and `password` columns. Hronaut opens the file through a native picker, parses at most 3,000 rows and 10 MB in the main process, shows counts before changing the vault, and imports only after explicit confirmation. Valid HTTP(S) accounts are re-encrypted atomically with Hronaut's operating-system-backed vault; later duplicate rows win, existing origin-and-username matches are updated, and invalid rows are reported as skipped. Password values and the selected file path never cross the preload boundary or reach MCP.

Browser CSV exports contain readable passwords. Delete the export after confirming the import. For password migration, Hronaut does not read or decrypt another browser's password database: those stores are protected by browser- and OS-specific credential systems, may require a primary password or biometric approval, and increasingly bind secrets to the source application. The browser's authenticated CSV export is the supported password-import boundary; cookie import has the separate human-consent flow above.

## Prevent accidental human interaction

Use **Lock input / Unlock input** beside the address bar to control the current tab, or the global lock icon in the tab strip to control every website tab. Both block human mouse, wheel, context-menu, and keyboard input inside websites. Trusted Hronaut controls remain usable, including the full-app unlock control and tab-close buttons, middle-click, context-menu actions, Delete, and `Ctrl/Cmd+W`. This lets you stop an unavailable page that an agent is repeatedly reloading without restoring page input. MCP inspection and interaction continue to work while human input is locked.

While the Hronaut-wide input lock is on, use the current tab's lock button to temporarily allow human page input in that one tab. Other tabs remain locked. Turning the Hronaut-wide lock off and on again clears every temporary unlock. This exception is not saved across restarts and is unavailable in read-only public observer workspaces.

An unblocked key-down that does not match the single expected agent keyboard event advances the tab's human-interaction generation, including while an agent operation is awaiting native input. MCP native-click guards then stop later presses with `OUTCOME_UNKNOWN`; already dispatched effects are not undone. Locked unmatched keys remain blocked. Matching uses event type, key, code, modifiers and repeat state; identical-shaped physical and CDP keyboard events remain indistinguishable, so this is not a general takeover guarantee. Concurrent mouse input still has a known gap: an unlocked mouse-down during the surrounding agent-input operation can reach the page without advancing that generation, allowing a later agent press. Use **Pause agents** for explicit takeover.

The page controls are separate buttons: **Lock input / Unlock input** controls human page input, **Pause agents / Resume agents** controls agent access, **Live / Frozen** controls page execution, and **Mute / Unmute** controls audio. Global input lock, agent pause, and mute remain in the tab strip.

If an existing native/debugger operation stays busy for two seconds, the control reports that locks were not changed and becomes available to retry after that operation finishes. The rejected request is not queued to unlock later.

A waiting spinner means a control change is queued or being applied. The affected button is temporarily disabled to prevent duplicate clicks; its accessible label includes **Waiting…**. Input-lock requests wait for an earlier lock change and any rollback to finish. If an input-lock request fails, Hronaut reports the error and makes the control available again; the spinner does not mean a failed request will be retried indefinitely.

## Debug a website with Chromium Developer Tools

Open **View → Developer Tools**, use **F12**, **Ctrl+Shift+I** on Linux or Windows, or **Cmd+Option+I** on macOS to open detached Chromium Developer Tools for the active website tab. The right-click **Inspect** action opens the same per-tab tools and selects the element under the pointer. Locking the tab or all of Hronaut closes its Developer Tools so the human-interaction lock remains effective.

Electron permits only one debugger connection to a website at a time. MCP actions that depend on the Chrome DevTools Protocol therefore ask you to close Developer Tools first; regular page actions and Hronaut's bounded console and network records remain available. Closing Developer Tools restores those debugger-backed MCP actions immediately.

Agents can use `browser_emulate` to reproduce failures under offline, Slow 3G, Slow 4G, or Fast 4G network conditions; ignore the HTTP cache; bypass service-worker fetch handlers; override the page's Data Saver preference; slow the CPU from 1–20×; pause document-timeline animations or play them at 10%, 25%, or normal speed; disable page JavaScript; switch screen or print media; emulate color scheme, forced colors, contrast, reduced motion, reduced transparency, or a vision deficiency; set a locale and IANA time zone; override the user agent; or apply a mobile/desktop viewport with DPR, touch, and orientation. The same tool can supply test coordinates and extra request headers for location-aware or server-variant debugging, and can enable Chromium paint flashing, layout-shift regions, layer borders, frame rendering stats, or scrolling-performance highlights through `renderingDebug`. Animation playback controls cover CSS transitions, CSS Animations, Web Animations, and view transitions on the document timeline; JavaScript `requestAnimationFrame` loops remain unaffected. A website still needs its normal Hronaut geolocation permission. Header values are applied inside the website tab but only their names appear in tab state or the trusted shell. Overrides apply only to the chosen tab, survive navigation and reload, and can be inspected or reset through the same tool. `cacheDisabled: true` ignores memory and disk cache for future requests without deleting cached data. `bypassServiceWorker: true` sends future requests to the network without unregistering the worker; combining it with Offline deliberately prevents the worker from supplying offline responses. Data Saver changes `navigator.connection.saveData` without throttling bandwidth; choose `enabled`, `disabled`, or `auto` to restore the system value. Reload after changing locale so `navigator.language`, `navigator.languages`, and subsequent request negotiation all reflect it. Reload after disabling JavaScript to inspect the page’s real HTML/CSS fallback; use `browser_emulate` with `javaScriptDisabled: false` or `reset: true` to restore execution even when page evaluation is unavailable. Hronaut marks the tab with a speed icon and shows the active condition beside its address; click that pill to restore normal conditions immediately.

Open **Page tools → Environment → Rendering diagnostics** to use the same overlays without opening Developer Tools. Paint flashing marks every repaint in green; layout-shift regions briefly identify unstable content; layer borders expose compositor structure; frame rendering stats show frame timing, dropped frames, and GPU state; scrolling-performance highlights identify regions that may delay scrolling. These are live diagnostic hints rather than performance measurements or root-cause verdicts. Paint and layout-shift overlays can flash rapidly and should be disabled immediately if flashing content could affect you. Developer Tools owns Chromium's only debugging connection while open; Hronaut restores still-active overlays after Developer Tools closes.

## Search and restore tabs

Use the fixed tab-search button, **Search tabs** at the bottom of the workspace switcher, or press **Ctrl/Cmd+Shift+A** from Hronaut or any active website. Search matches labels, titles and addresses across both open tabs and the bounded recently closed stack. Separate words with whitespace to require every term, in any order and without case sensitivity; for example, `report example.com` combines a title word with a hostname. Open tabs also match their workspace name. Archived workspaces match their name alone or their name together with one contained tab’s label/title/address; words from unrelated contained tabs are not combined. Terms are literal text, not regular expressions. Use Up/Down and Enter to switch to an open page or restore any matching closed page without leaving the keyboard; close open entries with each card's **×**, and pin, unpin or open a full-page preview from its **⋯** menu. **Result type** narrows Search tabs to **All results**, **Open tabs**, **Recently closed**, or **Archived workspaces**, together with the text query. Changing the type selects its first match; Enter activates that result using the existing open/restore action. Reopening Search tabs resets the type to All and clears the query. Each open card shows a thumbnail of the page as it was last seen. Hronaut takes it while the tab is in view: when the page finishes painting, and again about a second after your latest click, key or scroll there. A viewport screenshot of a background tab, by an agent (`browser_screenshot`) or by you, also updates its thumbnail once the page has finished loading. A tab that goes to sleep keeps the thumbnail it had, dimmed under a **Sleeping** badge, until it wakes. Hronaut never wakes or renders a tab just to picture it, so a tab that has not been in view since launch, or whose page changed while it was in the background, says **No preview yet** with its site icon and address. Thumbnails stay in memory for the current launch and are never saved, sent to agents or reported. Closed-only and archive-only views do not request new thumbnails; already-running capture settles normally and its late response is ignored. Recently closed entries retain only label, title, address, pin state, and close time for the current launch. Home remains application navigation and is intentionally excluded from website-tab results. This keeps active pages discoverable when the 50-tab strip overflows and makes recovery visible without requiring a shortcut.

Choose **Edit label** on an open tab in Search tabs to give it an independent task name, such as “Customer checkout”. Save trims surrounding whitespace and normalizes Unicode to NFC, with a limit of 100 Unicode code points (and 1,024 UTF-16 code units before normalization). Control characters, invalid surrogate code units and bidirectional embedding/override/isolate controls are rejected. **Clear label**, or saving an empty/whitespace-only label, restores the page title as the primary tab name. Cancel dismisses the editor; it does not undo an already submitted save. Home cannot be labeled. Duplicate labels are allowed and never identify a tab for dispatch or verify an account, origin or login state.

The strip shows the label, while its tooltip and Search tabs retain the real page title and address. Navigation, reload and website title changes do not modify a label. Duplication copies the committed label into an independent tab; editing either copy does not change the other. Labels survive active-session restart and workspace archive/restore. Closed-tab recovery preserves them only within the current launch, like other closed-tab metadata. Malformed optional labels in a profile are ignored without discarding valid tabs.

A label edit stages a snapshot on the tab-state save queue and updates visible state after file replacement. A rejected pre-replacement write leaves the previous label intact. If replacement succeeds but the directory flush fails, the new label remains visible with a durability warning; retry Save before relying on a restart. An older completion never replaces a newer label. Close, duplicate, archive and restore wait for admitted label edits; new edits are rejected while these lifecycle operations or shutdown are in progress. Other queued runtime saves take their snapshot when dequeued, preserving the committed label and current workspace state.

`browser_new_tab` accepts an optional `label` using the same validation. Omitting it preserves the existing creation response and asynchronous session saving. Supplying it, including an empty label, waits for a staged label save and adds `createdTabId`, `labelPersistence` and `retrySafe: false` to the authorized workspace response. The UUID belongs to that creation operation; duplicate labels never identify a tab for dispatch. No MCP label editing tool is added.

`labelPersistence: "saved"` acknowledges that creation label’s file replacement and supported flush, not that a later human edit cannot replace it. The returned tab state is refreshed at publication and may already contain a newer human label. `"durability-unconfirmed"` means replacement committed but the durability acknowledgment failed; the label remains visible with a warning. `"not-saved"` returns the error status `LABEL_NOT_SAVED`: the tab was created, but the label transaction failed before replacement. This does not acknowledge the tab’s own durability or roll back its creation/navigation. Inspect current state and edit the existing tab through Search tabs; never repeat creation automatically to retry a label.

Labeled creation retains the workspace writer and its place in the bounded label-save queue until actual disk settlement, including cancellation. Close, archive and shutdown wait for the admitted save. Authority is checked before creation, at queued snapshot/commit and after audit/capability settlement before publication. An asynchronous filesystem rename is not atomic with revocation: a submitted rename can commit after cancellation or access loss. Late authority or audit failure therefore withholds the workspace state, label and created ID and reports `OUTCOME_UNKNOWN` with possible effects, rather than implying rollback. A failure before creation dispatch preserves its admission error. Filesystem settlement has no additional timeout; cancellation cannot interrupt an already submitted disk operation.

Full workspace-scoped tab state can expose the separate authored `label` field; it is private task metadata, not verified document evidence. Compact MCP discovery remains unchanged: labels are absent from its rows, search matching, counts and verified-title fallback. Portable workspace templates do not export labels.


Choose **Full-page preview** from an awake tab's **⋯** menu to inspect its complete document without switching to it. From the search field, **Alt+Enter** previews the selected open result. **Fit page** shows the entire capture; **Fit width** enlarges it for scrolling. **Refresh preview** takes a new snapshot, **Open tab** returns to the live page, and **Escape** returns from the preview to the tab list. Navigation or closing the source tab discards its old preview. Sleeping tabs remain asleep until opened.

Full-page previews preserve the live page's viewport and scroll position. They are bounded JPEG snapshots (at most 1,440 pixels wide, 12,000 pixels high, 12 megapixels, and 4 MiB), so very large pages are reduced in size. They capture currently rendered content; they do not scroll a site to trigger lazy loading. Close the tab's Developer Tools before requesting a preview.

Deleting an archived workspace and clearing sign-ins still ask first, because they cannot be undone.

Human bookmark search matches every whitespace-separated word, case-insensitively, across each saved title and address. Words can appear in either field and in any order; punctuation is literal. The human Bookmarks panel can organize links into up to 50 single-level collections (names up to 80 characters). Choose All bookmarks, Unfiled, or a collection; search applies within that selection. Each bookmark belongs to at most one collection. New bookmarks start in Unfiled; adding an already saved URL preserves its collection, as do title and destination edits. Removing a collection moves its bookmarks to Unfiled without deleting links. This organization is profile-wide and does not change workspace permissions or the flat `browser_bookmarks` contract.

Storage remains backward-readable `version: 1`: the existing bookmark array is unchanged and collection membership is optional additional metadata in the same atomic file. Existing v1 files load as Unfiled. Hronaut 2.18 can read all links from new files; editing or repairing the file with 2.18 can discard collection organization, but does not discard the bookmarks. Reopening such a file in a newer version leaves its links in Unfiled. Invalid or dangling collection assignments never remove valid bookmarks.

## Review local browsing history

Human history search matches every whitespace-separated word, case-insensitively, across each saved title and address. Words may appear in either field and in any order; punctuation is literal. Search combines with the date range, exact-origin filter and sort order without changing stored visits or the MCP search contract.

Choose **Most visited** under **Sort history** to order the displayed records by their saved visit counts; equal counts retain the existing recent-first order. **Recently visited** remains the default. Sorting composes with search, date and exact-origin filters, and only changes the displayed list. Date filters apply to the last visit timestamp; counts remain the totals accumulated for each retained record, not counts within the selected date range. The choice survives panel close/reopen for the current application session and resets on restart. Live visit updates retain focus on a moved row, including a pending copy, background-open or bookmark action.

Press **Ctrl+H** on Linux/Windows, **Cmd+Y** on macOS, or use the history button to search recently visited pages, reopen one, remove an individual entry, or clear the collection. Hronaut stores one recency entry per normalized HTTP or HTTPS address, counts repeat visits, removes URL credentials and fragments, and automatically drops visits older than 90 days. Home, `about:`, `data:`, and other internal pages are never recorded, and restoring a saved tab does not count as a new visit. History stays in the local profile with atomic writes; clearing it does not remove cookies, passwords, bookmarks, or downloaded files. Agents can use `browser_visit_history` to list, search, reopen, remove, or clear the same collection.

## Identify and mute tabs

Website tabs display their real favicon after Hronaut safely normalizes it into a local 32px PNG; remote favicon URLs are never loaded inside the trusted shell. When a tab emits audio, a speaker appears beside its title. Click it to mute or unmute only that tab, press **M** while the tab is focused, or use the tab context menu. The speaker button in the global topbar controls browser mute for existing and future website tabs. It shows **Unmute all tabs** while browser mute is enabled, including when a tab has been temporarily unmuted. Turning browser mute off restores each tab’s saved mute preference. These controls do not change site-wide sound permissions. Agents can use `browser_audio` for a specific tab, and `browser_tabs` reports each tab's audible and muted state.

## Recover a failed page

When a website cannot be reached, its renderer crashes, or it stops responding, Hronaut shows a compact diagnostic row beneath the address bar instead of leaving an unexplained blank tab. **Try again** retries the exact failed address or reloads a crashed page in a fresh renderer process. The row expands the shell so it never covers website content, disappears after recovery, and includes the underlying Chromium error or process-exit reason when available. Agents receive the same structured `pageProblem` details through `browser_tabs` and can retry with `browser_history` using `reload` or `reload-ignoring-cache`.

## Change the MCP port

Open **Settings → MCP security**, enter an available port from 1024 through 65535, and choose **Apply port**. Hronaut starts the replacement listener before stopping the old one; if the requested port is unavailable, the current MCP endpoint keeps running and the saved setting is unchanged. Connected clients must be updated to the new endpoint after a successful move.

## Save a page as PDF

Use the **PDF** button beside the address bar to save the active page with backgrounds to the configured download directory. Hronaut derives a portable filename from the page title and adds a numeric suffix instead of overwriting an existing file. Agents can use `browser_pdf_save` and optionally choose a portable filename, A4/Letter/Legal paper, or landscape orientation.

MCP PDF exports recheck the request's cancellation and agent authority before rendering, at file-write boundaries, and immediately before publishing a successful result after audit and authorization work. Losing authority, including a pause followed by resume, prevents a pending export from reporting success and triggers best-effort cleanup of its owned file. Native rendering and in-progress filesystem operations are not interrupted immediately. Cleanup preserves a replacement file observed at the destination and cannot follow an export moved elsewhere; it is not an atomic filesystem rollback. Late cancellation or lost authority can reject the result after the file has committed; that completed file is retained. A lost response may likewise leave a completed PDF, so inspect the destination before retrying. Human PDF exports remain available while agents are paused.

## Track downloads

Website downloads appear in the toolbar with live byte progress and a recent-item count. Each HTTP(S) entry shows the origin (scheme, hostname, and effective port) of its retained download URL, omitting credentials, paths, query strings, and fragments. This is not necessarily the initiating page’s origin or a verification of the file’s publisher; unavailable and non-HTTP(S) origins are omitted. Open the download panel to pause or resume an active transfer, cancel it, reveal a completed file in its operating-system folder, or clear finished entries. **Copy saved path** copies a completed download’s retained destination path exactly as saved, without opening or changing the file. It is available only when the completed record has a saved path; it does not verify that the file still exists. Search matches every whitespace-separated word, case-insensitively, across each filename and displayed download origin. Words may appear in either field and in any order; punctuation is literal. URL credentials, paths, query strings, fragments, non-HTTP(S) URL content, and local saved paths are not searched. Combine the search with **All**, **Active**, **Finished**, **Completed**, **Cancelled**, or **Interrupted** to narrow the retained list; the count reports visible versus total entries. Active includes resumable interruptions until Electron marks them done; Finished includes completed, cancelled, and terminal interrupted entries. Completed and Cancelled match those exact states. Interrupted includes both resumable live interruptions and terminal interruptions; it does not imply that every matching transfer can resume. Filters only change the visible list and never retry or change a transfer. **Remove from list** removes only the selected finished record and keeps its file on disk; active, paused and live interrupted transfers cannot be removed. **Clear all finished** acts on the entire retained collection, including entries hidden by filters. Closing the panel resets its filters. The panel opens when a new download starts, floats over the page without resizing it, and keeps completed, cancelled, and interrupted items in memory for the current Hronaut launch. In **Settings → Downloads**, choose a persistent destination, open it in the operating-system file manager, or ask where to save every new website download. Automatic saves remain collision-safe and never overwrite an existing file. Active transfers keep the destination they started with. Pause and resume operate within the current session; resumable interruptions also offer Resume, while terminal failures do not. Servers without range support and matching validators may restart a resumed transfer from zero. The `browser_downloads` MCP tool accepts `list`, `pause`, `resume`, `cancel`, and `clear`; transfer controls require `downloadId` and retain workspace and observation-generation isolation. Returned entries expose `paused` and `canResume` for control availability.

## Run

Requirements: Node.js 22+ and a graphical Linux, macOS, or Windows session.

```bash
npm install
npm run dev
```

Development runs use a persistent `hronaut-dev` profile. This keeps development cookies, tabs, storage, and window state across restarts while avoiding the single-instance lock and profile of an installed Hronaut build. If an older window appears after upgrading the source, quit it from **Hronaut → Quit** once instead of only closing the window.

For the built application:

```bash
npm run build
npm start
```

To ask an already running development instance to flush its profile and quit cleanly:

```bash
node_modules/.bin/electron . --quit
```

The MCP endpoint is available while the app is running:

```text
http://127.0.0.1:47812/mcp
```

Health check:

```bash
curl http://127.0.0.1:47812/healthz
```

The authenticated health response includes the same bounded `readiness` report shown on Home. A healthy listener or a successful direct `initialize` / `tools/list` request proves only the Hronaut side of the connection. It does not prove that the active custom-agent host exposed those tools to the current task. Verify the tool inventory inside that active client, paste it into Home for a local comparison, then invoke `browser_status` or `browser_snapshot` once in a task-owned workspace. Hronaut reports unavailable host-side evidence as `client_visibility_unknown`; it never upgrades listener health into `client_tools_verified`. The report contains typed states, aggregate counts, bounded tool names, and timestamps, without client/session identifiers, configuration paths, tokens, raw errors, tool arguments, URLs, or page content.

Run reachability checks from the environment that actually launches the MCP client. A WSL distribution, container or Dev Container, local VM, Remote SSH session, and hosted runner can each have a different `127.0.0.1` from the Hronaut desktop process. The canonical [client topology guide](https://hronaut.dev/client-topology) separates `app_not_running`, `endpoint_unreachable_from_client_namespace`, `authentication_required`, `mcp_handshake_failed`, and `browser_not_ready`, then verifies the supported native same-host path with health, MCP discovery, and a harmless read of synthetic public content. For deliberate LAN access, enable **Allow connections from other computers** in **Settings → MCP security** and restart Hronaut. It binds all IPv4 interfaces with optional bearer authentication; use the desktop computer’s LAN IP and configured port in the remote client. Direct HTTP is unencrypted and intended only for trusted networks.

Authentication is off for a new profile so local agents can connect without token setup. If you enable **Require MCP authentication** in Settings, the exact token path is shown on Hronaut Home. On Linux, the packaged default is `~/.config/Hronaut/mcp-token`; development builds use `~/.config/hronaut-dev/mcp-token`. Hronaut creates one random token per profile and restricts the token file to the profile owner.

Trusted Settings can also create named capability credentials with a smaller tool preset and optional workspace, origin, exact-argument, expiry, and use limits. Exact argument constraints use `tool.argument.path=value` entries and can bind a credential to a tab, wallet, recipient, target, or payload field. Hronaut canonicalizes each value and persists only a domain-separated SHA-256 digest; the private value is used transiently during profile creation and authorization. Select an existing active capability as the parent to derive a delegated credential. Hronaut requires the child to be a strict subset of that parent, records the opaque parent profile, revision, and credential identifiers, and stores only credential and constraint digests. Every bounded child call consumes its own use budget and each bounded ancestor budget atomically. Parent rotation, editing, revocation, expiry, or exhaustion makes descendants inactive; reconnecting does not restore stale lineage. Derived profiles cannot be reparented through an edit, and their parent linkage remains visible in Settings. Creating a derived credential is a trusted local Settings action; browser pages and connected MCP clients cannot mint authority.

When a capability rejects a registered tool call, the MCP error gives a bounded human-readable reason and adds a machine-readable `policyDecision` object. The trace evaluates `grant`, `lineage`, `session`, `tool`, `action`, `operation-class`, `workspace`, `origin`, and `argument` in that fixed precedence order; it identifies the first denying rule and stable reason code, marks later rules as not evaluated, distinguishes missing from unrecognized operation classes, and distinguishes a direct credential from a delegated lineage. It includes the presented and active numeric session generations so stale context is diagnosable without exposing identity. The request summary includes only registered tool/action/category names and presence classifications, never configured origins, workspace IDs, profile names, credentials, selectors, prompts, constraint values or digests, or payloads. Permission, dispatch, and postcondition are separate fields: a pre-dispatch rejection has no effects, while a capability change detected after dispatch remains `OUTCOME_UNKNOWN` with possible effects and requires reconciliation. Every non-read tool has an explicit operation-class entry, and startup fails if a future tool is added without one instead of silently assigning a fallback category.

When action audit recording is active, each decision records whether the connection had full access or used a capability profile. Capability decisions include the bounded root-to-leaf profile IDs and revisions so a reviewer can verify delegation lineage. Decision and outcome observations also retain the privacy-safe exclusive-write lease mode, holder state, expiry, and only the current owner's opaque lease generation. A reviewer can therefore distinguish one continuous writer from a release, reconnect, expiry, or handoff without receiving a foreign generation or transport identity. Audit receipts never record bearer credentials, credential identifiers, profile scopes, cookies, tokens, page content, tool arguments, or MCP client/session identifiers.

## Connect an MCP client

Use a Streamable HTTP MCP configuration and start Hronaut before the client connects. A generic JSON configuration looks like:

```json
{
  "mcpServers": {
    "hronaut": {
      "url": "http://127.0.0.1:47812/mcp"
    }
  }
}
```

The exact schema depends on the MCP client; Hronaut Home includes separate current instructions for the major coding agents. Disconnecting or closing that client does not close Hronaut.

Tool availability must be checked in the active client or custom-agent context. A valid configuration file and a direct protocol probe can still coexist with a host policy that omits MCP tools. This verification remains entirely local: Hronaut defaults to loopback and requires an explicit Settings opt-in for LAN listeners and does not inspect or control another vendor's client.

Each GitHub release also publishes `hronaut-operator-manifest.json`. Its
`hronautVersion` matches that release, and its tool sets are generated from the
same runtime catalog Hronaut advertises to MCP clients. The manifest describes
local prerequisites, context invalidation, human takeover, bounded privacy
rules, and the `unsupported`, `blocked`, `unknown`,
`reconciliation_required`, and `verified` result states. Download it beside a
matching release with:

```bash
gh release download vVERSION --repo hronaut/hronaut --pattern hronaut-operator-manifest.json
```

A client flow reads the matching manifest, establishes the named workspace and
current browser context, makes a fresh bounded observation, requests or
dispatches the exact operation through the available MCP tool, and performs an
independent bounded read-back from the target system. Only that read-back can
support `verified`; a timeout or possible side effect remains `unknown` or
`reconciliation_required` before any retry. The manifest does not grant
authority, approve an operation, contain the live endpoint or credentials, or
replace current host policy.

Optional environment variables:

- `HRONAUT_MCP_PORT`: override the saved listen port for the current launch. Without the override, the port can be changed under **Settings → MCP security** and defaults to `47812` for new profiles.
- `HRONAUT_MCP_HOST`: loopback listen host, default `127.0.0.1`. Non-loopback values are rejected.
- `HRONAUT_MCP_TOKEN`: override the generated per-profile token with at least 32 URL-safe characters. While authentication is enabled, every MCP and health request must send `Authorization: Bearer <token>`.
- `HRONAUT_DISABLE_MCP_AUTH`: force the current launch to keep MCP authentication disabled even if the profile normally requires it. The setting can be changed immediately under **Settings → MCP security**. This override does not change the remote-access setting. Anyone who can reach the listener can control the profile while authentication is off; enable authentication on computers where local processes are not equally trusted.
- `HRONAUT_USER_DATA_DIR`: use an alternate profile directory instead of the packaged or `hronaut-dev` default. This is primarily useful for isolated integration tests.
- `HRONAUT_DISABLE_AUTO_UPDATE`: set to `1` to disable update checks for the current launch.
- `HRONAUT_DOWNLOAD_DIR`: use this directory as the profile's default instead of the operating system's Downloads directory. A folder explicitly chosen in Settings takes precedence.

## Track bounded task runs

The QA and Complete tool sets include `browser_task_runs` for workflows that
span several browser actions. Call `start` with an authorized active workspace,
an overall deadline, a heartbeat timeout, and up to eight typed completion
checks. The returned opaque run ID and revision are correlation handles, not
authorization. Send the latest revision with each `heartbeat` or `complete`.
Stale revisions are rejected, and heartbeats never extend the overall deadline.

For a repeatable workflow, call `save` with a bounded name and intent, typed
input declarations, ordered read-only/review-gated/mutation steps, the exact
browser or wallet capability used by every step, expected evidence, and one to
three attempts. Attempts beyond the first are always limited to read-only
steps. Saved definitions belong to the workspace in which they were created;
`list-saved` never exposes another workspace's definitions. Definitions are
immutable: changing a workflow creates a new ID and revision instead of
silently changing an existing run.

Before a saved run, call `preview` with its exact revision, target tab, expected
HTTP(S) origin, and runtime input bindings. The preview returns input names and
whether each was supplied, the named opaque browser context, declared
capabilities, evidence, human gates, retry policy, and a status of `ready`,
`needs_review`, `stale_context`, or `reconciliation_required`. Input values are
used only to bind the preview token; they are never returned or persisted. A
`start-saved` call must repeat the same bindings and current preview token.
Navigation, observation, origin, workspace-control, definition, or input drift
invalidates that token before admission.

Every admitted saved run adds a private machine check bound to its exact tab,
navigation and observation generations, expected-origin fingerprint, and
current workspace-control generation. Heartbeats and completion revalidate it.
Same-origin navigation or changed content becomes `stale-context`; a missing
tab or unavailable control evidence becomes `reconciliation-required`. Neither
outcome permits blind retry. Start a fresh preview and run after reconciling the
current browser state. A saved run never executes declared steps itself:
review-gated and mutation steps still use `browser_human_waiting` and the
ordinary exact-action dispatch controls.

Completion checks can require a fixed tab to be settled, require its current
HTTP(S) origin to match the exact origin supplied at start, or require a retained
action-audit run to be stopped without a persistence failure. Expected origins
are stored as SHA-256 fingerprints and are not returned. A `SUCCEEDED` claim
requires at least one check. Hronaut durably records an intermediate verification
admission, then every check must pass again before success is published. A failed check becomes `BLOCKED`; unavailable evidence becomes
`OUTCOME_UNKNOWN`; evidence drift while success is saved becomes
`OUTCOME_UNKNOWN` with `COMPLETION_CONTEXT_CHANGED`.

Missing heartbeats or the overall deadline produce `TIMED_OUT` with a fixed
reason. An unfinished run restored after application restart becomes
`OUTCOME_UNKNOWN`; Hronaut never resumes work or infers success. Callers may
also explicitly finish with `FAILED`, `CANCELLED`, `BLOCKED`, or
`OUTCOME_UNKNOWN`. Every summary adds a stable lowercase `outcome`, bounded
`reasonCode`, and `evidenceSource` while retaining `state` and `terminalReason`
for compatibility. `effects` remains `not-established`: stopping a run does not
prove that earlier browser effects were rolled back. The
profile retains at most 100 runs and evicts only the oldest terminal record when
full. Corrupt or oversized history makes the service unavailable rather than
silently resetting it.

Call `metrics` to correlate retained human-decision records whose `runId`
matches a retained task. The workspace report includes per-task and total counts
for interruptions, interruptions per completed task, approvals, rejections,
completed tasks, ambiguous outcomes, and decision time. `errorsCaught` counts machine-check failures and approved
actions invalidated before dispatch; it does not treat every prompt or rejection
as an error. Unknown correlation IDs are ignored. The report contains only
opaque IDs, bounded states, counts, and millisecond durations, and is available
to read-only capability profiles.

Saved-task files contain the bounded task name and intent, input schema, step
classes and capability names, evidence schema, retry policy, workspace and
opaque revisions. Run records add tab IDs, timestamps, typed check state,
generations, origin/control fingerprints, and opaque audit-run references. They
do not contain runtime input values, page text, URLs, tool arguments or results,
credentials, uploads, cookies, or artifact bodies. Saved-run summaries include
a versioned privacy-safe receipt with task revision, context generations,
declared approval state, and Hronaut's authoritative bounded outcome; the
fingerprints remain private. Workspace ownership is checked before and after
disk or browser work, and reconnect changes the bound control context. This
Hronaut workflow contract is separate from the version-negotiated
[MCP Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview),
which represents deferred execution of a single protocol request.

## Record action audit receipts

The QA and Complete tool sets include `browser_audit_receipts`. Recording is off
until an authorized client calls `start` with its `workspaceId`. Call `stop` to
drain pending actions, `list` to find retained runs, and `read` with a `runId` to
obtain a sanitized JSON report. After reconnecting, resume the workspace with its
private resume key before accessing its runs. Audit-control calls are excluded
from recording, so stopping a run does not wait for itself.

Archiving or closing a workspace finalizes its active run asynchronously. An
authorized archived workspace can still list and read its receipts; after
reconnecting, resume the archive with `browser_saved_workspaces` first. Starting
a new recording requires an active workspace. Reports include their recording
scope and interpretation caveats so exported JSON can be reviewed independently.

Each workspace retains at most three runs, each capped at 1 MiB and 1,000 journal
entries. Starting a fourth run retires the oldest whole run. Accepted actions
reserve space for their outcomes; site observations have a bounded write queue,
and omitted observations are counted. An interrupted run is reported as such and
never automatically resumed or replayed. Failed metadata persistence leaves the
run in a stopping state until stop succeeds. Unindexed journals are preserved for
recovery instead of silently discarded.

Receipts cover workspace-scoped browser tools, workspace admission, observed
site-policy decisions, and bounded before/after state. Workspace lifecycle and
wallet tools are outside this stream; wallet actions retain their separate audit
contract. Native page events may have no action correlation. Unavailable state is
`null`, and possible effects after failure or cancellation do not imply rollback.
Handoff-invalidated reads have outcome status `stale-observation`; uncertain
writes have `outcome-unknown`, including when their transport was cancelled.
Format version 4 observations include privacy-safe write-lease evidence; older
retained observations remain readable and may omit it.
These statuses do not authorize a retry or establish whether a write took effect.
Site identities are opaque and stable only within one live run. Reports contain
no raw URLs, titles, tool arguments, tool results, error text, form values, page
content, cookies, resume keys, or MCP tokens. The journal hash chain detects
inconsistent history; it is not proof against someone who can rewrite local files.

Format-version-2 reports include a bounded `evidenceCoverage` list before an
agent opens a separate diagnostic, network, DOM-change, storage-change, or
reproduction report. Available artifacts have opaque UUID references scoped to
the retained workspace run. Resolve one with `action=evidence`, its `runId`, and
`evidenceId`; Hronaut returns the existing tool to open, without copying that
tool's contents into the journal. Live references expire after process restart,
control changes, navigation, observation changes, or tab removal. Missing,
unsupported, dropped, expired, and uncorrelated coverage remains explicit, and
the list reports a limit and omitted count. Postcondition references locate the
exact retained verification receipt instead of a live browser surface.

### Verify a delayed browser write

Use `browser_reconciliation` before a visible system-of-record write when the
workflow needs to distinguish a new target, an already-satisfied target, a
changed target, a missing update target, blocked context, or an ambiguous read.
Supply a stable logical item key, target identity, source revision, create,
update, or upsert mode, and exact origin/account/target markers. Update mode
also requires the exact current target text. Hronaut reads once in an isolated
world and returns only fixed status fields plus domain-separated SHA-256
fingerprints for the logical item, target, and source revision. Raw identifiers,
selectors, account text, and target text are not returned or added to audit
receipts.

Preparation is read-only and grants no authority. Repeat the same object as
`browser_click.reconciliation` and provide a matching click `postcondition`.
Hronaut repeats the lookup immediately before dispatch. Create proceeds only
when the target is absent; update proceeds only when the exact expected current
text still exists; upsert accepts either condition. A target that already has
the desired value returns `SKIPPED_ALREADY_PRESENT` without clicking. Origin,
account, precondition, navigation, control, workspace, or human-input drift;
duplicate matches; unavailable reads; and missing update targets prevent the
click. The preparation and click share no reusable capability, and Hronaut does
not infer idempotency from HTTP or tool success. The click result keeps
pre-write, dispatch, transport, and read-back states separate under
`preWriteReconciliation`, `postWriteVerification`, and
`reconciliationOutcome`; only an authoritative match produces `verified`, while
a possible dispatch without that match remains `reconciliation_required`.

**Linux page-authored menus:** call `browser_click` with an explicit `tabId`, exactly one `ref` or `selector`, `native: true`, and `button: "right"`. Omitted button retains existing left-click behavior. The tab must already be active, visible, awake and locked through the trusted UI, outside split view, at default zoom/display scale 1 with no emulation overrides, child frames, native selection or Developer Tools. Hronaut does not wake, select, follow or unlock a page to admit right-click. Coordinates, double clicks, modifiers, dialog handling and unsupported platforms reject. Opening a menu and selecting its item are separate authorized calls; take a fresh snapshot between them. A page without a handler does not open Hronaut's native app menu under this lock.

The explicit button participates in exact action-review identity and `browser_click.button` capability argument constraints. An omitted/left review cannot authorize a right click. An unrestricted click capability still grants both supported buttons; add an exact button constraint when restricting a client.

Right-click retains the original sampled target and single matching release ownership. If a press may have executed, one best-effort release path runs even after authority loss; release preparation or acknowledgement failure never earns another attempt. Cleanup may itself produce menu/page effects, and an acknowledged release does not turn an uncertain press into success. Failed cleanup can leave button/compositor state uncertain; quarantine is containment, not proof of restoration. Pending native work retains workspace ownership through cancellation or transport loss until actual settlement, possibly indefinitely. Never automatically replay. Native event ordering is verified only on Linux; alternate ordering has controlled source tests, not Windows/macOS native support. Sampling is not an atomic routing or handler-execution guarantee.

`browser_click` accepts an optional `postcondition` when an action-receipt run is
active. It binds the click to the current workspace, tab, HTTP(S) origin, account
marker, and expected visible state before dispatch. After the click transport
succeeds, Hronaut performs up to five isolated-world reads with bounded backoff
for at most 30 seconds. The click itself runs exactly once.

Supply `expectedOrigin`, a unique `accountSelector` and its exact bounded
`expectedAccount` text, plus a unique `stateSelector` and exact `expectedText`.
Optional `timeoutMs`, `maxAttempts`, and `initialDelayMs` tune the bounded read
window. Selector and expected text values stay local and are excluded from the
receipt. The tool result includes a safe `postWriteVerification` status; the
receipt preserves the original transport outcome separately from pending,
not-yet-visible, verified, or unknown verification events.

A missing delayed state is not treated as permission to click again. Timeout,
read failure, account or origin change, navigation/control drift, cancellation,
human takeover, and persistence failure end conservatively. Verification
requires fresh authorization before each read, never executes page-authored
query hooks, and never resumes after restart. API-backed integrations can use
the same internal receipt lifecycle when they have a provider-specific revision
or idempotency contract; Hronaut does not infer such a contract from generic MCP
annotations or HTTP success.

## Check workspace readiness

The QA and Complete tool sets include `browser_preflight`. Supply your
`workspaceId`, an optional workspace `tabId`, and an optional `expectedOrigin`
(HTTP or HTTPS origin only). The response contains `PASS`, `WARN`, or `BLOCKED`
checks with fixed reasons and next actions for connection ownership, tab
readiness, expected origin, site policy, and pending human attention. It does
not wake a sleeping tab, navigate, inspect page content, or retry an action.

The QA and Complete tool sets include `browser_continuity`. Create an explicit

resume with the private workspace key. A checkpointed workspace returns its

`nextAction`. `PASS` means the compared evidence matches; when `suspended` is

evidence requires fresh review and acknowledgment of an unknown outcome.
Reports exclude raw origins, policy rules, page content, and resume keys.

the copy. If the required guard cannot be saved, direct agent access is revoked

It retains workspace order. Every whitespace-separated, case-insensitive literal term must appear in the same tab's projected title or address; terms may appear in either field, in any order. An empty query lists eligible tabs, one term matches that term, and no match returns an empty array with zero matching/returned counts.

Compact discovery includes only live HTTP(S) tabs in the authorized workspace with a parseable address of at most 8,192 UTF-16 code units. Application pages, closed/archived tabs, other workspaces, unsupported/malformed addresses and oversized source addresses do not contribute rows or counts. Native history-restored titles remain unverified even if Electron later marks their event explicit; an authored title identical to a restored title is conservatively omitted. This record retains at most 50 distinct normalized titles per tab; exceeding that bound omits all compact titles for that tab until it closes. Fresh distinct authored titles remain searchable below that bound. Titles are projected to 160 code units and addresses to 512; omitted components and truncated suffixes cannot influence matches. `projectionTruncated` reports whether any included explicit title or address was shortened (it does not count omitted unverified titles), and counts describe these projected fields rather than exhaustive full-text matches. Baselines live only in bounded process memory, are discarded with their tab, contain the same sanitized snapshot text, do not grant authority, and are not authoritative read-back for an external side effect.

Within one document, each observed control keeps its `e<n>` ref across captures, so inserting, removing or reordering other controls does not renumber surviving ones or report them as updates. Identity is held weakly in an isolated observation world, never in page JavaScript, and the `data-hronaut-ref` attribute is only the published handle: a replacement or cloned node with identical text receives a new ref and appears as a removal plus an addition. A component capture still publishes refs only inside its root, but surviving elements regain their earlier refs in a later whole-page capture. A new document restarts numbering at `e1`. After one million refs in one document, numbering restarts with fresh identities and the next delta reports the renumbering. Stable identity is comparison evidence for the same DOM element, not permission to act and not proof that its meaning is unchanged.

Semantic `browser_click` targets (refs or selectors) reject live native-disabled controls, including disabled fieldset descendants except controls in the first legend. This applies to ordinary, dialog-handled, native and double clicks. A control disabled after a snapshot is checked again at dispatch; wait for the page to enable it and inspect it again before retrying. ARIA-only disabled state does not suppress existing click behavior. A successful click acknowledges dispatch, not completion of a business operation; verify the resulting page state or use an explicit postcondition. Raw coordinate clicks retain their existing behavior.

**Tabs opened during a click:** when the clicked tab asks to open tabs while a successful `browser_click` runs, through a `target="_blank"` link or `window.open`, the result includes `tabsOpenedDuringClick`. `tabIds` lists up to five tabs that are still open in the same workspace when the result is returned, after any postcondition read-back; `more` counts further tabs beyond that bound, `closed` counts tabs closed before then, `blocked` counts requests Hronaut refused before opening (for example under a workspace navigation policy, without their destinations), `failed` counts requests Hronaut could not open, such as at the tab limit, and `pending` counts creations that had not settled when the click returned. Observation starts when the click resolves its tab and ends when the click returns, so a page timer that opens a tab during the click is reported too; it is not proof that the click caused it. A popup that opens after the click returns is not reported, and a missing field means no request was seen in that window, not that none will follow; use `browser_tabs` to find later tabs. A listed tab may still be loading or may later navigate elsewhere. Reporting never selects, focuses or loads anything, never repeats input, and failed or interrupted clicks report no tabs.

Semantic clicks, including dialog-handled clicks, recheck agent authority and document context after asynchronous pointer/input preparation and immediately before dispatch. A document commit during preparation rejects the action, including the initial load started by `browser_new_tab`; observe the intended target with `browser_wait` and obtain fresh page state before clicking. Rejections remain unsafe to replay automatically because preparation may already have effects.

Native `browser_click` input (coordinates, `native: true`, or double-click, without dialog handling) rechecks agent authority and cancellation before movement and each press, including after temporarily lifting the human-input barrier. If authority or navigation changes, later presses stop. A successfully dispatched press still receives its matching release, which can complete that click. An interrupted result is not safe to replay automatically: scrolling, hover, or an earlier click may already have effects. Inspect fresh page state before deciding what to do next. This does not establish that the page accepted the action.

For ref/selector native and double clicks, Hronaut retains the original top-document element before page preparation and samples the exact floating-point viewport CSS coordinates before each press, after lifting any native input barrier. This path supports only `text/html` documents; XHTML/XML documents reject before page flag, scroll and pointer preparation, but input setup/cleanup can already run, so failures conservatively retain possible effects. An isolated-realm hit test rejects a disconnected, replaced, ambiguous, disabled or covered target. Ordinary descendants and pointer-events-none overlays can pass. Embedded receivers and their fallback descendants are conservatively unsupported, as are receivers with open, closed or user-agent shadow roots. The ancestor check rejects paths exceeding 64 nodes. CDP receiver descriptions can transport attributes and other node data internally even at depth zero; admission consumes only kind, shadow and frame metadata and does not publish the raw description. Programmatic, dialog-handled and raw coordinate clicks keep their existing paths.

This is sampled admission, not atomic routing: the renderer can change after the final sample (or native shadow metadata read), so a later press can still reach another receiver. Page-world scroll, geometry and pointer preparation are not hardened against all page overrides. Acknowledgements are command transport evidence, not handler or business success. Failures are MCP errors with bounded reasons and separate attempted/acknowledged movement, press and release counts. Rejection before the first press can still follow effective scroll or hover; rejection before a second press can leave the first click complete. Do not replay automatically or substitute a programmatic click. Inspect fresh visible state and any explicit postcondition.

The existing MCP workspace write lease remains held through input cleanup and final settlement; overlapping MCP mutations in the same workspace return `WORKSPACE_BUSY` before dispatch. If retained-handle cleanup, input restoration, or a matching release cannot be confirmed, subsequent semantic native clicks on that tab are blocked until it is closed. Holds require the active visible, already awake page outside split view, with no child frames, native selection or Developer Tools. They never wake, select or force focus. `DISPATCH_ACKNOWLEDGED` reports acknowledged down and release, not application success. Every MCP browser workflow creates a fresh workspace with `browser_workspaces` **create** before using page tools. An agent can first call **list** to find sources marked `forkOnly`. It must pass only the UUIDv7 `id` returned by its own create call as `workspaceId` to page tools. Create also returns a private `resumeKey`. A live MCP connection is authorized only for workspaces it created, resumed with that key, or reopened from one of its authorized archives. The normal list returns full state only for those authorized active workspaces; sources whose direct agent access is disabled appear as metadata-only `forkOnly` entries. These entries cannot be browsed, resumed, or changed. The separate `list-fork-sources` action exposes bounded metadata (`id`, `name`, `description`, `color`, `archived`, `agentAccess`) for every active and archived source. Neither list reveals source tabs, URLs, origin inventory, storage IDs, or resume keys for unauthorized sources. When the same task reconnects or Hronaut restarts, it must retain the workspace ID and resume key outside website content and call `browser_workspaces` **resume** before page tools. Archived workspaces use the parallel `browser_saved_workspaces` **resume** action before open or delete. Archive/reopen preserves both the stable workspace ID and resume key, including when the human archives or restores the workspace through Hronaut chrome. Names are only human labels, may repeat across isolated clients, and can change; neither a name nor knowledge of another workspace UUID grants access.

New tabs, bookmark/history opens, website popups, duplicated tabs, closed-tab restores, the implicit active tab, and returned browser state all stay inside the supplied agent workspace. Direct commands, page navigation, redirects, and popups cannot open local files, Hronaut application pages, internal browser pages, other privileged/custom schemes, or URLs with embedded HTTP credentials. Normal credential-free HTTP(S), web-page source views, embedded `data:` QA documents, origin-bound HTTP(S) `blob:` documents, and inert `about:blank` documents remain supported. The separate `browser_file_upload` capability remains an explicit way to attach an agent-supplied absolute local path to a website file input. Hronaut rejects a tab ID from a different workspace and preserves workspaces and their tabs across restarts. Global human New tab commands (including Ctrl/Cmd+T) use the focused tab's workspace, otherwise the first active workspace, and create a normally named workspace only when none exists. The trailing **New tab** button inside a workspace explicitly creates its tab in that workspace.

Click a named workspace header to collapse or expand its tabs, or focus the header and press Enter or Space. Hronaut remembers collapsed workspaces across restarts, keeps the current workspace visibly emphasized, and shows its tab count even while the individual tabs are hidden. Right-clicking a workspace header opens its controls. **Pin Workspace to Top** there moves a workspace above the others, in the rail and the tab strip, with a small pin icon after its name and "Pinned to the top" in its tooltip and accessible description; workspaces pinned later go after those pinned earlier, and **Unpin Workspace** returns it to its usual place. Tab shortcuts (Ctrl+Tab, Ctrl+1 to 9) and the tab shown after you close or put one to sleep follow that order on screen. The pin is saved with the workspace as the time it was pinned (`pinnedAt`, also reported by `browser_workspaces`), changes neither when the workspace was last used nor what agents may do there, and is dropped when the workspace is archived. Only the person pins or unpins a workspace; no MCP tool changes it. A saved pin that is not a readable time is dropped when Hronaut loads its tabs. With the tab rail on the left, a workspace's header also shows the coding agents seen there in the last five minutes, as small overlapping avatars after its name: the first letter of each MCP client's name in its avatar color, with an accent ring while it works, an amber ring while it needs you, dimmed while idle, up to three and then a +N count. In a narrow header the avatars that no longer fit whole are left out before the name is cut, and in a rail narrower than the default a workspace that needs you shows its **Needs you** label without them. Their names and states, up to three and then a +N count, are in the header's tooltip and accessible description ("Agents here: Claude Code (Working)"), not its name. A folded workspace opens by itself when an agent that was not there starts working in it, or when it starts waiting for you, including an attention request that names no tab. If you fold it again, it stays folded while the same agents work there, through the pauses between their steps, and when a request for you ends while the agent carries on; it opens again when another agent starts working there, when an agent comes back after five minutes without a call, or when it waits for you again. What the workspaces show when the rail first loads, or when a workspace first appears, is where they start, so restarting Hronaut opens no folded workspace by itself. The top tab strip shows no avatars and opens no workspace by itself; the toolbar shows the agents of the workspace in view. Tabs can be reordered only inside their current workspace and cannot be moved between workspaces. The workspace editor offers nine labeled colors; agents receive the same palette through `browser_workspaces` create and update operations.

Use **Archive Workspace** from that context menu when an investigation should leave the active tab strip without being lost. Archived workspaces retain their browser profile and reopen their ordered URLs and pinned state under the same stable `workspaceId`. Permanently closing or deleting a workspace deletes its browser data; it does not recreate Default. Closing one from its editor or archiving it from its header offers Undo for 6 seconds, as described for tabs above. `browser_saved_workspaces` lists only archives authorized for the current MCP connection, and a reconnect must resume its own archive with the private key returned at creation or save time before opening or deleting it.

Every workspace receives its own persistent Electron partition for cookies, local storage, cache, service workers, and related website state. On `browser_workspaces` `create`, choose `storage: "scratch"` for clean storage or `storage: "fork-workspace"` with a `sourceWorkspaceId` from `list-fork-sources`. A fork copies cookies and local storage once, receives a new identity and private resume key, inherits the source navigation restrictions, and starts without copying source tabs. Sources with direct agent access disabled can still be forked; this never authorizes access to the original workspace. Only the human can change direct agent access or navigation policy. Use the human transfer controls to copy or move data between existing workspaces. Hronaut rejects overlapping copies and prevents a participating workspace from being renamed, archived, or deleted during a transfer. Bookmarks, history, download records, and remembered permissions remain application-wide.

`browser_storage` inspects or edits local storage, tab-specific session storage, and non-HttpOnly cookies for one tab inside the caller's workspace. Lists default to metadata-only; request `includeValues` or use an explicit `get` when a bounded value is needed. Results are capped at 200 entries, 16 KiB per returned value, and 128 KiB of values in total; inputs are capped at 256 KiB. Local and session storage keys are matched exactly, including empty and whitespace-only keys; get, set, and delete still require an explicit key. HttpOnly cookie values are never returned or edited. Use `browser_site_data` when the task requires clearing broader origin data such as caches or all cookies and storage.

Cookie `delete` with only `key` removes every non-HttpOnly cookie of that name that applies to the tab. To remove one cookie, also pass `cookieDomain` and `cookiePath` exactly as a cookie listing reports them, including any leading dot on the domain. Matching is exact, with no prefix, wildcard, or suffix matching and no fallback to deleting by name only. Same-name cookies on other paths or domains, and cookies in other workspaces, are left unchanged. Exact deletion uses Chromium's debugging connection, so it is unavailable while Developer Tools is open for the tab. It rejects HttpOnly, missing, partitioned, and ambiguous identities before dispatch, including a partitioned cookie that shares the same name, domain, and path. The result reports `changed: true` only after a fresh read no longer finds the selected cookie. If that check fails after the delete was submitted, the outcome is unknown; inspect storage before deciding what to do next, and do not repeat automatically. These selectors are rejected for every other action and storage kind.

Cookie edits recheck the original document and workspace, workspace access, pause state and MCP control before each native write and before publishing results. These checks also reject a document or access change that is subsequently reversed. A rejected operation with no submitted cookie writes reports `NOT_DISPATCHED`; an interrupted operation with attempted writes reports `OUTCOME_UNKNOWN`, `effects: "possible"`, and attempted/acknowledged native-call counts. One native call can affect multiple same-name cookies under the existing deletion contract; these are not counts of cookie identities changed. An acknowledgement is not a transactional guarantee. Earlier writes are not rolled back, and neither outcome authorizes automatic replay. The existing cookie-session generation check at MCP admission is retained. This does not extend that check across later asynchronous cookie work: cookie changes from another tab, a server or the operation itself are not distinguished, and concurrent session changes after admission remain unguarded. Ordinary single writes and batches retain their existing completion behavior when the document, workspace and control checks remain valid. These checks do not establish cookie-session stability, add exact cookie selectors or make a multi-cookie edit atomic.

Local/session `browser_storage` reads and mutations retain document, workspace access and control checks through result publication, including later audit/review settlement. A veto withholds keys and values. Failures before JavaScript submission report `NOT_DISPATCHED`; after submission, reads report `STALE_OBSERVATION` with no mutation effects and mutations report `OUTCOME_UNKNOWN` with possible effects. `executionSubmitted` and `executionAcknowledged` describe execution, not proof or a count of writes. A late veto does not roll back changes: even an acknowledged call can have changed storage before intervention. Inspect fresh state before deciding what to do next; never automatically replay. These checks do not establish an atomic storage snapshot, prevent concurrent page writes, or add cookie-session guarantees.

Use `browser_storage_changes` to save a volatile baseline before reproducing an issue and compare it afterward. The report groups added, updated, and removed local-storage, session-storage, and cookie keys, includes byte sizes and cookie attribute changes, and omits values by default. `includeValues: true` returns only bounded non-HttpOnly values; HttpOnly values remain protected. Baselines are held only in memory, clear automatically when the tab changes origin, and never authorize access outside the caller's workspace. Pending captures reject if their document changes between the DOM-storage and cookie reads or before saving; a rejected same-origin capture preserves the previous completed baseline and comparison. These reads are sequential, not an atomic storage snapshot. MCP comparison results and terminal activity are checked again after audit settlement for page, workspace access, control and cancellation changes. Withheld results omit stored keys and values. Failure metadata reports `comparisonStateChanged` for updates already made by this operation and `siteStorageWriteSubmitted: false`; it does not promise rollback or prevent page-owned storage APIs from having effects. A late veto preserves an already completed comparison update unless a newer action or navigation has replaced it. Do not automatically replay.

`browser_indexeddb` inspects the same top-level-origin database state shown in Site storage → IndexedDB. Without a database it returns bounded names and versions; selecting a database adds object-store key paths, auto-increment state, indexes, and entry counts; selecting an object store adds an ordered, paged key list. Values are omitted by default. `includeValues: true` returns bounded JSON-like previews for supported structured-clone values, including safe descriptions for blobs, buffers, maps, sets, dates, and typed arrays. The inspector runs in an isolated Chromium world, remains available on human-locked or MCP-created tabs, does not occupy the Developer Tools connection, and never mutates a database. Third-party-frame databases and database or object-store names beyond the documented 512-character bound are out of scope; lists are point-in-time snapshots, and website-authored database, store, index, or key names—as well as opt-in values—can contain private application data.

`browser_storage_usage` returns the same read-only origin overview shown in Site storage → Overview: total usage, Chromium's current quota estimate, remaining allowance, percentage used, and a bounded byte breakdown by browser-defined storage category. It works on locked and MCP-created tabs. When Developer Tools owns Chromium's debugging connection, Hronaut falls back to `StorageManager.estimate()` and marks the reduced-detail source in the report. The tool never returns storage keys, values, filenames, or cached response bodies, and it never changes quota or clears data.

`browser_indexeddb` and `browser_storage_usage` retain their document, workspace-access and control checks through native reads and final MCP publication. Invalidated observations withhold database names, keys, values and usage details and report `STALE_OBSERVATION`, `effects: "none"` and `retrySafe: false`. Cancellation also withholds a pending result; it does not cancel an already submitted native read. Quota fallback requires the original inspection authority to remain current, including after an unsupported native command. These checks do not make point-in-time reads atomic or detect every concurrent storage/session change. Obtain fresh context before choosing a new inspection.


`browser_pwa` inspects the same top-level-origin offline state shown in Site storage → Offline. It returns bounded web app identity, presentation, icon, shortcut, parse-error, and Chromium installability diagnostics together with service-worker registration scopes, worker script/state metadata, and current Cache Storage names; selecting a cache adds server-side-paginated request URL, method, response status, type, and time metadata, with an optional path filter. Raw manifest source and cached response bodies are never returned, and headers are omitted by default; `includeHeaders: true` adds bounded headers with recognized security-bearing names redacted. Registration discovery remains available on locked or MCP-created tabs even when Chromium Developer Tools owns the debugging connection; in that case the report clearly marks debugger-dependent manifest, installability, and Cache Storage inspection unavailable. The tool is point-in-time and read-only. Use `browser_site_data` only when the task explicitly requires unregistering workers or clearing caches.

`browser_pwa_lifecycle` explicitly starts, reads (`get`), stops or clears a bounded metadata observation for a top-level HTTP(S) page. Site storage → Offline provides the same controls; an active tab badge also stops observation. The observer reads registrations and subscribes to worker/controller events, without updates, messages, activation, worker evaluation, cache clearing or permission changes. Registrations belong to the origin and workspace, not exclusively to the tab. Capture-local worker identities distinguish versions at the same script URL. Callback timestamps describe observations, never reconstructed lifecycle times. History is always incomplete: one-second discovery can miss early transitions and registrations created and removed between scans. Limits are 100 events, 20 registrations, 100 workers and two minutes; hitting a collection limit ends capture with truncation. Reads return the last drained snapshot and its `lastDrainedAt`, not an atomic live state. Navigation/reload, closure, debugger loss or authority loss interrupts capture; stopping or interruption may lose undrained events. Sleeping or frozen tabs are not awakened; sleep or freeze interrupts observation. Five captures are retained in memory, with the oldest stopped capture evicted first. Use `captureId` and another live tab in the same workspace to read a closed tab's retained evidence. Workspace boundaries remain enforced. This feature does not claim universal worker-lifetime neutrality or complete historical coverage.

When a manual step is unavoidable—such as entering credentials, completing a CAPTCHA, approving a device prompt, or pressing a control that cannot be automated—an agent can call `browser_request_user_attention` with a short reason and optional tab ID. The optional `notificationMessage` sets the system notification text; it defaults to the reason. Hronaut marks the requested tab, plays the selected attention cue, pulses its tray icon, and flashes its taskbar entry until the window is focused or the alert is dismissed from the tray menu. The cue can be selected, previewed, or disabled in Settings → Appearance. The pending request is also reported by `browser_status` and `browser_preflight` until the human acknowledges it. Do not include passwords, tokens, or other secrets in either text because the operating system can display them outside Hronaut.

A click or key press in Hronaut, opening the notification, or **Show** in the tray menu acknowledges the request: the cue, tray pulse, taskbar flash and notification stop, and `browser_status` and `browser_preflight` stop reporting it, but the requesting agent's avatar, its workspace and the requested tab keep their **Needs you** mark until the request ends. While it is open, the page that needs you carries the handoff edge light: an amber ring that the shell draws just outside the requested tab's page, or outside each page in view from the requested workspace when the request names no tab, over the edge of the toolbar and rail and never on the page. It swells once over 2.4 s when it appears (not with reduced motion), is set aside while a dialog or menu covers the page, and becomes a system-colored outline in forced-colors mode. The human answers it from the agent's card: **Done, hand back** resolves it and **Dismiss** dismisses it. A request made for a `browser_human_waiting` decision is answered as that decision instead (see the agent card below) and lasts while it is waiting or acknowledged. A plain request also ends when, after it was acknowledged, the agent that asked successfully finishes a step that it started after asking and that acts in that workspace (click, type, fill a form, choose, press a key, drag, navigate, use the page's history to go back, go forward, reload or stop, open or close a tab, or upload), unless the step names another tab than the requested one; reading, screenshots, waiting and status calls do not end it. A request stays after acknowledgement only while an agent's avatar shows it, so that its card can answer it: a request that no avatar shows, because it names no workspace, the MCP server stopped or the workspace's agent access was turned off, ends when acknowledged, and an acknowledged one ends when its avatar goes away. Any request ends on expiry, when a newer request replaces it, when its tab or workspace closes, or with **Dismiss** in the tray menu. For a tab-scoped request, the human can also choose **Mark as resolved** in that tab's context menu. Opening or dismissing the notification only acknowledges the alert; it does not complete the manual task. The menu remains available after acknowledgement and resolves only the request captured when the menu opened. It cannot resolve a newer request, a closed/moved tab, or a consequential `browser_human_waiting` decision.

Keep the returned attention `id`. Call `browser_user_attention` with your authorized `workspaceId`, `requestId: id`, and `action: "wait"` to await explicit human resolution (default 30 seconds, `timeoutMs` from 1 to 60000). `action: "status"` reads immediately. A wait returns `{outcome, request}`: only `outcome: "resolved"` means the human explicitly resolved that request. Timeout leaves the request open; supersession, expiry and target closure are distinct outcomes. Workspace access loss/removal and cancellation fail closed through the existing MCP error contract. Concurrent waiters and an already-resolved request observe the same identity; waiting does not hold a workspace mutation lease or approve another agent action. Recheck fresh page state before continuing.

This lightweight lifecycle is runtime-only: up to 100 request records, unresolved expiry after 24 hours, and no history across app restart. An unavailable request is never treated as resolved. Workspace-only attention can be inspected, but the tab-menu resolution flow requires a tab-scoped request. Existing durable human decision/approval review semantics remain separate.


For a durable decision, `browser_human_waiting` provides `request`, `list`, and `cancel` actions scoped to an owned, agent-accessible workspace. A request supplies a UUID `runId`, one of `review-page`, `approve-action`, `provide-input`, or `resolve-unknown`, and optional `owner`, `fallbackOwner`, and `timeoutMs` (1 millisecond to one day; default 15 minutes). Owner labels are at most 128 characters and identify responsibility; they are not authentication credentials. No page text or arbitrary prompt is accepted. A request establishes the workspace continuity guard before recording the decision and requesting local attention.

An `approve-action` request must include one `review` object. It can describe one mutating workspace tool with `toolName`, proposed `arguments`, `reversibility`, and either a bounded `description` or `visible-browser-only` representation, with an optional bounded `expectedPostcondition`. It can instead contain `steps` with two to four ordered `browser_click` reviews. Every grouped step requires both the click's declarative `postcondition` and a bounded human-readable `expectedPostcondition`; this keeps advancement tied to authoritative read-back rather than transport success. Hronaut validates and normalizes every proposed argument object with the target tool schema, then retains only domain-separated SHA-256 artifact hashes and bounded review metadata. Raw selectors, entered values, scripts, credentials, and other proposed arguments are not written to human-decision history. The visible review identifies every ordered step plus the workspace, capability profile, current safe origin and tab, action class, reversibility, state generations, deadline, exact artifact hashes, and bounded receipt timeline.

Records have an ID and revision, deadline, notification status and attempt count, prior-outcome classification, and a distinct `WAITING_FOR_HUMAN`, `ACKNOWLEDGED`, `RESOLVED`, `REJECTED`, `EXPIRED`, `CANCELLED`, `ATTEMPTED`, `VERIFIED`, or `UNKNOWN` state. Listing needs no live tab and remains available after reconnect once workspace ownership is resumed. Cancellation requires the exact ID and revision. Records are stored locally with bounded capacity; unresolved records, approved reviews, and reviews with an action in progress are never evicted to admit another request. A storage failure is reported instead of an empty history. After restart an unexpired ordinary decision requires fresh acknowledgement; proposed and approved consequential reviews expire, and an attempted action becomes unknown. A decision the person resolved, rejected or cancelled in Hronaut also carries `answeredAt` and can carry the person's `note` for the agent: at most 1,000 UTF-16 code units, with line breaks kept, tabs as spaces, and other control characters, invisible format characters (except the zero-width joiner and non-joiner) and surrounding space removed. Both are kept in memory while the decision stays in the history, are dropped when a resolution is undone because the page changed while it was saved, and are never written to the decision history, so a decision listed after a restart has neither. A cancellation by the agent carries neither.

Open **Edit workspace → Human decisions** to refresh decisions, acknowledge receipt, reject or cancel a proposed action, or complete a review. Each open decision has a field for a note to the agent ("Your answer for the agent" for `provide-input`), sent with **Complete review**, **Approve**, **Reject** or **Cancel decision** and shown under the decision once answered, with when. What was typed stays in the field if sending fails. Grouped reviews show every ordered action and postcondition before approval. Completion requires an explicit checkbox and a fresh workspace continuity review above the panel, checked again after saving. A `review-page` or `provide-input` decision can also be completed from the agent's card, and a `review-page` or `approve-action` decision rejected there, with the same note bounds; approving an action and reviewing an unknown outcome stay in this panel. Agents cannot acknowledge, reject, or complete human decisions through MCP. Pending decisions block consequential page tools while inspection remains available. An approved consequential review also blocks every unrelated mutation. Its `id` and current `revision` can be supplied once to the exact normalized tool call; a changed artifact, origin, tab, navigation generation, human-input generation, workspace, scope, session, expiry, or continuity state invalidates it.

Before that exact tool dispatch, Hronaut durably records `ATTEMPTED`. A matching postcondition changes a single action to `VERIFIED`. For a group it advances to the next exact step, issues a fresh revision in `reviewContinuation`, and keeps unrelated mutations blocked; only the last verified step completes the group. An error or ambiguous result changes the review to `UNKNOWN`; a successful single action without authoritative postcondition remains `ATTEMPTED`. Restart converts an unresolved attempt to `UNKNOWN` and expires proposed or approved handles, so reconnecting cannot replay an old approval. Acknowledgement, rejection, cancellation, expiry, and completion never replay actions, unpause agents, erase an unknown outcome, or automatically clear the separate continuity guard. Notification delivery describes dispatch to local attention controls, not proof that a person saw or understood it.


For viewport capture only, optional `annotateRefs` accepts 1–50 current snapshot refs. The result adds a bounded text legend and numbered labels composited onto a derived image outside the page; default screenshots remain image-only. Targets use the existing latest-snapshot ref lifetime: take a fresh snapshot after page changes. Duplicate refs are deduplicated. Missing, ambiguous, hidden, offscreen, unsupported, moved or replaced targets are explicit per-ref outcomes; overlapping labels may be omitted. `bounds` and `labelBounds` use final output-image pixels, and partial viewport clipping is marked. Output is capped at 1920×1080, further reduced by `maxWidth`/`maxHeight`. PNG and JPEG are supported. Do not combine annotations with `fullPage`, `ref`, `selector` or `clip`.

Annotated capture pins each resolved element identity across the screenshot, rejects changed viewport/scroll/document/authorization, and omits detected target movement or replacement. It does not write labels to the DOM, move focus or scroll, or take debugger ownership. Geometry and pixels are sampled asynchronously; transient changes between samples can be missed. Bounds do not prove occlusion-free visibility, clickability, accessibility conformance or painted shape. Frame/shadow descendants, editors and pinch zoom are unsupported. The legend contains only requested refs, numeric labels, statuses and geometry, with no duplicated page text or form values. Screenshot pixels can still contain private data: annotation is not redaction.

`browser_screenshot` returns image content directly to the connected agent, ready to display or copy into its chat. Capture the visible viewport, the full page, one element from the latest snapshot with `ref`, any unique element with `selector`, or an exact visible rectangle with `clip: { x, y, width, height }`. Element targets are scrolled into view and captured at their full page bounds; clip coordinates are viewport-relative and must fit inside the visible page area. A plain viewport capture of a tab in the background also refreshes that tab's thumbnail in Search tabs, which stays in memory on this computer and is not returned to agents. PNG remains the lossless default; agents can request JPEG with a quality from 1–100 and bound any result with `maxWidth` and/or `maxHeight` while preserving its aspect ratio. For a human-reported issue, use the screenshot-region button in the website toolbar and drag the relevant area, or choose **Element screenshot** from Page tools or the command palette and click one component. Hronaut copies the resulting PNG directly to the system clipboard; paste it into Cursor, Codex, Claude, or another agent chat with Ctrl/Cmd+V. Element screenshots include the complete selected node even when it extends beyond the visible viewport. The pickers work on Default and MCP-created tabs, including locked tabs and pages with Developer Tools open. While selection is active, Hronaut owns the native input, blocks website handlers, ignores concurrent agent-generated pointer events, and restores normal input rules immediately afterward. Main-process coordinate and element fallbacks keep the selection valid when a reactive page replaces its picker state during the drag. Hronaut clears and reads the image back after copying, retries a rejected Linux clipboard write, and surfaces a concrete error when the system clipboard does not accept it. Compact captures reduce image transfer and model-context cost, and every scope keeps working while Hronaut is hidden in the tray. `browser_pdf_save` writes a rendered PDF to the configured download directory and never silently overwrites an existing file. Console and network histories are bounded to the 500 most recent stored entries per tab; adjacent identical ordinary Console events share one entry with `repeatCount`, while exceptions remain distinct. `browser_network` waits for detailed Chromium diagnostics to be ready and returns lightweight HTTP, WebSocket, and EventSource metadata with credentials, fragments, and security-related query values removed; call it once before reproducing an issue when later XHR replay or response-body inspection matters. Each completed response identifies direct network, disk-cache, prefetch-cache, service-worker, or fallback browser-cache provenance. Service-worker responses additionally identify Cache Storage, HTTP cache, fallback code, or a network fetch and include the bounded, best-effort-redacted Cache Storage name when Chromium provides one. Pass one returned ID to `browser_network_request` to inspect the same provenance plus bounded request and response headers and bodies; the parser, script, preload, redirect, or other initiator; retained redirect hops; direct parent and dependent requests reported by Chromium; and Chromium's connection setup, DNS, TLS, send, TTFB, response-header, content-download, and total timing when available. Relationship collections are capped at 12 summaries per kind, raw protocol IDs are never returned, and Hronaut does not guess dependencies from matching URLs or stack text. For WebSockets, the same call returns handshake status, open or closed state, and up to 100 sanitized sent, received, or error messages; text is capped at 4,096 characters per frame, binary payloads are omitted, and a tab retains at most 500 messages across its connections. For EventSource/SSE, it returns open or closed stream state plus up to 100 sanitized event names, IDs, and data records per connection; each data record is capped at 4,096 characters and a tab retains at most 500 events. Script initiators include at most 12 sanitized source frames with 1-based positions; URL credentials, fragments, and security-related query values are redacted, and inline `data:` or `javascript:` sources are omitted. Authorization, cookies, API keys, tokens, passwords, and other named structured secrets are redacted, while binary and multipart bodies are omitted. The human Network list has dedicated SSE and WebSocket filters, badges cached and worker-served requests, and shows the exact response source, worker provenance, Cache Storage name, initiator, relationships, timing, WebSocket messages, and Event stream evidence. People can jump between related requests and copy the complete sanitized request JSON directly into an agent chat. Every Hronaut text-copy action, including Home setup snippets, clears, writes, and reads back the native clipboard with retries; a rejected write produces a top-level application error toast and never reports a false success. For HTTP(S), the panel can also copy a sanitized cURL or fetch command; agents can request the same text with `copyAs: "curl"` or `copyAs: "fetch"` on `browser_network_request`. The human cURL copy action and copied feedback identify its POSIX-shell requirement. Copy cURL requires POSIX-shell syntax and rejects retained literal NUL characters, which cannot be represented in process arguments, with an explicit error before copying anything. Copy fetch remains available and preserves those characters through JavaScript string escaping. Existing secret filtering and body omission rules still apply. Hronaut never executes these commands. A retained XHR also exposes **Replay XHR** in the human panel and `browser_network_replay` to agents. Chromium recreates the original XHR inside the same tab and session while its original body, headers, credentials, username, and password remain internal; the result returns a new sanitized Hronaut request ID for inspection. GET and HEAD replay directly. POST, PUT, PATCH, DELETE, and every other method require a second human click or `confirmSideEffects: true` because replay can repeat writes, purchases, messages, or other side effects. Fetch, document, and non-XHR requests are rejected rather than reconstructed inaccurately. It rejects invalid or non-HTTP requests, removes recognized secret and transport headers, omits incomplete or oversized replay data, and explains the omissions in the result. This is structured redaction rather than data-loss prevention: arbitrary URL paths and body text may still contain private data, so review every copy before sharing or running it. `browser_network_har` exports the filtered current-visit evidence as bounded HAR 1.2 using the captured timing phases instead of placing the whole duration in `wait`, with response provenance, initiators, and payload-free WebSocket and EventSource counts under bounded Hronaut metadata. It removes cookie collections and secret-valued headers, defaults to 100 requests without bodies, caps exports at 200 requests, and includes bounded HTTP text bodies only when explicitly requested. Cached, service-worker, failed, or still-pending requests may omit evidence that Chromium did not expose. Chromium keeps only a bounded diagnostic payload buffer, so old or very large response bodies may be unavailable. Website downloads are tracked through MCP, use collision-safe filenames, and never silently overwrite an existing file.

Use the Search action in the human Network header—or `browser_network_search` through MCP—to find a string across bounded sanitized URLs, errors, headers, request payloads, response bodies, retained WebSocket text, and retained server-sent events. Search covers the 50 most recent requests by default and returns request IDs plus short matching snippets; case-sensitive mode and bounded request, body, and result limits are optional. Queries are literal strings; default matching uses Unicode-aware case-insensitive comparison, and snippets retain offsets in the original sanitized text. Search results set `truncated` when request/result limits omit evidence or when searched body or stream content was clipped or stream messages were dropped; the human search shows its bounded indicator in those cases. Zero matches do not establish absence from omitted content. Unavailable response bodies are counted separately. Mixed (indeterminate) states and custom ARIA controls remain unsupported. Hidden checkpoints require one existing element at authoring time; missing or ambiguous targets are rejected. Exports first assert one matching target before checking visibility, so a missing result element does not automatically satisfy a hidden checkpoint. Visibility reflects rendering, including content-visibility suppression and display:contents descendants; opacity alone does not make a target hidden. Boxless-container traversal is limited to 1,000 nodes and 100 levels; exceeding either limit rejects the checkpoint and asks for a smaller target. Selectors are converted to structural light-DOM selectors; review them before using the exported test.

For MCP, call `browser_repro` with `action: "get"`, then submit `action: "checkpoint"` and `checkpoint: { "context": "<checkpointContext>", "selector": "#result", "condition": "text", "text": "Item created", "reviewed": true }`. The context is bound to the active recording and current navigation/control generation. A stale context requires a fresh read and review. Count-free structured recordings use `formatVersion: 2`; recordings containing count checkpoints use `formatVersion: 3`; expectation steps retain intended conditions separately from `observedMatch`. A false match is useful when recording a bug and never silently changes the expected result. Text comparisons normalize whitespace, like Playwright's string `toHaveText` assertion.

Checked-state MCP example: after reading the current Repro context, submit `action: "checkpoint", checkpoint: { "context": "<checkpointContext>", "selector": "#terms", "condition": "checked", "reviewed": true }` (or `"unchecked"`). Do not include `text`. Exports use `toBeChecked()` or `not.toBeChecked()`; this records an expectation, never toggles the control or infers consent.

Count checkpoints use `condition: "count", count: 0` (or another explicit integer through 500), without `text`. The selector must contain only lowercase tag names, optional `:nth-of-type(N)` with N from 1 through 999999, and canonical ` > ` child combinators, such as `ul > li`. IDs, classes, attributes, other pseudo-classes and selector lists are rejected rather than retained. Counts include hidden matching light-DOM elements and allow zero. Matching form controls, frames or editable elements (including descendants of editable regions) reject the entire checkpoint; ordinary containers containing form controls remain eligible. No values or text are read. More than 500 matches or 2,000 visited document elements rejects the observation without a recorded step or partial result. Exports independently validate version 3 count data and emit `css:light` / `toHaveCount`; malformed count records remain explicit TODOs. Changing the number requires fresh review.

URL-path checkpoints use `condition: "urlPath", path: "/orders/complete", reviewed: true` with the current `context`, without `selector`, `text` or `count`. The human Repro form also offers **URL pathname**. Supply a reviewed serialized pathname of at most 2,048 characters; full URLs, query/fragment delimiters, noncanonical dot segments, whitespace and malformed percent escapes are rejected. Percent-encoded path characters remain encoded. Observation compares Chromium’s current HTTP(S) pathname without executing page JavaScript and rejects current URLs longer than 16,384 characters. The expectation stores only your intended path and `observedMatch`; existing timeline URL redaction remains unchanged. Origin, query and fragment are deliberately ignored, so a match does not establish the site, signed-in account, successful submission or business outcome. Paths can contain private identifiers: review the path and timeline before sharing.

Recordings containing URL-path checkpoints use `formatVersion: 4` and retain support for count and earlier checkpoints. Playwright export uses an HTTP(S) `toHaveURL` predicate comparing `url.pathname` exactly with the reviewed path. Malformed or older-version URL-path records remain explicit TODOs. Like other checkpoints, navigation/control changes require a fresh recording context and review; no waiting, navigation or retry is performed while authoring the checkpoint.

Supported checkpoints export deterministic Playwright assertions. The final recorded step must be a supported checkpoint to omit the final assertion TODO: an earlier checkpoint does not establish the outcome of later actions. Otherwise, add a reviewed final checkpoint or replace the TODO with an expected-result assertion before running the export. Omitted-input placeholders remain required. Unsupported steps remain TODOs. Checkpoints share the existing 200-step bound and volatile retention. The initial Repro startup page read and each checkpoint page read have a five-second deadline once their evaluation starts. A startup timeout leaves no active recording and permits a retry; late startup results cannot replace a newer recording. A checkpoint timeout explicitly rejects the request without adding an expectation, releases the recorder queue for Stop or retry, and ignores late results. It does not cancel page JavaScript, thaw the page, or impose a deadline on other recorder operations. No cleanup actions, network causality, automatic uploads or claims of business-outcome verification are added. Approved expectation text may itself be private: review the timeline and export before sharing.

For a small regression test with an intended text result:

1. Open **Page tools → Repro**, start recording, and reproduce the issue manually.
2. After the last page action, add an **Exact text** checkpoint for one small, unique, non-editable light-DOM result element. Enter the intended result (for example, `Item created`), review the selector and text, and confirm the checkpoint. A current mismatch is useful bug evidence; it does not replace your intended text with the observed failure.
3. Stop recording and choose **Copy Playwright**. Review the recorded URLs and selectors, supply safe test inputs for every named omitted-input environment variable, and resolve any manual-step or completeness TODOs.
4. Run the reviewed test against the broken behavior, then against the fix. A final supported checkpoint replaces only the final assertion TODO; it does not resolve missing inputs, unsupported steps, or a truncated recording. If you record another page action after the checkpoint, add a new reviewed final checkpoint or write the final assertion yourself.

`browser_dom_changes` records the same current-document structural evidence available under **Page tools → DOM changes**. Start it, perform an action, then stop to review which structural targets added or removed nodes, changed an attribute name, or changed text content. Reports contain at most 200 grouped entries and never include page text, markup, attribute values, IDs, classes, form values, clipboard content, or file paths. Cross-origin frames and changes inside existing shadow roots are outside its scope. A full navigation clears the recording because it creates a different DOM; same-document route changes remain observable.

`browser_live_region` records what one selected region contained while an action ran, such as a loading message, a search-result count or an asynchronous status line that is gone by the next snapshot. Call `start` with a `selector` (at most 512 characters) that matches exactly one element in the top-level document's light DOM; the selection is rejected when it matches nothing, more than one element, `html`, `head` or `body`, or a form field, editable region, frame, script or style or anything inside one. Offscreen or visually hidden regions are accepted. The report keeps the region's initial text separately from observations. Each observation is the region's text at one MutationObserver callback, recorded only when its bounded text (the first 1,000 characters) or truncation differs from the previous one, so a change beyond that bound reads as unchanged. It carries `elapsedMs`, the callback's `mutationRecords`, `empty` and `truncated` flags, and the authored `aria-busy` value when present. Changes made synchronously between callbacks are coalesced into one observation; `callbackCount` and `unchangedCallbacks` show how many callbacks ran and how many produced no new text; mutations inside skipped form controls and editable descendants are not counted. Intermediate text is never invented, and observations are not announcement counts. Text is the DOM text of the region with form controls, editable descendants, scripts, styles, frames and shadow roots skipped, so hidden descendants are included. Each read visits at most 2,000 nodes and keeps at most 1,000 characters; a recording keeps at most 100 observations and 50,000 characters in total, handles at most 10,000 callbacks, and lasts at most five minutes. `stopReason` reports `stopped`, `expired`, `detached`, `excluded` (the region later became editable, the document entered design mode, or the region moved into a shadow tree; eligibility is checked again before every read), `observation-limit`, `total-char-limit` or `callback-limit`. `metadata` repeats only authored `role` (alert, log, marquee, progressbar, region, status or timer), `aria-live`, `aria-atomic`, `aria-relevant` and `aria-busy` tokens; it is not computed accessibility semantics or an accessible name. Selected page text can contain private information: it is captured only from the region you select, only while recording, stays in the page's isolated world, and is never persisted, exported or written to diagnostic logs. A full navigation, removal of the selected element, pausing the agent on the tab or a workspace control change stops the recording and releases its text; it never rebinds to a replacement element. Same-document route changes keep recording while the element stays connected, and an active recording keeps its tab awake. `get` is a read; `start`, `stop` and `clear` count as browser-state changes for capability profiles. The structural `browser_dom_changes` recorder stays text-free.

`browser_css_state_preview` forces the CSS `:hover` and/or `:active` state on one element so its hover or pressed styling can be inspected or captured without moving the pointer. `set` takes a `selector` (at most 512 characters) that matches exactly one element in the top-level document's light DOM, other than `html`, `head` or `body`, plus `states` and an optional `durationMs` from 1,000 to 60,000 (default 30,000). Chromium applies the override in Hronaut's own DevTools session: no pointer, click, focus or keyboard events are sent, `document.activeElement` and DOM attributes do not change, and page scripts see only the resulting styles. It is a styling preview, not proof of interaction behavior, disabled semantics or accessibility, and forced rules can still start transitions or animations, load resources they reference or trigger page observers. A tab has at most one preview; a new `set` removes the previous override first. The preview ends when it expires, on `clear`, on a cross-document navigation, when the element is removed or the document is replaced, when the agent is paused on the tab, on a workspace control change, when Developer Tools open or the DevTools session detaches, when the tab closes, and when the person selects the address-bar control that shows the forced states (`Forced :hover`). It never moves to a replacement element, and a `clear`, pause, reset, navigation, workspace control change or Developer Tools opening that arrives while a `set` is still starting cancels that start and rolls back its override. `get` reports `status` (`active`, `inactive` or `reset-uncertain`), the active preview with `remainingMs`, and `lastEnded` with its `reason` and whether removal was confirmed clean. When Hronaut cannot confirm that the override was removed, the preview stays visible as `reset-uncertain` and the next `clear` or address-bar reset retries; reloading the page also drops it. While a preview is active, `browser_screenshot` adds a text item with `cssStatePreview`, and `browser_element_inspect` and `browser_visual_compare` captures add a `cssStatePreview` field, so the rendering is not mistaken for natural page state. CSS provenance and rendered fonts report `debugger-in-use` because collecting them would reset the session's DOM bindings, code coverage cannot start until the preview is cleared, and a preview cannot start while coverage records. An active preview keeps its tab awake. `get` is a read; `set` and `clear` count as browser-state changes for capability profiles.

`browser_visual_compare` exposes the same per-tab Visual compare workflow to an agent. Use `set-baseline`, perform the action under test, then call `compare` to receive changed-pixel metrics and a diff PNG in the same MCP response. `get` returns the current baseline/result and `clear` discards it. The optional 0–255 threshold defaults to 24, while `settleMs` can wait up to two seconds before a capture. For the default whole-viewport baseline, a URL change is allowed and clearly marked; a viewport-size change is rejected so the result remains geometrically meaningful. Captures stay in memory only and remain scoped to the workspace that owns the tab.

To compare one live component while unrelated content changes elsewhere, pass `clip: { x, y, width, height }` only to `set-baseline`. Coordinates are finite viewport CSS pixels, with nonnegative positions and positive dimensions; the rectangle must fit fully inside the viewport and contain at least one complete native bitmap pixel. `compare` reuses the retained rectangle; providing a new clip to `compare`, `get`, or `clear` is rejected. Omit clip on a new baseline to restore the whole-viewport default. No element tracking, exclusion masks or automatic scrolling are performed.

Region captures derive exact CSS viewport extents from trusted viewport bounds and native page zoom, then map into the actual native bitmap dimensions, including display scaling. Partially covered edge pixels are excluded, then the crop is normalized to at most 1920×1080; cropping precedes resizing so neighboring pixels cannot enter the resize filter. `scope` records the requested CSS clip, actual native `bitmapClip`, source dimensions and CSS viewport extent. Snapshot dimensions, `totalPixels`, `changedPixels`, percentages and `diffBounds` describe only the cropped normalized image. The UI labels this coverage and copies only that diff PNG. A zero-change result says nothing about pixels outside the region; cropping is not anonymization.

A region baseline requires unchanged native zoom, device pixel ratio, viewport dimensions, scroll position and top-level document, including same-URL reloads. Incompatible comparisons require a new baseline, and captures invalidated while pending are rejected. Pinch-scaled or offset visual viewports are explicitly unsupported; reset page scale first. The existing whole-viewport cross-navigation behavior is unchanged. Regions retain the same one-baseline/one-diff memory lifecycle and workspace authority as whole-viewport comparisons; no hidden full-viewport duplicate is retained or returned for a scoped result.

It shows the first agent of the workspace in view, in the avatars' order (needs you, working, idle): its avatar, name, state and current step in the same plain words as the card, cut to fit with the whole step in a tooltip, then +N with the other agents' names. **Pause** or **Resume** and **Take over** act on the tab the agent asked about or last used, as in its card, and are disabled while agent control is locked. When the agent needs you, the strip turns amber: a plain request shows its reason with **Hand back**, and a decision shows "Waiting for your decision" in your language, not the request's fixed English line, with **Answer**, which opens its card (as a new card, since pressing Answer closes an open one). Pause is hidden then, since the agent is already waiting. The reason and both answers apply only when the current request is about the workspace in view and, when both name one, the tab the agent asked about, since main sends a new request before it publishes who made it; until then the strip says the agent is asking for help. With no agent in the workspace the strip stays and says so (only once main's presence has arrived, so a remount does not flash it), so pages do not move as agents come and go; Home, Settings and pages outside a workspace have none. In a strip narrower than 640 px the state, unless it is needs you, and the +N give way first, and the agent's name shrinks before the buttons do. The strip is part of the shell, so the page card moves down by the strip's height and keeps its bottom edge, and with the tab rail it starts after the rail like the page. Its chevron unpins it and moves keyboard focus to the agent's avatar, or the address field, unless focus went elsewhere meanwhile; a button that disappears while focused, such as Hand back once answered, hands focus to the strip's next control. The strip reads only the shell's presence snapshot, the attention request the shell already has and the tab list, so it adds no new data channel and no page data; the setting has its own trusted-shell IPC handler that accepts only a boolean.

**Full-page view** (**Ctrl/Cmd+Shift+F** from the shell or the active website, **View → Full-Page View**, or **Toggle full-page view** in the command palette) gives a website the window. The tabs, the tab rail with its title-bar surface, the toolbar and the pinned live strip leave the layout and turn invisible. The shell then reports only a band as tall as the window controls with the page's title, so main places the page card directly under it (main keeps at least 44 px above the page); a hidden rail reports no width, so the page keeps only its 10 px gutter on the left. The rail keeps its vertical layout for when it returns. Resting the pointer on the band, or with the rail on a 10 px strip at the window's left edge, shows everything again after 180 ms, and the page makes room as it would without the view; leaving the chrome hides it 260 ms later. This is the timing of the folding rail. A window blur, such as a click on the page, hides it 400 ms later, so the page does not move between the press and the release. Nothing in the view drags the window: the system takes the pointer over a title-bar drag region away from the shell, which would hide the bars the pointer had just revealed. Leave the view to move the window by its tabs or toolbar. Keyboard focus inside the chrome shows it at once and keeps it shown, so shortcuts such as **Ctrl/Cmd+L** and Tab navigation work as before, and the view keeps the chrome shown when it starts while focus is in it. The chrome also stays shown while an agent needs you (any current attention request), while an agent card is open under its avatar, and while the MCP readiness summary, the update notice, address suggestions, tab search, downloads, history, the split view menu or site controls are open. A bar under the toolbar keeps it shown as well, so the bar does not move under the pointer: Find, Zoom, a page that failed to load, and the renewal notice. It returns with a 140 ms fade, none with reduced motion. The view applies only to a website in the main window: Home, Settings and separate panel windows show the usual chrome, and pages show it again on return. The revealed toolbar adds an **Exit full-page view** button. When the view ends while that button has focus, by the button, the keys, the menu or the palette, focus moves to the active tab, or to the address field. The view is kept for the current launch only and changes no setting. Like Hronaut's other shortcuts, the key no longer reaches the website. While you pick an element or capture an area, the website's keys go to that instead, so press the keys in the shell or after **Escape**.

**Take over from an agent.** When you click or press a key in a page while an agent in its workspace is working on that tab (its latest call used the tab, within the working state's 10-second grace), main offers a take over to the shell, and the toolbar shows **Take over from <agent>?** with **Take over** and a dismiss button at the start of the commands. It is never drawn over the page and only takes room the toolbar has to spare: on the address field's row, the space around a field at its widest (520 px); when the commands have their own row, the space before them. The prompt measures unseen copies of itself with and without its words and shows the largest that fits, so the address field keeps its width and the toolbar its height. With no room for even the buttons, the agent's avatar gets a hand badge whose tooltip names the shortcut (or, once you have the tab, says to resume the agent to hand it back), and the status message still announces the offer. Wheel and touch scrolling, the browser's own shortcuts and input an agent sends do not offer it; an agent's own **Ctrl/Cmd+Shift+O**, such as for a web app's command, reaches the page and never takes over. The offer lasts 8 seconds from your latest click or key press, and only while the same agent is still working on that tab, the tab is not paused, and agent control is not locked; main tells the shell at most once a second while you keep typing. The dismiss button hides the offer and keeps that agent's offers for the tab away while it goes on working there, so you can keep typing. **Take over**, or **Ctrl/Cmd+Shift+O** pressed in the shell while an agent is working on the tab in view or in a page an agent is working on, even before an offer appears, pauses agents on that tab (from a page, the tab you pressed it in), as **Pause agents** does, and records the take over; **Take over** in the agent card and the live strip records it too. The website keeps **Ctrl/Cmd+Shift+O** while no agent is working on its tab or the tab is paused. While you have the tab, the toolbar shows **You have control** with **Hand back to <agent>**, naming the agent that last used the tab, or **Hand back** once it has left or when only the button fits. An agent's call that targets the tab fails with "Agents are paused for this tab: the person took it over in the Hronaut window and has control…", which says that `browser_tabs` will show the hand back; while all agents are paused it gets the general pause message instead, and other tabs are unaffected. Any resume of the tab hands it back: the button, **Resume agents** on the page controls, the agent card or the live strip, turning global pause off when that leaves the tab running, or telling an agent you finished what it asked of you on that tab (**Done, hand back** in its card, **Hand back** in the live strip, or **Mark as resolved**). Main then sets the tab's `handedBack` to `{ at, note }`, a plain English note of how long you had the tab, whether its address changed (both addresses, without sign-in details, secret-looking query values or the fragment, as in network details, and each cut at 200 characters) or it reloaded or navigated back to the same address, whether you clicked or typed in it, and that the agent should read the page again. It never includes what you typed, field values or page text. A taken-over tab carries `takenOverAt` in epoch milliseconds, and a new take over clears the previous `handedBack`. Both are kept in memory for the current launch only; the tab's pause is saved like any per-tab pause, so after a restart it is a plain pause. In the full-page view the band shows the offer in place of the page's title. Screen readers hear the offer and "You have control" through a status message, and the **Take over** button announces its shortcut.

`browser_resize` applies a persistent per-tab desktop viewport override for responsive testing and can reset it without resizing the application window. `browser_emulate` adds isolated network, HTTP-cache, service-worker, Data Saver, CPU, animation-playback, JavaScript execution, CSS media, vision, locale, time-zone, user-agent, mobile/touch viewport, geolocation, extra-request-header conditions, and optional Chromium rendering-debug overlays to one tab. Agents can select `compact-phone`, `phone`, `large-phone`, `tablet`, `laptop`, or `desktop` with `viewportPreset` plus an optional `viewportOrientation`, or continue supplying exact raw `viewport` metrics. Preset and raw viewport inputs cannot be combined. Set `safeAreaInsets` to integer CSS pixels from 0 to 1000 for any of `top`, `left`, `bottom`, `right` and their `topMax`, `leftMax`, `bottomMax`, `rightMax` counterparts to override `env(safe-area-inset-*)` and `env(safe-area-max-inset-*)` for notch and home-indicator layout QA. Each call replaces the whole override, and omitted fields resolve to `0px` like an unemulated desktop tab, so `env()` fallbacks do not apply. It does not draw a device frame or notch. Set `osTextScale` from `0.85` to `2` to emulate the operating-system text-size preference in one tab without changing system settings. Only pages that opt in with `<meta name="text-scale" content="scale">` or read `env(preferred-text-scale)` respond, so many sites will not change; it is separate from page zoom. `null` or `reset: true` removes the override and returns the tab to the browser's own preference. Validated on Linux, where that preference is 100%. Set `smallViewportHeightDifference` to an integer from 0 to 1000 CSS pixels to emulate mobile browser controls for `svh`/`lvh` layout QA: `100lvh` becomes that much taller than `100svh`, as in a phone browser showing its address bar. With a mobile `viewport` the small viewport shrinks below the emulated height; in a desktop-size tab the visible viewport stays the small viewport and the large viewport grows. It applies to the top-level frame only, must be smaller than an emulated viewport height (a later viewport change that would break this is rejected), and does not emulate `dvh` changes, scrolling or address-bar animation. `0` matches a clean desktop tab; `null` or `reset: true` removes it. Set `cacheDisabled` or `bypassServiceWorker` to `true` for a cold-network or no-worker reproduction and back to `false` to restore normal request handling; neither control clears storage or unregisters a worker. Set `dataSaver` to `enabled` or `disabled`, and use `auto` to restore the system value without changing network throttling. Set `animationPlaybackRate` to `0`, `0.1`, `0.25`, or `1` to pause, slow, or restore document-timeline motion without changing `prefers-reduced-motion`. Pass a partial `renderingDebug` object to merge overlay choices or `null` to clear all five. Use an empty string to clear only `locale`, `timezoneId`, or `userAgent`; set `javaScriptDisabled` to `false` to restore page scripts; use `null` to clear only `viewport`, `geolocation`, `safeAreaInsets`, `osTextScale` or `smallViewportHeightDifference`; use an empty object to clear `extraHttpHeaders`; omit overrides to inspect state; or use `reset: true` to restore every normal condition. Locale accepts a BCP 47 tag such as `fr-CA`; time zone accepts an IANA ID such as `America/Toronto`. Request-header values are intentionally redacted from returned state. After a submitted emulation command fails or its document/debugger context changes, retained settings are not proof of native application. A read returns `{ application: "pending" | "unknown", retainedSettings, recovery: "restore-committed" }`; tab and debug-report projections expose this as `emulationState` and omit the applied `emulation` field. New edits and reset are blocked while unknown. Use `recover: true` alone to explicitly restore the last fully committed configuration, including unrelated viewport and private header settings; recovery never replays the failed request or applies a UI draft. A failed restoration remains unknown. Network application health is separate: if unknown, first explicitly clear request conditions, then restore emulation. No background debugger attachment repairs either state. Ordinary completed navigation preserves acknowledged emulation; navigation during an operation invalidates that operation, and renderer loss or debugger detach makes application unknown until explicit restoration. A later queued change can supersede an acknowledged operation before its MCP response is published; inspect current health rather than replaying that operation. The Environment panel and address bar show uncertainty. Native right-click, wheel, key hold, comparison metadata, and bounded full-page preview require confirmed emulation. Humans can manage Network, HTTP cache, service-worker bypass, Data Saver, CPU, animation playback, JavaScript-disabled startup, rendering diagnostics, screen or print media, color scheme, forced colors, contrast, motion, transparency, vision-deficiency simulation, locale, time zone, user-agent, and geolocation through **Page tools → Environment**, then apply live or reload without cache. Environment displays a separately managed viewport and agent-set header names, preserves both when applying or resetting its own controls, and never exposes header values. Reload after changing locale because the current document's navigator language does not change immediately. Disabling page JavaScript does not disable the trusted Environment panel or MCP command that restores it, but page evaluation and site interactions can remain unavailable until execution is enabled again. These rendering conditions reproduce browser signals and visual effects, but do not replace manual testing with assistive technology or a person who has the relevant vision deficiency. Throttling is relative to the current computer and cannot reproduce a physical device architecture or real-world radio conditions. `browser_zoom` changes real page zoom from 50% to 400% without scaling the Hronaut toolbar or Settings. The toolbar and zoom shortcuts reach 400%; reset returns to 100%. This supports manual reflow QA, not an automatic accessibility verdict. Measure the page viewport when comparing CSS-pixel breakpoints, rather than assuming it matches the outer window. Chromium can share zoom between same-origin pages in one workspace; separate workspace sessions remain isolated. To compare zoom levels side by side in one workspace, create a tab with `browser_new_tab` and `zoomIsolated: true`. That tab starts at 100% regardless of the origin's shared level. Its zoom does not affect other same-origin tabs, and their zoom does not affect it. Isolation survives navigation and reload, and duplicating, reopening a closed tab or restarting the app keeps it; tabs reopened from a saved workspace use shared zoom. It is set only at creation and cannot be switched back to shared; close the tab instead. The zoom bar shows **This tab only** for an isolated tab, tab state reports `zoomIsolated: true`, and performance comparisons treat isolated and shared zoom as different conditions. Older Hronaut versions ignore the saved flag and reopen such tabs with shared zoom. For accessibility QA with a larger browser text preference, pass `defaultFontSize` (an integer from 9 to 72 CSS pixels; the browser default is 16) to `browser_new_tab`. It sets Chromium's standard default font size for that tab only, through the tab's native WebContents preferences: text sized by the browser default, `em` and `rem` units and font-relative media queries such as `(min-width: 40em)` follow it, while authored pixel sizes, the monospace default and the minimum font size do not change. This is different from page zoom, which scales everything, from `osTextScale`, which only affects pages that opt in, and from injecting a root `font-size` declaration, which leaves media queries at the browser default. The size is set only at creation; open another tab for another size. Navigation, reload, screenshots, sleep and wake, duplicating, reopening a closed tab and restarting Hronaut keep it; tabs opened by the page and tabs reopened from a saved workspace use the default, as with `zoomIsolated`. Tab state, the zoom bar (**Default text 32px**) and performance environments report a non-default size as `defaultFontSize`; 16 is not recorded. Values outside the range are rejected before any tab is created. It does not change operating-system settings or claim accessibility compliance. `browser_audio` mutes one tab without changing site-wide sound permissions. `browser_bookmarks` lists, adds, renames, removes, or opens locally saved pages. The human **Bookmarks → Edit address** action changes one saved destination by ID while preserving its title and creation time. It accepts HTTP(S) URLs using the existing normalization and credential-stripping rules, rejects an address already saved under another ID, and retains the previous bookmark if persistence fails. Escape cancels the draft; a failed save keeps it available for correction. Destination editing is a human UI action and does not add an MCP mutation. `browser_visit_history` searches, reopens, removes, or clears the bounded local visit log. The human History panel can filter the latest `visitedAt` of each retained URL by **Today**, **Last 7 days**, or **All**, together with title/address search. Dates use the computer’s local calendar, matching the displayed visit time; website timezone emulation does not affect this filter. Today starts at local midnight; Last 7 days includes today and the six preceding calendar dates, including daylight-saving transitions. Date filters exclude later calendar days. The panel refreshes its boundaries at midnight, on focus/visibility changes, and within a minute of clock or timezone changes while open. All retains the existing list; the selection persists only for the current application session. **Filter by exact origin** on a History row restricts the list to its HTTP(S) `URL.origin` (scheme, hostname, and effective port), together with the text and date filters. It does not match a hostname mentioned only in another address or title, subdomains, a different scheme, or a different port. The visible origin filter can be cleared even when no visits match; it survives panel close/reopen only for the current application session. **Clear all** always clears the entire retained history, even with filters active. Storage, retention, visit counts, and the flat MCP contract are unchanged. `browser_site_data` inspects one explicit HTTP(S) origin or clears selected `cookies-and-storage`, `cache`, and `history` categories for that origin so agents can reproduce clean-session bugs. It cannot clear the whole profile, does not reload open pages, and never removes bookmarks, passwords, permissions, downloads, or settings. `browser_fill_form` updates several inputs, text areas, selects, checkboxes, radios, or editable elements in one call.

`browser_dialog` accepts or dismisses an already-open JavaScript `alert` or `confirm` dialog. An agent that knows a click or evaluation will open one can instead provide `dialogAction` directly to `browser_click` or `browser_evaluate`. For a website click that opens `window.prompt()`, `browser_click` also accepts `promptText` together with `dialogAction: "accept"`; invalid or dismissing prompt-text combinations fail before clicking. Hronaut responds inside the same operation so the page cannot deadlock the tool call. Electron does not implement native prompts, so Hronaut installs a prompt response only around that explicit click; all other dialogs remain native and user-visible.

`browser_webmcp` makes Hronaut an MCP-to-WebMCP consumer bridge; it does not make Hronaut's local MCP server available to page JavaScript and does not add WebMCP to a website. The tool is available in Web QA and Complete profiles, but not Browser Essentials. `status` feature-detects the browser-native `document.modelContext` API, `list` returns bounded tools registered by the selected top-level HTTP(S) document, and `call` requires the exact workspace tab, origin, navigation generation, descriptor digest, name, and arguments from that listing. Same-origin iframe tools are deliberately excluded. A call re-lists the tools immediately before dispatch, rejects descriptor or schema drift, treats page descriptions, annotations, errors, and results as untrusted content, and remains classified as open-world and potentially destructive even when the page labels a tool read-only. Its returned value and fresh bounded page snapshot separate dispatch from observation; neither proves that an external side effect succeeded. Hronaut enables Electron's native experimental WebMCP implementation without injecting a polyfill, and an explicit Chromium `--disable-features=WebMCP` policy keeps it unavailable.

## Security model

- The MCP server binds to loopback by default and rejects non-local browser origins.
- MCP authentication is off for new profiles and remote access defaults off. Remote access takes effect after restart and listens on all IPv4 interfaces. Authentication is independently configurable and changes immediately. Without authentication, anyone who can reach the listener can control the profile. Resetting MCP settings disables authentication immediately and remote access after restart. Enable **Require MCP authentication** in **Settings → MCP security** when local processes are not equally trusted; Hronaut then generates and reuses an owner-only token unless a valid `HRONAUT_MCP_TOKEN` override is supplied.
- Website tabs have Node.js disabled, context isolation enabled, Chromium sandboxing enabled, and web security enabled.
- New browser windows become managed tabs.
- Unknown site permission requests require explicit confirmation. Hronaut remembers each decision per website origin and permission type, and lets you review or revoke it later in Settings.
- Camera, microphone, and file-system grants are never reused: Hronaut shows the requested scope and asks again each time.
- `browser_evaluate` is intentionally powerful: only connect trusted AI clients to this browser profile.
- Saved passwords use OS-backed encryption and can only be filled by a human from the Hronaut toolbar. Filling pauses MCP first because any password placed into a page can otherwise be read by page JavaScript or a trusted client using `browser_evaluate`.
- `browser_network_request` can return API request and response content plus sanitized WebSocket text messages and EventSource events to an authenticated client. It redacts named security headers and structured secret fields, bounds text, and omits binary or multipart payloads, but it is a debugging aid rather than a data-loss-prevention boundary. Only connect clients you trust with the visible browser session.
- `browser_network_replay` can repeat a retained XHR with the original in-session credentials, headers, and body. It does not expose those values, rejects non-XHR requests, and requires explicit side-effect confirmation outside GET/HEAD, but a confirmed replay can still repeat a real write or purchase.
- `browser_network_search` examines the same bounded sanitized evidence and returns short neighboring text around matches. Arbitrary response text may still contain private data, so review results and connect only clients you trust.
- `browser_network_wait` evaluates URL patterns against the live request address but returns only the same sanitized lightweight metadata as `browser_network`; it does not return headers or bodies.
- `browser_storage_changes` omits values by default, never returns HttpOnly cookie values, caps snapshots and returned values, and clears its volatile baseline when the selected tab changes origin. Opt-in values can still contain page data, so request them only from a trusted client when needed.
- `browser_indexeddb` is read-only, bounds database, schema, key, and record collections, redacts recognized secret URL fields, and omits record values by default. Website-authored schema names, keys, and opt-in previews can still contain arbitrary private application data, so request and share them only through a trusted client.
- `browser_storage_usage` is read-only and returns aggregate byte counts only. Quota is a point-in-time Chromium estimate rather than device free space, and third-party or partitioned storage can have separate accounting.
- `browser_pwa` is read-only, never returns cached response bodies, omits headers by default, and bounds worker/cache collections and names. Registration scopes, script URLs, cache names, request paths, and opt-in headers remain website-authored debugging data, so review them before sharing beyond a trusted client.
- `browser_element_inspect` excludes form values, inline event handlers, page markup, arbitrary DOM properties, and complete stylesheet bodies. Only explicit `cssProperties` requests add bounded declaration candidates; its selector, allowlisted attributes, visible text, and accessible name can still contain page-authored private data.
- `browser_generate_locator` excludes form values, page markup, arbitrary DOM properties, and stylesheet source, but the returned semantic name, test ID, or CSS selector can still contain page-authored private data.
- `browser_network_routes` can replace or fail website requests in the selected tab. Routes are visible, bounded, temporary, and human-resettable, but a trusted client can still alter what that page receives while they are active.
- Accessibility audits execute the bundled axe-core rules inside the selected website and return bounded selectors and failure summaries. They do not send page content to a third party, but selectors and page addresses still reach the authenticated MCP client.
- Performance reports execute the bundled `web-vitals` collector locally in an isolated world and return aggregate timings, sizes, and bounded element selectors without resource URLs or markup. Page addresses and metric target selectors still reach the authenticated MCP client.
- Debug reports exclude request headers and bodies and filter sensitive URL fields. Page-authored console messages, exception text, and function names receive best-effort filtering but can contain arbitrary text, so review copied reports before sharing them beyond a trusted MCP client.
- Browser Issues expose normalized Chromium reason codes and bounded affected URLs, never raw issue payloads or cookie values. Review copied diagnostics before sharing them outside a trusted agent session.
- `browser_file_upload` can attach any absolute local file path supplied by a connected client. Only connect clients you trust with local file access.

## Local Web3 wallets

Available since Hronaut 2.4.21, the local-wallet preview supports EVM, Solana, and Tron. Preview means the provider and automation surface may evolve; the feature is included in published builds. Hronaut can generate or import managed wallets, add watch-only addresses, and create dedicated agent wallets. Managed signing material stays in the trusted Electron main process inside an authenticated encrypted vault; websites and MCP clients refer to public wallet IDs and can request scoped access, simulation, signing, submission, status, or cancellation without receiving private keys or recovery phrases.

Wallet access is scoped to the wallet, workspace, top-level origin, account, network, requester, and capability. Mainnet defaults to explicit human approval in trusted Hronaut chrome. A dedicated EVM agent wallet may use a user-created, short-lived **Bypass Approve** policy that binds one exact workspace, network, origin, destination, and method, plus the token contract for a token call, with complete amount, spend, fee, simulation, operation-count, and expiry limits. Websites and all requests outside that delegation still require a person, except that a separate, default-off sign-in switch on a bounded policy lets one exact website origin connect the wallet and get Sign-In with Ethereum messages that name that site, address and chain signed without a click on eligible EVM testnets and loopback local chains (other plain-text `personal_sign` messages only on a dedicated agent wallet); a second, separately warned switch extends that to a dedicated EVM mainnet agent wallet with one origin, at most 100 operations and a seven-day expiry. Other bounded automatic approval is limited to allowlisted EVM testnet chain IDs or known loopback local chains; configured, requested, and RPC-reported chain IDs must agree, but this is not independent proof of endpoint honesty. It fails closed for undecodable requests, unsuccessful simulation, policy-limit violations, or changed approval data. Hronaut does not integrate WalletConnect, Reown, or external-wallet SDKs in this iteration. See the [wallet security and usage reference](docs/WALLETS.md) for supported provider methods, onboarding and recovery, Linux secret-store behavior, policy limits, RPC configuration, revocation, testing, and the exact threat boundary. The [watch-only public-address wallet QA recipe](docs/WATCH_ONLY_WALLET_QA.md) verifies read-only observation without importing signing material; the separate [local EVM wallet QA quickstart](docs/WALLET_QA_QUICKSTART.md) provides a disposable signing first run with independent receipt readback. The [external-wallet and mobile dApp QA boundary](docs/EXTERNAL_WALLET_QA_BOUNDARIES.md) separates those Hronaut-local checks from extension, WalletConnect, proprietary SDK, and mobile-wallet suites.

## Testing

Unit tests live in `tests/*.test.ts` and use Vitest. Real-application integration tests live in `tests/integration/*.e2e.ts` and use Playwright's Electron API with reusable fixtures from `tests/integration/fixtures.ts`. Every integration test launches Hronaut with an isolated temporary profile and cleans it up afterward. The suite covers the visible shell, tabs, MCP, Home, themes, site permissions, restart persistence, and updater settings without contacting the live release feed. Application, test, preload, website, and build configuration source is TypeScript.

Run `npm run evaluate:browser:docker` for the opt-in local browser-boundary evaluation. It launches Hronaut in Docker against loopback-only synthetic pages and exercises navigation and reconnect drift, expired authentication, an unattended human-review expiry, a flaky read, and a possible write followed by ambiguous browser state and independent fixture read-back. The command writes `test-results/browser-evaluation/report.json`; use `-- --output <repository-relative-path>` to choose another location. The deterministic report records pinned fixture, client, and Hronaut versions; stable logical task and action-attempt identities; fixed context roles; capability and approval transitions; tool, dispatch, transport, postcondition, and final reconciliation states. Its closed schema cannot carry raw URLs, selectors, page content, cookies, credentials, resume keys, MCP tokens, or live account identifiers. These disposable scenarios evaluate failure handling and do not establish production correctness.

Run `npm run example:scheduled-browser-task:docker` for the same real-Electron
fixture with its report written to
`test-results/scheduled-browser-task/report.json`. The report also records the
external scheduler, calling agent, Hronaut, and target-system ownership boundary;
stable synthetic trigger, task, session, and action-attempt identities; and a
cancellation-before-dispatch case. The complete orchestration, cancellation,
reconnect, retry, and receipt interpretation is in the
[scheduled browser workflow](SCHEDULED_BROWSER_WORKFLOW.md).

## Releases

GitHub Actions validates every pull request and every push to `main`. When `package.json` changes to a new version on `main`, the auto-tag workflow creates an annotated `v<version>` tag and dispatches the release workflow. A tag is created only when the version differs from the parent commit.

The release workflow creates one draft release, builds Linux, macOS, and Windows artifacts in parallel from the immutable tag commit, uploads the updater manifests and a `hashes.txt` SHA-256 manifest, and publishes only after every platform job succeeds. Uploads are reconciled one at a time against the draft by filename, uploaded state, size, and GitHub's SHA-256 digest. A failed response is read back before any replay, verified assets are preserved, transient retries are bounded, and invalid requests or authorization failures stop without retrying. If the attempt budget is exhausted, fix any reported nonretryable error and rerun the failed release job: the same draft is the resume point and already verified assets are skipped. The workflow refuses conflicting, unexpected, or already-public assets rather than replacing them. Packaged Hronaut builds use those manifests through `electron-updater`. After public download routes are verified, the workflow updates the matching Scoop manifest from the published Windows portable checksum and dispatches full CI plus the Windows Scoop install/reinstall smoke. It skips that write if `main` has already advanced to another package version. The workflow can also be dispatched manually for an existing version tag.

Current releases are unsigned community builds: the binaries are not platform code-signed and macOS packages are not Apple-notarized. macOS Gatekeeper and Windows SmartScreen may therefore warn before first launch. Build jobs never receive release-write credentials; the final job publishes the completed set and generates GitHub artifact attestations. Verify a downloaded asset with `gh attestation verify <asset> -R hronaut/hronaut`, then compare it with `hashes.txt`.

Dependabot checks npm packages and GitHub Actions weekly and groups related Electron, Vue/Vite, MCP, and TypeScript updates. The Cloudflare Pages storefront deploys independently from the desktop release workflow in `hronaut-page`.


## Record product walkthroughs

Open **Page tools → Video recorder**, or use `browser_video` in any MCP tool set.
Recording is explicitly started for a specific HTTP(S) tab, including a background tab. It captures page
pixels (including any personal data on screen), without browser chrome or audio.
Use a demo account and review the result before sharing. Nothing is uploaded.

The first version captures up to 12 frames per second, fitting the viewport
inside 1280 × 720 without upscaling. Each recording is limited to two minutes and
64 MiB of JPEG frames; at most three recordings are retained and may capture
concurrently. Each recording keeps its original tab and workspace. Video control calls do not
trigger Follow agent; other tools retain their normal follow behavior without
retargeting the recording. Separate authorized agents can record separate
workspaces while the human uses another tab. Raw frames and rendered previews stay in memory and disappear
on discard, tab closure, workspace closure/archive, or application exit. Explicit
exports remain in the configured download directory with collision-safe filenames.

Keep Hronaut visible and each recording viewport at a fixed size. The source tab
need not be selected. Background frames reuse the existing per-tab rendering
surface and queue; this remains bounded sampled video, not a guaranteed frame rate.
Same-origin navigation is supported; a frame spanning a navigation is discarded.
Resizing, loss of access, a hidden/minimized Hronaut window, trusted UI occlusion,
a held/sleeping page, or an unavailable renderer pauses capture. Active recordings
are protected from Memory Saver. System suspend pauses them without automatic
resume; recording during OS sleep is unsupported. A gap of more than three seconds
without usable frames pauses and trims the unsampled tail, rather than claiming
a healthy frozen video. Return
to the original origin and restore the viewport before resuming. Pause time is
excluded from the timeline. When agent control or its write lease changes, resume
requires a fresh authorized call. Explicit MCP session termination revokes its
recording authority. Merely closing an HTTP client locally or losing network
connectivity is not an observable session termination; a previously authorized
recording can continue within its two-minute limit until stopped or revoked.
Reading or exporting retained content requires
the original tab, workspace and origin. Website content has no access to the
recorder or encoder bridge.

`browser_video` accepts `workspaceId`, `tabId`, and one of:

- `start`, `pause`, `resume`, `stop`, `get`, `clear`: recording controls. Starting
  again requires clearing the old recording first. `get` returns bounded metadata.
- `edit`: after stopping, replace `annotations` and/or `clips`. Omitted arrays are
  preserved; `annotations: []` removes overlays. Annotation kinds are `text`,
  `callout`, `arrow`, `highlight`, `spotlight`, and `click`. Each uses source
  `startMs`/`endMs` and an optional hex accent `color`. Text and callouts require
  `text` (240 characters maximum). Arrows, highlights, spotlights and click markers
  require normalized viewport `x`/`y` (0–1). Arrows, regions and callouts also
  require `endX`/`endY`: the pointer target for a callout, or the opposite corner
  for a highlight/spotlight. Regions must have non-zero width and height.
- `inspect`: read a stopped, nonempty recording without capturing again. Supply its
  `recordingId`, `expectedRevision` from `timing.revision`, an inclusive source-time
  `startMs`/`endMs` interval within its duration, and `maxFrames` (1–12). The response
  contains one numbered PNG and metadata with actual source frame sequences/times,
  retained/selected/omitted counts. An empty interval returns metadata only. For N
  eligible frames and K selected frames, selection uses `floor(i*(N-1)/(K-1))`;
  K=1 selects `floor((N-1)/2)`. Narrow the interval to inspect a retained state omitted
  from a broad sample. This is not evenly spaced time sampling or proof that a flash
  was absent. Pause time, capture gaps and unknown exact pixel time remain unchanged.
  The sheet uses original source pixels, without clips, annotations, camera effects
  or audio; existing recording, preview and exports are unchanged. It is transient,
  not a new saved pixel store. Every call requires current capability/control and
  access to the recording's stored tab, workspace and origin, checked again after
  final MCP settlement. Capture permission does not grant permanent read access.
  Clear/new/edit/close, origin/workspace changes, cancellation and authority loss
  invalidate an in-flight result.

  Operational limits: at most 12 selected JPEGs, 4 MiB per JPEG and **8 MiB aggregate
  selected bytes**, intrinsic dimensions at most 1280×720, output at most 2048×2048,
  and returned PNG at most 4 MiB (checked before arrayBuffer/base64/IPC). Frames are
  decoded sequentially and their decoded dimensions checked before drawing. One
  inspection runs at a time with no queue. A five-second deadline initiates rejection
  and teardown; the slot and selected-frame references remain held until renderer
  exit is confirmed. Uncertain cleanup quarantines inspection until Hronaut restarts.
  These are operational bounds, **not a hard RSS/64 MiB memory limit, an encoder
  allocation cap, or a guarantee of exact native interruption latency**. Oversized
  selections/images fail explicitly; request fewer frames or a narrower interval.
- `render`: prepare a local preview without writing a file.
- `export`: render if necessary and save a `.webm` file with optional composed Opus audio. Returns its path,
  filename, bytes, codec, MIME type and edited duration. This action requires the
  capability's `external-request` operation class as well as workspace write access.

### Video timing observations

Recording responses include optional `timing` metadata. Older consumers can
continue using `durationMs`; idle/cleared states have no timing observation.
Pair every observation with the response's `recordingId`:

- `clock: "recording-monotonic"` means milliseconds since this recording was
  created, measured in the main process. `observedAtMs` includes explicit pause
  time; it is neither Unix time nor the caller's clock. `sourceTimeMs` is the
  response's `durationMs`, sampled at that same instant, with paused time excluded.
- `revision` changes on pause, resume, stop, interruption recovery and successful
  timeline edits. Recheck identity/revision before using a prior observation or
  derived output mapping. Clear/start creates a new recording identity and clock.
- Optional `lastFrame` describes only the latest retained frame: its one-based
  `sequence`, source timestamp, capture-attempt `captureStartedAtMs` and
  `captureCompletedAtMs`, and the revision under which it was captured. Its
  revision can be older than the current observation after pause/resume or edits.
  Bounds use the same recording clock and include asynchronous capture work.
  They do not prove when Chromium presented or sampled the pixels;
  `pixelTime: "unknown"` states that limitation explicitly. No last frame is
  reported until one is retained, and dropped/late frames do not advance it.

Source zero remains the first retained frame's timestamp. Later frames retain
capture-attempt source timestamps. This metadata does not change frame placement,
recover missing frames or promise precise event-to-pixel alignment. A response is
already historical when received: bracket calls with a caller-local monotonic
clock to bound round-trip transport uncertainty, but do not subtract timestamps
from unrelated clocks or extrapolate through a revision change. Even within one
revision, sparse capture can leave a substantial gap between source time and the
last retained frame. Re-observe after pause/resume or interruption: stale-tail
recovery can shorten source duration and invalidate a previously observed moment.

Observations stay on the source timeline after edits; they are not output-time
anchors. For a moment inside a retained clip, output time is the sum of preceding
clip lengths plus its offset within that clip. A trimmed-out moment has no output
time. Existing origin/workspace access checks and memory-only retention apply;
no pixel bytes, captured text, persistent markers or wall-clock history are added.

Up to 100 annotations and 30 kept ranges are supported. Clip ranges are ordered,
non-overlapping source `startMs`/`endMs` pairs. With no clip edits, the whole
recording is kept. Overlay times refer to original footage, so trimming preserves
alignment. Coordinates refer to the captured viewport; arrows do not automatically
track moving elements. Agents can use snapshots/screenshots to choose positions.
Edit layers remain separate from the captured pixels until rendering, allowing
wording and timing changes without repeating the demonstration.

Text cards use readable neutral text, rounded surfaces, padding and a separate
accent, with word wrapping and safe margins. Agents can control their placement:

- `placement`: `top-left`, `top-center`, `top-right`, `center-left`, `center-right`,
  `bottom-left`, `bottom-center`, or `bottom-right`. No coordinates are needed.
- `placement: "custom"` with `x`/`y` puts the card's top-left corner at that
  normalized position. The whole card is clamped inside the safe margins.
  Existing text annotations with `x`/`y` and no placement keep custom positioning.
- `placement: "auto"` (or omitted coordinates) puts text at bottom-center and
  callouts on the opposite side from their target. This is geometric placement;
  inspect the page to avoid covering important controls.
- `width` limits the card to 0.15–0.9 of the viewport width. Defaults are 0.56 for
  captions, 0.7 for titles, 0.34 for labels and 0.3 for callouts. Short text cards
  shrink to their content. Long copy wraps, with ellipsis if the frame cannot fit
  it; keep each instruction brief.
- `preset`: `caption`, `title`, or `label`; `size`: `small`, `medium`, or `large`;
  `theme`: `dark` or `light`; `align`: `left`, `center`, or `right` within the card,
  independently of its position. `textColor` optionally
  overrides the contrasting default; `color` styles accents and pointers.
- Callouts support an optional `title` (80 characters) and `step` (1–99).
  A spotlight dims the page outside a rounded rectangle; annotations remain above
  the dimmed layer, regardless of array order.
- `animation`: `fade` (default), `none`, or `draw`. Entrances/exits are short;
  `draw` additionally reveals arrows and pulses click markers. `curvature` from
  -1 to 1 controls arrow bending; zero is straight. Animations use source time,
  so trimming does not shift their relationship to the recording.

Use one main instruction per step. Put captions in empty space using anchors or
custom coordinates, and use a callout or spotlight to show the target. Point to
the edge of a control to keep its label readable. The Page tools editor includes
style and positioning controls.

Example `edit` arguments after recording at least three seconds:

```json
{
  "workspaceId": "<your workspace ID>",
  "tabId": "<your tab ID>",
  "action": "edit",
  "clips": [{ "startMs": 0, "endMs": 3000 }],
  "annotations": [
    { "kind": "text", "preset": "caption", "text": "Your project is ready for the next step.", "placement": "bottom-center", "width": 0.55, "startMs": 0, "endMs": 3000 },
    { "kind": "callout", "title": "Invite your team", "step": 2, "text": "Choose Send invite to add a teammate.", "placement": "center-left", "width": 0.3, "endX": 0.75, "endY": 0.6, "startMs": 500, "endMs": 3000 },
    { "kind": "spotlight", "x": 0.65, "y": 0.5, "endX": 0.9, "endY": 0.7, "startMs": 500, "endMs": 3000 }
  ]
}
```

Exports use WebM with VP9 and an opaque background. This targets current Chrome,
Edge, Firefox and Safari, including Safari 17.4+ on iOS/iPadOS and Safari 14.1+ on
macOS ([WebKit compatibility notes](https://webkit.org/blog/15063/webkit-features-in-safari-17-4/)).
WebM is not a universal native-player/editor format; MP4/H.264 conversion is not
included. The bundled WebCodecs encoder is checked at export time. Unsupported
encoding reports an error while preserving the raw recording for review/retry.

### Human-reviewed local incident package

Open **Page tools → Create debug report → Reviewed incident package**. Explicitly select Repro steps, sanitized network entries, and/or console diagnostics, then capture a recent 1–60 minute window. This first increment exports one self-contained HTML file for offline reading, not a runnable application or ZIP archive. It uses existing retained evidence and redaction; request/response bodies, cookies, profiles, screenshots, receipt collection and replay are excluded. Missing historical data cannot be reconstructed. Use the [incident handoff checklist and companion-note example](docs/INCIDENT_HANDOFF.md) to supply reviewed startup/reset instructions, safe replacement inputs and a bounded observation condition when needed.

Incident review also supports up to 10 artifact-scoped literal property paths, entered as JSON arrays such as `["console", 0, "message"]`. Each path has 1–16 segments; strings select exact own object keys (up to 256 characters), numbers traverse existing array indexes, and the serialized UTF-8 path is limited to 4 KiB. Only object properties can be removed, never the root or an array element; array positions stay stable. All paths must match the frozen sanitized source in included artifacts. Duplicate or overlapping paths, missing fields and unavailable artifacts reject the review. Paths are resolved before global field omissions, ordered text replacements and redaction. The manifest records only artifact kinds and removal counts, not path tokens or removed values. Editing rules retires the old preview in both the shell and main process; every invalid review request also retires the owner's prior preview. Saving still writes only the exact approved preview bytes, including checks after the native dialog and before file commit. Other copies of omitted information may remain; review the complete preview.


The trusted main process freezes the selected sources. Choose which captured artifacts to keep, optionally omit an exact JSON field name, remove an artifact-scoped property by literal path, or apply literal text replacement, and preview the exact package. Global field-name omission is case-sensitive and recursively removes matching object properties from kept artifacts before replacement; unlike artifact-scoped literal paths, it does not interpret paths, wildcards or array indexes. For example, `url` removes fields named `url`, not copies embedded in messages or fields named `URL`. The UI and typed review contract accept up to ten distinct names (1–256 characters each). Add or remove omission rows in the editor; empty and repeated UI entries are ignored, while case and whitespace in nonempty names remain exact. Editing, adding or removing a row requires a fresh preview and acknowledgement. Omitted containers remove their children, while unaffected array positions are preserved. Removed names and values are not copied into the manifest. Add up to ten literal text replacement rows (search and replacement are each at most 256 characters). Rules run top to bottom after field omission; later rules can match earlier replacement output. Empty search rows are ignored; an empty replacement deletes the matched text. These are case-sensitive literal matches, not regular expressions. Replacement search text is not embedded in the manifest. Check the review acknowledgement before choosing a local destination. Changing review options invalidates the preview and acknowledgement. Cancelling the file dialog creates no export; navigating or closing the review discards its draft. Drafts expire after ten minutes. Saving uses the frozen preview, never a fresh capture of live data. Manual review/export remains available under the existing manual-access licensing policy.

The package contains a static manifest and escaped JSON text, with capture/window timestamps, artifact states, source truncation flags, field-omission and replacement occurrence counts and SHA-256 hashes. Empty means no retained entries in the selected window, not proof that no event occurred. Unavailable, oversized and omitted artifacts remain labelled. Capture is bounded to 30 seconds, three artifacts, 256 KiB per artifact and 4 MiB for the complete HTML file; excess artifacts are labelled rather than silently clipped. Replacements that make two field names identical are rejected; narrow the rule and preview again instead of silently losing evidence. Hashes establish byte integrity, not factual truth or anonymization. Arbitrary private text may remain: review before sharing.

The offline file contains no executable captured content or remote resources and uses a restrictive Content Security Policy. A hash-authorized fixed stylesheet wraps long JSON lines and tokens to fit the preview or browser width; selection and copied artifact text retain their original characters and line breaks. The preview is additionally sandboxed. There is no automatic upload or external sharing, and original evidence is not edited. This UI-only review path adds no MCP export bypass. Screenshots and masking, ZIP packaging and additional evidence types remain follow-up work on #336.


### Native image-element state

`browser_image_state({ workspaceId, tabId, selector })` passively samples one unique, connected top-level light-DOM HTML `img`, including a hidden image or an `img` inside `picture`. Selectors address the current document; snapshot `ref` input is rejected, even with a selector. Frames, shadow descendants, CSS backgrounds, canvas, SVG `image`, XML documents and `picture`/`source` containers are unsupported. The tab must already be active in its page lifecycle; inspection does not select, wake, focus, scroll, reload, fetch a source, call `decode()` or change attributes.

The report contains `observedAt` (Unix milliseconds), native `complete`, `naturalWidth`, `naturalHeight` and `hasSelectedSource` (native `currentSrc` is nonempty). **`complete: true` also includes broken and no-source images**; it is not a loaded/decoded/rendered verdict. Natural dimensions are density-corrected CSS pixels, not necessarily encoded-file pixels. Zero means intrinsic dimensions are unavailable. A selected source does not prove loading succeeded or identify the responsive variant.

Only these validated scalars cross the renderer boundary. Source URLs, lists, paths, query strings, fragments, alt text, markup and bytes are not returned or logged by the observation. Native `currentSrc` is transiently read inside the isolated renderer and reduced to a boolean; this may materialize a large string before reduction. It is not a source-allocation bound.

Limits are 1,000 selector characters, 5,000 top-level light-DOM elements (counted before native selector matching), 512 JSON characters per report, eight unsettled inspections per tab and a five-second publication deadline. Slots include native work and cleanup still pending after timeout. A deadline withholds late results; it does not interrupt renderer execution. The element-count bound limits match collection, not CSS selector CPU cost. Missing, ambiguous, invalid-selector, unsupported, document-limit and native-read failures are distinct and omit page-supplied error details.

The original element and document are retained until a final trusted renderer identity check. Main-owned workspace, document-commit, control and cancellation checks continue through final MCP publication, after audit work. **DOM/image state can still change after the last renderer check and before delivery.** Detach/reinsert or source changes that return to the original state between samples may go undetected. This is sampled state, not continuous identity, atomic delivery-time DOM identity, compositor-pixel proof, decode completion or future readiness. Separate geometry and network observations do not form an atomic joint snapshot. Activity history reflects the final publication outcome; a generic audit receipt records operation settlement and is not proof of atomic delivery.

### Native media-element state

`browser_media_state` separately reads one uniquely selected current top-level light-DOM `audio` or `video` element through a required unique `selector`; hidden audio is supported. Snapshot `ref` input is explicitly unsupported and rejected, including when supplied alongside a selector. Selectors resolve the current document; they do not identify a historical snapshot node, and a pre-call replacement matching the same selector is the current target. Identity and authority are guarded from acquisition through publication. It returns only `kind`, `observedAt` (Unix milliseconds), `paused`, `ended`, `seeking`, `muted`, `volume`, `playbackRate`, `currentTime`, `duration`, `readyState`, `networkState`, and `errorCode`. Duration is `{state:"finite", seconds}`, `{state:"unknown"}` or `{state:"infinite"}`. Error code is native MediaError 1–4 or `null`; no error message or source URL is acquired. Native `readyState` is 0–4 and `networkState` 0–3. Scalar validation rejects invalid values; volume is 0–1, playbackRate is bounded to ±1024, and finite times are nonnegative and at most `Number.MAX_SAFE_INTEGER`. Reports are bounded to 1024 JSON characters before transport.

Media inspection requires an already active website document. It neither wakes frozen/sleeping tabs nor selects/follows the tab, and never calls play/pause/load, seeks, focuses, scrolls or changes autoplay/permissions. Frames, shadow descendants, non-media, missing/ambiguous and obsolete targets fail. A native accessor/read failure reports unavailable, a non-media target reports unsupported, and a supported media error remains an ordinary state report with its numeric code. Native scalars are acquired in an isolated world; page-defined getters are not used. The five-second inspection and publication guard conservatively rejects DOM changes, replacement, navigation, closure, cancellation and authority changes while the report is pending. Up to eight transient guards retain identity only until settlement/expiry. Native state is a point-in-time observation; playback may progress naturally between reads.

`browser_evaluate` remains an arbitrary-script workaround. `browser_tabs` audibility and `browser_audio` tab mute are separate from media-element paused/muted/volume state: `paused:false` does not prove audible output, speaker routing, or correct media content, and `paused:true` does not establish autoplay denial. Media-state inspection returns no tracks, metadata, bytes, screenshots, sound capture, WebAudio graph or devices.

### Opt-in native form validity

Set `includeValidity: true` on `browser_element_inspect` with one unique CSS selector to add `formValidity`. This passive observation supports rendered top-level native input, select and textarea controls. Password, file, hidden, one-time-code and payment-autocomplete controls, customized built-ins, editors, frames and shadow descendants are excluded. Unsupported controls report `unavailable`; ambiguous or missing selectors are rejected. Snapshot refs, password occupancy, CSS provenance and rendered fonts cannot be combined with this option. Omitted/false preserves ordinary inspection.

An `observed` report contains `willValidate` and the eleven native `ValidityState` booleans: `valueMissing`, `typeMismatch`, `patternMismatch`, `tooLong`, `tooShort`, `rangeUnderflow`, `rangeOverflow`, `stepMismatch`, `badInput`, `customError` and `valid`. Disabled/readonly controls can have `willValidate: false` independently of the flags. Values, lengths, validation messages, raw constraints and custom-error text are not added. Reads use native accessors in an isolated world and do not call `checkValidity`, `reportValidity`, `setCustomValidity` or submission methods. Existing inspection metadata is still page-authored and may contain private information.

Native validity is not exact-value acceptance, whole-form readiness, server validation or submission success. An optional empty control may be valid. Length-constraint flags follow Chromium's user-input semantics and can differ after programmatic assignment. See the [HTML constraint-validation API](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#the-constraint-validation-api). Results are point-in-time observations, not a promise that validity remains unchanged.

Customized built-ins are excluded even when created programmatically or after removing their `is` attribute. For the three native control brands only, the isolated-world check calls native `attachInternals`, which must reject before attaching internals under the [HTML algorithm](https://html.spec.whatwg.org/multipage/custom-elements.html#dom-attachinternals). Only Chromium's exact non-custom-element refusal is accepted; unexpected API behavior or changed wording rejects the control conservatively. This reads no field content, invokes no author method and creates no internals. Native exception text is used only for this internal eligibility check and is never returned.

Inspection does not focus, scroll, follow-select, wake or thaw tabs. Sleeping, waking and frozen tabs are rejected. Temporary identity/type guards are bounded to eight pending requests per document and expire after five seconds. Tree changes, target replacement, sensitive type/autocomplete transitions, navigation, cancellation and authorization changes invalidate pending results. Guards remain active through final MCP publication after audit persistence; slow persistence can therefore expire an observation. The deadline does not bound disk I/O or guarantee cancellation of Chromium execution. No permanent observer, automatic retry, validation UI or form mutation is installed.

### Expected text value comparison

To check whether a text field still holds an expected string, pass `expectedValue` (at most 4,096 UTF-16 code units) to `browser_element_inspect` with one unique CSS selector. Hronaut reads the field's current native value in an isolated world and compares the two there. The result is `valueComparison`, which is one of `{ "status": "match" }`, `{ "status": "mismatch" }` or `{ "status": "unavailable", "reason": "unsupported-target" | "native-unavailable" | "oversized" }`. Neither the expected nor the observed value is returned, and no length, prefix, hash or mismatch position is returned either. The comparison is exact, with no trimming, case folding or Unicode normalization. It uses the current value rather than the HTML `value` attribute and ignores page-defined getters. A textarea's value uses Chromium's native newline normalization.

Only a rendered top-level `<input type="text">` or `<textarea>` is supported, including disabled and read-only controls. The same sensitive and unsupported targets as form validity are excluded: password, other input types, one-time-code and payment autocomplete, hidden controls, customized built-ins, editors, frames and shadow descendants. A field whose value exceeds 4,096 code units reports `oversized` instead of a truncated match. Snapshot refs, form validity, password occupancy, sizing inputs, CSS provenance and rendered fonts cannot be combined with this option. The match bit still discloses whether a guess was right, so use it only for values the caller already knows. It does not focus, scroll, fire events, or wake or thaw tabs, and it keeps the same identity, document, workspace and settlement checks as form validity. A match is a point-in-time observation, not proof that the value was saved or accepted.

### Opt-in password occupancy

`browser_element_inspect` accepts `includePasswordOccupancy: true` for one uniquely resolved top-level light-DOM native password input. Its optional `passwordOccupancy` field is `empty`, `nonempty`, or `unknown`. Default inspection and snapshots are unchanged. Unsupported controls, hidden controls, editors and password inputs marked with OTP/payment autocomplete produce `unknown`; frames and shadow descendants are outside this scope. Missing/ambiguous targets and stale observations fail instead of silently rebinding.

The native string exists transiently inside an isolated page-world getter call and is immediately reduced to the enum. Values, lengths, masked characters, hashes and password-manager metadata are not returned. This is point-in-time native control occupancy, not evidence of correctness, authentication, account identity or permission to submit. Authorized clients can already perform a state-only `browser_evaluate`; this option supplies a typed, lifecycle-checked observation.

Occupancy does not focus, scroll, fill, submit, select or wake a tab. Sleeping, waking or frozen tabs are rejected. CSS provenance (`cssProperties`) and `includeFonts: true` cannot be combined with occupancy. Collection uses no CDP DOM acquisition. Temporary per-request identity/type guards expire after five seconds, with at most eight pending guards in a document; any tree change conservatively invalidates the observation. Request cancellation, authority/control generation changes, navigation, tab closure, target replacement and password-type ABA transitions discard pending evidence. MCP publication checks run after audit persistence and capability settlement; identity/type guards remain active until this final check. Slow audit persistence can outlive the guard deadline and cause the observation to fail; the deadline does not bound audit disk I/O. No retries or permanent observers are installed. Existing inspection metadata remains page-authored and should be reviewed before sharing.

### Semantic multiple selection

`browser_select` preserves the existing `value` string contract. Alternatively, provide `values` for one unique top-level light-DOM native `select[multiple]`: exact option values replace the complete selection; `[]` clears it. Provide exactly one of `value` or `values`. Duplicate requested values and ambiguous matching option values are rejected. Limits are 50 requested values, 1024 UTF-16 units each, 8192 units total, and 1000 options per target, each with a native value of at most 1024 UTF-16 units. Every option value is checked, including unrequested options, bounding the retained value snapshot to 1,024,000 units. Reading an oversized native value still requires transient allocation before its length can be rejected. Disabled controls, fieldsets (with the native first-legend exception), options and optgroups cannot be changed. Disabledness uses Chromium’s native `:disabled` matching in the isolated world, including optgroup inheritance through intervening elements; page-world prototype overrides do not supply a fallback. The whole set is validated before any option is changed.

This is semantic state-setting, not modifier-click, keyboard or touch emulation. It performs no focus, scroll or submission. One bubbling synthetic `input` and then `change` event is sent; both see the complete requested set unless an earlier handler changes it. A handler that changes the selection, option identities or target stops further events and returns uncertainty. Only the original target is modified. Results contain a count and immediate native-state observation, not option labels/values or an application/server acceptance claim.

Workspace, capability, pause, cancellation and document authority are checked before submitting the renderer operation and before publishing its result. Once submitted, effects can be uncertain; no automatic retry or rollback occurs. A later asynchronous application update can still supersede the immediate observation. Frames, shadow targets, custom ARIA listboxes, form-fill batches and Repro recording/export are outside this option-set increment.

Audit receipts record operation settlement before audit persistence and final MCP publication checks. A persisted success receipt alone is not proof of final publication authority; use the final response and terminal activity for that outcome. Authority changes after renderer submission may produce `OUTCOME_UNKNOWN` even if the selection took effect. A `NOT_DISPATCHED` response means no selection renderer operation was submitted; an acknowledged `REJECTED` response with `effects: none` means whole-set validation changed no options. None of these outcomes authorizes automatic replay.


### Explicit file-source evaluation (Linux)

`browser_evaluate_file` executes one captured source file in a specific top-level HTTP(S) document. Supply outer `workspaceId` and `tabId`, plus a strict `source` object containing `path`, `sha256`, `workspaceId`, `tabId`, and `expectedOrigin`. Outer and embedded targets must match. The path must be canonical, absolute POSIX syntax, without symlink components; the origin must be its exact HTTP(S) origin spelling. Only regular files, strict UTF-8 and at most 65,536 captured bytes are accepted. SHA-256 is computed over those exact raw bytes, including any BOM. The same captured source is submitted once without reopening the caller path.

This operation requires a separate capability credential. In Settings, choose the complete preset and set the exact whole-object argument constraint `browser_evaluate_file.source` to an array of approved source tuples. Each complete object is hashed as one value; independent per-field constraints cannot authorize a combination. Ordinary complete profiles, read-only profiles, inline `browser_evaluate`, uploads, exports and compatibility full-access credentials do not confer this permission. Delegated credentials must retain or narrow the whole-tuple constraint. Missing authority returns an unavailable/unauthorized result before filesystem lookup. The tool is destructive, non-idempotent and open-world.

Linux filesystem namespace means any filesystem mounted there, including network, FUSE and pseudo filesystems; it does not prove local-disk provenance. Linux procfs is required; other platforms and Windows/UNC paths are unsupported. The process owns two acquisition slots across clients and reconnects. The one-second acquisition deadline and cancellation stop delivery and future dispatch, but do not cancel native IO or free a slot before actual completion and handle cleanup. Uncertain close quarantines both the slot and its retained handle. File operations can block kernel/libuv work indefinitely. A separate process-wide limit also bounds pending file evaluations at two; pending CDP execution remains owned after the caller stops waiting.

Dispatch uses the current document's CDP `uniqueContextId`, with no direct-evaluation fallback. Preparation rechecks target identity, current authorization, workspace ownership, pause/control, human input and review state. A review certificate conservatively rejects any intervening human-waiting service request, including reads in another workspace; start a fresh explicit decision after inspecting state. Consuming a reviewed attempt does not extend its original dispatch deadline. The execution-stage 30-second deadline cannot undo or prove nonexecution after submission; later audit and review settlement are not a hard transport deadline. A retained document-commit guard also rejects a navigation that started before admission and commits while acquisition is waiting. Successful publication rechecks current authority and document identity after settlement. Cancellation or disconnect retains workspace mutation ownership until queued/submitted native evaluation and its cleanup settle; a stuck evaluation can keep that workspace unavailable. Timed-out acquisition cannot later submit a script, while its separate process-wide resource capacity remains held until native file cleanup. `NOT_DISPATCHED` records that no script submission was attempted; `OUTCOME_UNKNOWN` preserves possible effects after submission. Neither outcome authorizes automatic replay. Successful `RETURNED` output is a script result, not proof of an application postcondition.

Automatic tool errors and audit records omit the file path, source and script exception excerpts. Explicit page-script return values remain output. The hash proves byte identity, not safety or authorship; expected origin constrains the initial target, not network egress. Normal page JavaScript retains its capabilities, including possible fetch and dynamic import. This feature adds no Node privileges, host module resolution, dependency installation, remote-source downloader or implicit file search.


### Selected-element computed sizing inputs

Set `includeSizingInputs: true` on `browser_element_inspect` with one unique CSS selector to add `sizingInputs`: `flex-basis`, `flex-grow`, `flex-shrink`, `min-width`, `max-width`, `min-height`, `max-height`, and `align-self`. These eight computed values accompany the existing sampled box; they are not a rendered flex-item diagnosis. Identical values may occur outside flex layout, including beneath closed shadow roots. There is no parent collection or inference of participation, applicability, cause, resolved flex base size, or cascade winner. Direct-container inspection from #732 remains outside this partial feature.

Grow/shrink are finite nonnegative numbers capped at 1,000,000,000. Other values use fixed keyword lists or nonnegative `px`/`%` tokens of at most 64 characters, capped at 1,000,000,000; unsupported expressions (including `calc()` and `anchor-size()`), units and keywords become null before IPC. Returned `auto`, percentages and intrinsic keywords remain distinct from measured physical geometry; native `getComputedStyle` returns CSSOM resolved values and can resolve authored `min-width:auto` to `0px` outside flex layout, so these are not authored declarations; values are not resolved against a container. A null field does not mean zero or inapplicable.

The option requires an already active tab and cannot combine with snapshot refs, validity, password occupancy, CSS provenance or rendered fonts. It uses the existing top-level light-DOM selector scope without entering frames or shadow roots or attaching a debugger. Default inspection is unchanged. Existing selected-element text/attribute privacy filtering still applies; this option adds no text, attributes, parent or sibling data. Selectors are capped at 1,000 characters; acquisition and settlement reject HTML documents above 5,000 light-DOM elements using a count-only preflight. This bounds node enumeration, not native selector/layout CPU time or allocation of a computed CSS string before reduction. Up to eight transient target handles expire after five seconds; main-process slots retain ownership until submitted native work and cleanup settle. `includeScroll` may accompany these fields under its existing selected-element contract. The same connected unique target is checked again at the final renderer settlement, and existing authority/navigation/publication checks apply. Samples and publication are not atomic across awaits; temporary remove/reinsert or reparent-and-return cycles between samples are not detected, and computed values may change after sampling.
